# 요구사항_정의(create-prd) — 도메인 개요

## 도메인 정의

`create-prd` 스킬이 담당하는 영역이다. 제품이나 프로젝트를 새로 시작할 때 무엇을 왜 만드는지를 질의응답으로 확정하고, 그 결과를 PRD 문서 한 편으로 남긴다. 해법과 기술 선택은 다루지 않는다.

계획서 흐름과는 독립적이다. PRD가 없어도 계획을 세울 수 있고, PRD가 있으면 `create-plan`과 `create-docs`가 의도의 근거로 삼는다.

### 책임 범위

| 구분 | 내용 |
| --- | --- |
| 담당한다 | 여덟 카테고리의 질의응답, 요구사항의 필수·선택 구분, 성공 판정 기준 확보, 미해결 질문의 관리, PRD 확정 |
| 담당하지 않는다 | 구현 방식과 기술 선택(계획_작성), 기능 단위의 설계, 구현과 문서화 |

## 유비쿼터스 용어 사전

| 용어 | 영문 표기 | 정의 |
| --- | --- | --- |
| PRD | Product Requirements Document | 제품의 목적·목표·요구사항을 담은 문서 한 편 |
| 카테고리 | category | 문서의 한 절을 채우기 위한 질문 묶음. 여덟 개가 순서를 가진다 |
| 넘어갈 조건 | exit condition | 다음 카테고리로 이동해도 되는지 판정하는 기준 |
| 요구사항 | requirement | `R1` 형식의 ID를 가지며 필수와 선택 중 하나로 표시되는 항목 |
| 충족 판정 | acceptance criterion | 무엇을 보면 그 요구사항이 충족된 줄 아는지 |
| 미해결 질문 | open question | 확정하지 못한 항목. 결정 주체와 필요 시점을 함께 적는다 |

## 핵심 비즈니스 규칙

1. 산출물은 단일 문서 한 편이며 여덟 절을 넘기지 않는다. 절마다 표 하나 또는 문단 셋 이내로 유지한다.
2. 여덟 카테고리를 순서대로 순회한다. 카테고리마다 열린 질문을 먼저 던지고, 답변만으로 절을 채우기 어려울 때만 선택지 두셋과 각 선택이 만드는 차이를 제시한다.
3. 넘어갈 조건을 만족해야 다음 카테고리로 이동한다. 질문 횟수를 미리 제한하지 않는다.
4. 요구사항은 모두 필수와 선택 중 하나로 갈리고, 각각 충족 판정 기준을 가진다.
5. 목표에는 관찰 가능한 성공 판정 기준이 하나 이상 붙는다. "빠르다", "편리하다"처럼 사람마다 다르게 읽히는 표현은 수치나 관찰 가능한 상태로 바꾼다.
6. 사용자 항목은 직군이나 상황으로 좁힌다. "모든 사용자"는 넘어갈 조건을 만족하지 못한다.
7. 범위 밖의 제외 항목에는 이유를 함께 적는다.
8. 해법과 구현 방식은 쓰지 않는다. 답변이 구현 방식으로 흐르면 PRD의 범위가 아님을 알리고 목적과 요구사항으로 되돌린다.
9. 추측으로 빈칸을 메우지 않는다. 확정하지 못한 내용은 `미해결 질문` 절에 남기며, 항목이 남아 있으면 확정하지 않는다.
10. 약어와 내부 용어는 처음 나오는 자리에서 한 번 풀어 쓴다. 같은 내용을 두 절에 반복하지 않는다.

### 예외 케이스

| 상황 | 처리 |
| --- | --- |
| 요청의 대상이 기능 하나의 구현 방식이다 | PRD를 만들지 않고 `/create-plan`을 안내한 뒤 종료한다 |
| 사용자가 카테고리를 건너뛰자고 요청한다 | 해당 절을 비우지 않고 미확정 내용을 `미해결 질문`으로 옮긴 뒤 다음으로 넘어간다 |
| 답변이 선택지 밖으로 나온다 | 선택지에 맞추지 않고 그 답변을 새 기준으로 삼아 질문을 이어간다 |
| 같은 우려를 세 번 짚어도 답변이 유지된다 | 우려를 문서에 기록하고 진행한다 |
| 사용자가 미해결 항목을 남긴 채 마무리하기를 요청한다 | 확정 대신 초안 상태임을 문서에 표시하고 남은 항목을 그대로 둔다 |
| 보관 경로가 `.gitignore`에 없다 | 사용자에게 보관 방식을 확인한다 |
