# 문서_루트_판정(docs-root) — 도메인 개요

## 도메인 정의

네 스킬이 산출물을 어디에 둘지 정하는 규칙을 담당한다. 프로젝트마다 문서를 두는 위치가 다르므로, 고정된 기본값을 쓰지 않고 저장소를 조사해 문서 루트를 판정한 뒤 그 루트를 기준으로 계획서와 PRD와 개발 문서의 경로를 만든다.

규칙의 정본은 `plugins/project-helper/skills/_shared/docs-root.md` 한 편이며, 네 스킬이 모두 이 문서를 읽는다. 어느 스킬에도 속하지 않는 공용 참조 문서를 두는 방식은 이 도메인에서 처음 도입되었다.

### 책임 범위

| 구분 | 내용 |
| --- | --- |
| 담당한다 | 문서 루트의 탐색 순서, 후보가 여럿일 때의 좁히기 기준, 판정 결과를 남기는 방식, 루트를 기준으로 만드는 산출물 경로 |
| 담당하지 않는다 | 각 산출물의 내부 구조와 형식(계획_관리, 요구사항_정의, 개발문서_생성), 보관 경로를 `.gitignore`에 등록할지의 판단(각 스킬의 준비 절차) |

## 유비쿼터스 용어 사전

| 용어 | 영문 표기 | 정의 |
| --- | --- | --- |
| 문서 루트 | docs root | 계획서와 PRD와 개발 문서가 함께 놓이는 최상위 디렉터리 |
| 탐색 순서 | lookup order | 문서 루트를 찾기 위해 차례로 적용하는 네 단계 |
| 후보 | candidate | 탐색에서 문서 루트로 판정될 수 있는 디렉터리 |
| 조상 기준 | ancestor rule | 작업 대상 파일 경로의 가장 가까운 조상에 있는 후보를 고르는 좁히기 기준 |
| 루트 기록 | root record | 계획 최상위 문서에 남기는 확정된 문서 루트와 그 판정 근거 |
| 공용 참조 문서 | shared reference | `skills/_shared/` 아래에 두어 여러 스킬이 함께 읽는 판정 규칙 |

## 핵심 비즈니스 규칙

1. 보관 경로를 정할 때 `docs/`를 기본값으로 가정하지 않는다. 탐색 순서로 문서 루트를 판정한 뒤 그 루트를 기준으로 경로를 만든다.
2. 탐색은 네 단계다. 프로젝트 지시사항의 명시 경로, 개발 문서의 표지가 있는 디렉터리, 계획서가 쌓인 디렉터리의 부모, 그리고 마지막으로 `docs/`다. 앞 단계에서 결정되면 뒤 단계를 보지 않는다.
3. 탐색은 저장소 전체를 훑지 않는다. 생성물이 쌓이는 디렉터리를 제외하고 저장소 루트에서 네 단계 깊이까지만 찾는다.
4. 후보가 둘 이상 나오는 것은 모노레포에서 정상이다. 곧바로 사용자에게 묻지 않고 조상 기준, 이름 일치 기준을 차례로 적용해 좁힌다.
5. 두 기준으로도 좁혀지지 않을 때만 사용자에게 후보를 번호 매김 목록으로 제시한다.
6. 작업 대상 코드가 아직 없는 스킬은 조상 기준을 쓸 수 없으므로 이름 일치 기준부터 적용한다.
7. 확정한 루트는 계획 최상위 문서에 기록한다. 기록이 있으면 이후 스킬은 탐색을 다시 하지 않는다.
8. 사용자에게 물어 정한 경우에만 그 경로를 프로젝트 지시사항에 적어 두기를 제안한다. 명확하게 판정된 경우에는 제안하지 않는다.
9. 루트를 기준으로 계획서는 `<루트>/plans/`, PRD는 `<루트>/prds/`, 개발 문서는 `<루트>` 바로 아래에 둔다.

### 예외 케이스

| 상황 | 처리 |
| --- | --- |
| 지시사항의 경로가 존재하지 않는다 | 탐색으로 넘어가지 않고 사용자에게 경로를 확인받는다. 오타를 조용히 덮어쓰지 않기 위해서다 |
| 개발 문서 표지와 계획서 위치가 서로 다른 디렉터리를 가리킨다 | 개발 문서 쪽을 우선한다. 더 확정된 구조이기 때문이다 |
| 정한 루트에 다른 문서 체계가 이미 있다 | 덮어쓰지 않고 사용자에게 경로를 확인받는다 |
| 계획 최상위 문서에 기록이 없다 | 기록 규칙이 도입되기 전의 계획서이므로 탐색으로 판정하고, 그 사실을 알린 뒤 진행한다 |
| 기록된 루트가 현재 저장소에 없다 | 진행을 멈추고 사용자에게 알린다 |
| 후보가 없어 `docs/`로 정했는데 그 디렉터리도 없다 | 만들고 그 사실을 알린다 |
