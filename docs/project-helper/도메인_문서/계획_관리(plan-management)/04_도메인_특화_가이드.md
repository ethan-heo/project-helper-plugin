# 계획_관리(plan-management) — 도메인 특화 가이드

## 외부 의존성

| 대상 | 종류 | 용도 |
| --- | --- | --- |
| `grep` | 명령줄 도구 | 두 검증 스크립트가 상태·진행률·항목 형식을 검사한다 |
| `find` | 명령줄 도구 | 도메인 디렉터리와 기능 계획서를 열거한다 |
| Git | 버전 관리 | 구현 항목 하나가 커밋 하나에 대응한다. 브랜치 이름은 계획 디렉터리 아래 경로에서 확장자를 뺀 값이다 |

### 설정

| 항목 | 값의 출처 | 비고 |
| --- | --- | --- |
| 계획서 보관 경로 | 프로젝트 지시사항 | 이 저장소는 `docs/project-helper/plans/`를 쓰며 `.gitignore`에 등록되어 있다 |
| 브랜치 이름 | 계획서 경로 | 기능 계획서는 `<도메인>/<기능>`, 계획 묶음은 `feature/<주제>` |
| 커밋 메시지 형식 | 프로젝트 지시사항 | 없으면 최근 커밋 열 개로 추정해 사용자에게 확인받는다 |

## 핵심 테스트 시나리오

| ID | 상황 | 기대 동작 |
| --- | --- | --- |
| T1 | 최상위 README, 도메인 README, `계획 완료` 기능 계획서를 갖춘 정상 계획서를 검사한다 | 두 스크립트가 모두 통과한다 |
| T2 | 날짜 디렉터리 바로 아래의 단일 초안을 `impl-plan` 스크립트에 넘긴다 | 검사가 실패하고 구조 이전으로 돌려보낸다 |
| T3 | 기능 계획서에 `<!-- 사용자 검토 필요 -->`가 남아 있다 | 검사가 실패한다 |
| T4 | 구현 항목 수와 진행률의 전체 수가 다르다 | 정합성을 확인해 전체 수를 항목 수로 맞춘다 |
| T5 | 완료된 계획에 연관된 추가 작업을 제시한다 | 기존 계획서를 갱신하고 단계를 `계획 완료`로 되돌린다 |
| T6 | 완료된 계획에 무관한 작업을 제시한다 | `추후 작업` 절에 기록만 남기고 구현에 넣지 않는다 |

### 실행 방법

```bash
bash -n plugins/project-helper/skills/create-plan/scripts/validate-plan.sh
bash -n plugins/project-helper/skills/impl-plan/scripts/validate-plan.sh
```

T5와 T6은 스크립트로 판정할 수 없는 대화 시나리오이므로 설치된 세션에서 직접 확인한다.

## 트러블슈팅

| 증상 | 원인 | 조치 |
| --- | --- | --- |
| `impl-plan`이 계획서를 찾지 못한다 | 계획서가 세 층 구조가 아니거나 보관 경로 밖에 있다 | 구조 이전 절차로 세 층을 만든 뒤 다시 시작한다 |
| 계획서가 `계획 완료`인데 구현이 시작되지 않는다 | 선행 관계가 닫히지 않았다 | 최상위 문서의 선행 관계 표에서 선행 ID를 찾아 해당 항목의 체크 여부를 확인한다 |
| 구현 도중 상태가 `완료`로 바뀌지 않는다 | 체크되지 않은 항목이나 통과하지 못한 검증이 남아 있다 | 남은 항목과 대응 검증을 확인한다 |
| 계획서가 Git 상태에 잡힌다 | 보관 경로가 `.gitignore`에 없다 | 보관 경로를 `.gitignore`에 추가한다 |
| 같은 주제의 계획서가 여러 개 늘어난다 | 연관된 추가 작업을 새 계획으로 만들었다 | 연관성 판정을 먼저 하고, 연관되면 기존 계획서를 갱신한다 |
| 선행 ID가 가리키는 계획서를 찾을 수 없다 | ID의 앞 두 조각이 실제 도메인·기능과 어긋난다 | ID 용어 표와 디렉터리 이름을 대조해 ID를 고친다 |
