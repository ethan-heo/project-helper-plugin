# 스킬_실행_맥락(skill-trigger) — 도메인 개요

## 도메인 정의

어떤 요청에서 어느 스킬이 켜지고, 켜진 뒤의 대화가 어디까지 그 스킬의 입력으로 해석되는지를 정하는 영역이다. 네 스킬이 이름과 목적에서 서로 가깝기 때문에, 발동 조건과 맥락 유지·종료 규칙을 같은 방식으로 맞춰 두지 않으면 요청이 엉뚱한 스킬로 들어간다.

규칙의 실체는 각 `SKILL.md`의 `description` 필드와 `실행 원칙`·`경계` 절에 나뉘어 있다. 이 도메인은 네 파일에 걸쳐 같은 문장 구조로 유지되는 그 규칙을 하나로 설명한다.

### 책임 범위

| 구분 | 내용 |
| --- | --- |
| 담당한다 | 스킬 발동 조건 서술, 스킬 명시 후의 맥락 해석, 설명 질문과 실행 요청의 구분, 맥락 종료 조건, 스킬 사이의 인계 |
| 담당하지 않는다 | 각 스킬 내부의 작업 절차(해당 도메인), 플러그인 설치와 등록(배포와_설치) |

## 유비쿼터스 용어 사전

| 용어 | 영문 표기 | 정의 |
| --- | --- | --- |
| 발동 | trigger | 사용자의 자연어 요청에 맞는 스킬이 자동으로 켜지는 일 |
| 명시 호출 | `/create-plan` 등 | 사용자가 슬래시 명령으로 스킬을 직접 지정하는 일 |
| 실행 맥락 | execution context | 스킬이 켜진 뒤 후속 답변을 그 스킬의 입력으로 해석하는 상태 |
| 설명 요청 | explanation request | 스킬의 개념이나 사용법만 묻는 질문. 실행으로 해석하지 않는다 |
| 인계 | handover | 한 스킬이 자신의 경계 밖 요청을 다른 스킬로 넘기는 일 |
| 근접 요청 | near-miss query | 발동해야 할 요청과 표현이 비슷하지만 발동하면 안 되는 요청 |

## 핵심 비즈니스 규칙

1. 사용자가 스킬을 명시하면 뒤따르는 답변은 기본적으로 그 스킬의 작업 입력으로 해석한다.
2. 질문이 스킬의 개념이나 사용법만 묻는 설명 요청이면 작업을 진행하지 않고 일반 답변을 제공한다.
3. 실행 맥락은 해당 작업이 끝나거나, 사용자가 다른 스킬을 명시하거나, 일반 질문을 명시할 때까지 유지한다.
4. `description`에는 발동해야 할 상황과 발동하면 안 되는 상황을 함께 적는다. 사용하지 않을 상황에는 대신 쓸 스킬 이름을 붙인다.
5. 각 스킬은 `경계` 절에서 자신이 맡지 않는 요청을 어느 스킬로 넘길지 명시한다.
6. 네 스킬은 계획서와 PRD를 매개로 이어질 뿐 서로의 파일을 읽지 않는다. 인계는 사용자에게 다음 스킬을 안내하는 방식으로만 이루어진다.
7. 발동 정확도는 `evals/trigger-eval.json`의 사례로 측정한다. 각 질의를 여러 번 던져 어느 스킬이 켜지는지 센다.

### 예외 케이스

| 상황 | 처리 |
| --- | --- |
| 계획서 없이 "이거 구현해줘"라고 요청한다 | `impl-plan`이 아니라 `create-plan`으로 계획서를 먼저 만든다 |
| 계획서가 이미 `계획 완료`인데 계획 작성을 요청한다 | `create-plan`이 아니라 `/impl-plan`으로 안내한다 |
| 기능 하나의 구현 방식을 PRD로 쓰자고 요청한다 | `create-prd`가 아니라 `/create-plan`으로 안내한다 |
| 구현이 끝나지 않은 계획의 문서화를 요청한다 | `create-docs`를 진행하지 않고 `/impl-plan`으로 구현을 먼저 마치도록 안내한다 |
| 구현 중 계획의 전제가 깨진다 | 진행을 멈추고 현재 상태를 유지한 채 `create-plan`으로 넘긴다 |
| 작업 중 무관한 요청이 들어온다 | 연관성을 판정해 `추후 작업`에 기록하고 현재 맥락을 유지한다 |
