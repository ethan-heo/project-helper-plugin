# project-helper 스킬 사용법 튜토리얼

브라우저에서 도는 Todo 리스트를 소재로, `project-helper`의 스킬 다섯 개를 부르는 순서와 각 스킬이 남기는 산출물을 따라갑니다.

## 0장. 이 문서를 읽는 방법

### 이 문서가 다루는 것

`project-helper`의 스킬 다섯 개를 부르는 순서와, 각 스킬이 남기는 산출물의 모양을 보여 줍니다. 소재는 브라우저 한 화면에서 도는 Todo 리스트입니다.

Todo 리스트 코드는 만들지 않습니다. 4장과 5장은 실행 기록 대신 구현이 어떤 순서로 진행되는지를 표로 서술합니다.

### 장 구성

| 장 | 스킬 | 남는 산출물 |
| --- | --- | --- |
| 1 | `create-prd` | PRD 한 편 |
| 2 | `create-sub-prd` | 하위 PRD 두 편 |
| 3 | `create-plan` | 계획서 네 파일 |
| 4 | `impl-plan` | 커밋과 갱신된 계획서 |
| 5 | `explain-commit` | 커밋별 학습 문서 |

1장부터 3장까지는 아래 다섯 절을 같은 순서로 둡니다.

- 언제 쓰는가
- 부르는 방법
- 대화 흐름
- 만들어진 산출물
- 다음 단계

4장과 5장은 실행 결과가 없으므로 `대화 흐름` 자리에 진행 표가 들어갑니다.

### 산출물을 확인하는 자리

각 장의 `만들어진 산출물` 절에서 부록 링크를 답니다. 전문은 문서 끝의 [부록 A](#부록-a-todo-리스트-prd-전문), [부록 B](#부록-b-하위-prd-전문), [부록 C](#부록-c-todo-리스트-구현-계획서-전문)에 모여 있습니다.

### 시작하기 전에

플러그인이 설치되어 있어야 스킬을 부를 수 있습니다.

```
/plugin marketplace add ethan-heo/project-helper-plugin
/plugin install project-helper@helpers
```

설치 후에는 새 대화부터 스킬이 잡힙니다. `claude plugin list`로 설치 결과를 확인합니다.

### 다섯 스킬을 언제 쓰는가

| 지금 상태 | 부를 스킬 |
| --- | --- |
| 무엇을 만들지 정하지 못했다 | `create-prd` |
| PRD가 커서 요구사항이 뭉뚱그려져 있다 | `create-sub-prd` |
| 무엇을 만들지는 정했고 방법을 정해야 한다 | `create-plan` |
| 계획서가 `계획 완료` 상태다 | `impl-plan` |
| 커밋은 쌓였는데 내용이 기억나지 않는다 | `explain-commit` |

## 1장. create-prd — 무엇을 만들지 정합니다

### 언제 쓰는가

만들 것의 윤곽은 있지만 요구사항이 아직 말로만 있을 때 부릅니다. "Todo 리스트를 만들고 싶다"까지만 정해진 상태가 여기에 해당합니다.

반대로 무엇을 만들지 이미 정해졌고 방법만 남았다면 이 스킬이 아니라 `create-plan`입니다.

### 부르는 방법

```
/create-prd 브라우저에서 도는 간단한 Todo 리스트를 만들고 싶습니다
```

스킬은 문서 루트를 판정해 `<루트>/prds/`에 `2026-09-04-todo-list.md` 초안을 만들고, 여덟 카테고리를 순서대로 묻기 시작합니다.

### 대화 흐름

카테고리마다 열린 질문이 먼저 오고, 답변만으로 절을 채우기 어려울 때 선택지가 따라옵니다.

> **AI** — 이 제품을 한 문장으로 설명하면 무엇입니까?
>
> **사용자** — 오늘 할 일을 적고 끝나면 지우는 화면입니다.

> **AI** — 지금은 이 일을 어떻게 처리하고 있습니까?
>
> **사용자** — 메모 앱에 줄글로 적고 끝난 줄에 줄을 긋습니다. 끝난 것과 남은 것이 섞여서 남은 개수를 세기 어렵습니다.

여기서 나온 "남은 개수를 세기 어렵다"가 뒤에 R5 요구사항으로 이어집니다. 배경 절의 문제 서술이 요구사항의 근거 자리를 만듭니다.

판단이 갈리는 자리에서는 선택지가 나옵니다.

> **AI** — 목록을 어디에 저장할까요?
>
> 1. 브라우저 로컬 저장소 — 서버가 필요 없고 한 브라우저에서만 보입니다
> 2. 서버 — 기기를 옮겨도 보이지만 계정과 서버가 필요합니다
>
> **사용자** — 1번으로 하겠습니다. 혼자 한 컴퓨터에서만 씁니다.

이 답변이 제약 절의 기술 조건과 범위 밖의 "서버 저장과 계정"을 동시에 확정합니다.

요구사항 카테고리에서는 각 항목이 필수와 선택 중 하나로 갈리고, 항목마다 충족 판정 기준이 붙을 때까지 질문이 이어집니다.

> **AI** — 완료 항목만 한 번에 지우는 기능은 필수입니까?
>
> **사용자** — 없어도 쓸 수는 있으니 선택으로 두겠습니다.

### 만들어진 산출물

PRD 한 편이 남습니다. 전문은 [부록 A](#부록-a-todo-리스트-prd-전문)에 있습니다.

확인할 자리는 세 곳입니다.

| 확인 지점 | 무엇을 보는가 |
| --- | --- |
| 요구사항 표 | 필수와 선택이 갈렸고 충족 판정이 모두 채워졌는가 |
| 범위 밖 표 | 제외 항목마다 이유가 붙었는가 |
| 미해결 질문 | 남은 항목이 없어야 확정된다 |

확정 직전에 `validate-prd.sh`가 여덟 절과 표기를 검사합니다. 미해결 질문이 남아 있으면 확정되지 않습니다.

### 다음 단계

요구사항이 여섯 줄로 뭉뚱그려져 있어 그대로는 구현 방식을 정하기 어렵습니다. 2장의 `create-sub-prd`로 묶음을 가릅니다.

## 2장. create-sub-prd — 요구사항을 묶음으로 가릅니다

### 언제 쓰는가

PRD는 확정됐는데 요구사항 한 줄이 너무 커서 그대로는 구현 방식을 정할 수 없을 때 부릅니다. 부록 A의 `R1 항목을 입력해 목록에 추가한다`는 공백 입력 처리와 입력창 초기화를 함께 안고 있어 한 줄로는 부족합니다.

요구사항을 새로 발굴하는 스킬이 아닙니다. 이미 있는 요구사항을 나누고 좁힐 뿐입니다.

### 부르는 방법

```
/create-sub-prd docs/prds/2026-09-04-todo-list.md 를 나눠주세요
```

스킬은 먼저 상위 PRD가 확정 상태인지 확인합니다. `미해결 질문`에 항목이 남아 있거나 `validate-prd.sh`를 통과하지 못하면 분해를 시작하지 않습니다.

### 대화 흐름

묶음 후보는 AI가 지어내지 않고 상위 PRD의 `사용자와 사용 상황` 절에서 끌어옵니다.

> **AI** — 상위 PRD의 사용 상황이 "할 일을 적을 때"와 "일을 끝냈을 때" 두 행입니다. 요구사항을 붙이면 아래 두 묶음이 나옵니다.
>
> | 묶음 | 담당 |
> | --- | --- |
> | 항목 관리 | R1, R2, R3, R6 |
> | 저장과 현황 | R4, R5 |
>
> **사용자** — 그대로 진행해 주세요.

후보는 판단 재료일 뿐이므로, 다른 묶음을 지정하면 그 지정이 배정이 됩니다. 배정이 끝나면 상위의 모든 ID가 어느 한 묶음에만 들어갔는지 검사합니다.

하위 PRD를 쓰는 동안에는 담당 요구사항을 더 좁은 항목으로 가르는 질문이 이어집니다.

> **AI** — R1이 성립하려면 무엇이 각각 가능해야 합니까?
>
> **사용자** — 입력한 값이 목록에 붙어야 하고, 붙은 뒤에는 입력창이 비어야 합니다. 공백만 넣으면 아무 일도 없어야 합니다.

이 답변 하나가 R1을 `R1-1`, `R1-2` 두 항목으로 가릅니다. 상위의 한 줄이 하위에서 판정 가능한 항목으로 바뀌는 자리입니다.

승계와 질의는 절마다 갈립니다.

| 절 | 처리 |
| --- | --- |
| 제약과 전제 | 상위에서 그대로 가져옵니다 |
| 사용자와 사용 상황 | 묶음의 근거가 된 행만 가져옵니다 |
| 요구사항 | 질의응답으로 새로 가릅니다 |

### 만들어진 산출물

상위 PRD가 `docs/prds/2026-09-04-todo-list/README.md`로 옮겨 가고, 그 옆에 하위 PRD 두 편이 놓입니다. 전문은 [부록 B](#부록-b-하위-prd-전문)에 있습니다.

확인할 자리는 세 곳입니다.

| 확인 지점 | 무엇을 보는가 |
| --- | --- |
| 상위 요구사항 표 | `하위 PRD` 열이 붙고 빈 행이 없는가 |
| 하위 문서의 머리 | `상위 PRD` 줄에 담당 ID가 적혔는가 |
| 하위 요구사항 ID | `R1-1`처럼 상위 ID를 이어받았는가 |

상위 요구사항의 서술은 지우지 않습니다. 상위만 읽어도 전체 범위가 보여야 하기 때문입니다.

### 다음 단계

무엇을 만들지가 판정 가능한 수준까지 좁혀졌습니다. 3장의 `create-plan`으로 만드는 방법을 정합니다.

## 3장. create-plan — 어떻게 만들지 정합니다

### 언제 쓰는가

무엇을 만들지는 정해졌고 방법을 정해야 할 때 부릅니다. 앞의 두 스킬과 달리 이 스킬은 코드베이스를 조사합니다. 기존 파일과 제약을 찾아 놓고, 그 위에서 사용자가 해법을 고르게 합니다.

계획서 없이 바로 구현을 요청해도 이 스킬로 돌아옵니다. 구현할 순서가 정해져야 되돌릴 수 있는 커밋 단위가 나오기 때문입니다.

### 부르는 방법

```
/create-plan 하위 PRD 두 편대로 Todo 리스트를 만들 계획서를 써주세요
```

스킬은 문서 루트를 판정하고, `<루트>/plans/`가 `.gitignore`에 있는지 확인한 뒤 초안 한 편을 만듭니다.

### 대화 흐름

섹션을 위에서부터 하나씩 확정합니다. 앞 섹션이 확정되어야 다음 섹션의 판단 재료가 생깁니다.

| 순서 | 섹션 | 이 자리에서 정하는 것 |
| --- | --- | --- |
| 1 | 요약 | 목표와 배경. 변경점은 비워 둡니다 |
| 2 | 상태 | 단계와 진행률. 자동으로 채워집니다 |
| 3 | 설계 | 해법과 근거, 기각한 대안 |
| 4 | 구현 순서 | 되돌릴 수 있는 커밋 단위 |
| 5 | 테스트 | 항목마다 대응하는 검증 |
| 6 | 요약 확정 | 변경점을 채우고 앞과 대조합니다 |

설계 섹션에 들어가기 전에 어떤 설계 유형이 필요한지 먼저 묻습니다.

> **AI** — 이 계획에는 구조 설계와 의사결정 설계가 필요해 보입니다. 상태 전이와 외부 연동은 해당하지 않습니다.
>
> **사용자** — 두 가지로 진행해 주세요.

해당하지 않는 유형은 계획서에 넣지 않습니다. 빈 절을 남기면 읽는 사람이 그 자리를 매번 확인해야 합니다.

설계 질문은 해법을 제시받는 자리가 아니라 사용자가 고르는 자리입니다.

> **AI** — 항목을 완료 표시할 때 화면을 어떻게 갱신할까요?
>
> 1. 목록 전체를 다시 그린다 — 분기가 없지만 항목이 많아지면 느려집니다
> 2. 바뀐 줄만 고친다 — 빠르지만 추가·삭제마다 분기가 생깁니다
>
> **사용자** — 1번입니다. 한 화면에 담기는 분량이라 다시 그려도 됩니다.

이 답변이 결정 요약 표의 한 행이 됩니다. 기각한 대안과 그 이유도 같은 행에 남습니다.

구현 순서를 채운 뒤에는 문서 경계를 정합니다.

> **AI** — 독립적으로 돌려 볼 수 있는 지점이 둘입니다. 항목 조작만으로 화면이 동작하는 시점과, 저장이 붙어 새로고침을 견디는 시점입니다. 기능을 `TODO-ITEM`과 `TODO-STORE` 둘로 가르겠습니다.
>
> **사용자** — 그렇게 해주세요.

기능이 하나뿐이어도 최상위·도메인·기능 세 층은 그대로 만듭니다.

### 만들어진 산출물

계획서 네 파일이 남습니다. 전문은 [부록 C](#부록-c-todo-리스트-구현-계획서-전문)에 있습니다.

확인할 자리는 네 곳입니다.

| 확인 지점 | 무엇을 보는가 |
| --- | --- |
| 최상위 문서 | 문서 루트와 선행 관계가 적혔는가 |
| 결정 요약 표 | 기각한 대안과 이유가 남았는가 |
| 구현 항목 | 항목마다 완료 판정 줄이 있는가 |
| 테스트 절 | 모든 구현 항목이 검증에 대응하는가 |

확정 직전에 `validate-plan.sh`가 세 층 구조와 상태 표기, 항목 형식을 검사합니다. 단계는 이때 `계획 완료`로 바뀝니다.

### 다음 단계

계획서가 `계획 완료`가 되면 구현을 시작할 수 있습니다. 4장의 `impl-plan`이 이 계획서를 입력으로 받습니다.

## 4장. impl-plan — 계획서대로 구현합니다

이 장부터는 실행 결과가 없습니다. Todo 리스트 코드를 만들지 않기로 했기 때문입니다. 대신 부록 C의 계획서를 입력으로 받았을 때 구현이 어떤 순서로 진행되는지를 표로 보여 줍니다.

### 언제 쓰는가

계획서의 단계가 `계획 완료`일 때 부릅니다. 계획서가 없는 상태의 "이거 구현해줘"는 이 스킬이 아닙니다.

중단했던 작업을 이어갈 때도 같은 스킬입니다. 현재 브랜치 이름으로 어느 계획서를 이어서 할지 판정합니다.

### 부르는 방법

```
/impl-plan todo-list 를 진행해주세요
```

### 시작하기 전에 확인하는 것

구현을 시작하기 전에 네 가지를 확인하고, 하나라도 어긋나면 시작하지 않습니다.

| 확인 대상 | 통과 조건 |
| --- | --- |
| 단계 | 상태 표가 `계획 완료`다 |
| 검토 표시 | 사용자 검토 표시가 남아 있지 않다 |
| 선행 관계 | 최상위 문서의 선행 ID가 닫혔다 |
| 작업 트리 | 커밋되지 않은 변경이 없다 |

부록 C의 최상위 문서에는 `TODO-STORE-001`의 선행이 `TODO-ITEM-004`라고 적혀 있습니다. 그래서 `store.md`는 `item.md`의 마지막 항목이 체크된 뒤에야 시작합니다.

브랜치는 `feature/todo-list`를 만들고, 기능 계획서마다 `TODO/item`과 `TODO/store`를 그 위에서 땁니다.

### 항목별 진행

항목 하나가 커밋 하나입니다. 아래는 부록 C의 구현 항목 여덟 개가 어떻게 처리되는지를 정리한 것입니다.

#### TODO/item 브랜치

| 항목 | 하는 일 | 대응 검증 | 커밋 메시지 |
| --- | --- | --- | --- |
| TODO-ITEM-001 | `index.html`과 `style.css`에 입력창과 빈 목록을 만든다 | 화면에 입력창이 보인다 | `feat: 화면 뼈대 추가 (TODO-ITEM-001)` |
| TODO-ITEM-002 | `app.js`에 목록 배열과 추가 함수를 만든다 | 공백 입력이 배열에 들어가지 않는다 | `feat: 항목 추가 구현 (TODO-ITEM-002)` |
| TODO-ITEM-003 | 완료 여부를 바꾸는 함수를 만든다 | 두 번 누르면 완료 값이 되돌아온다 | `feat: 완료 표시 구현 (TODO-ITEM-003)` |
| TODO-ITEM-004 | 항목 줄에 삭제 버튼을 만든다 | 지운 뒤 배열 길이가 하나 준다 | `feat: 항목 삭제 구현 (TODO-ITEM-004)` |

#### TODO/store 브랜치

| 항목 | 하는 일 | 대응 검증 | 커밋 메시지 |
| --- | --- | --- | --- |
| TODO-STORE-001 | 배열을 JSON으로 저장한다 | 저장된 문자열이 배열과 같다 | `feat: 목록 저장 구현 (TODO-STORE-001)` |
| TODO-STORE-002 | 화면을 열 때 저장분을 읽는다 | 복원한 완료 값이 유지된다 | `feat: 목록 복원 구현 (TODO-STORE-002)` |
| TODO-STORE-003 | 파싱 실패를 빈 배열로 받는다 | 잘못된 값에서 빈 배열이 나온다 | `fix: 깨진 저장분 처리 (TODO-STORE-003)` |
| TODO-STORE-004 | 미완료 개수를 화면 위에 그린다 | 완료 항목이 개수에서 빠진다 | `feat: 미완료 개수 표시 (TODO-STORE-004)` |

### 항목 하나가 끝날 때 계획서에 남는 것

계획서에서 고쳐지는 자리는 네 곳뿐입니다. 설계와 구현 순서의 내용은 건드리지 않습니다.

| 고치는 자리 | 무엇으로 |
| --- | --- |
| 체크박스 | `[ ]`에서 `[x]`로 |
| 구현 진행률 | `0 / 4`에서 `1 / 4`로 |
| 마지막 갱신 | 그날 날짜로 |
| 기록 줄 | 완료 판정 줄 아래에 무엇을 어떻게 했는지 |

항목이 끝나면 코드 변경만 커밋합니다. 계획서 갱신은 로컬에 남습니다. 계획서 경로가 `.gitignore`에 등록되어 있기 때문입니다.

### 계획이 틀렸을 때

구현 중에 설계의 전제가 바뀌는 사실을 발견하면 그 자리에서 멈추고 `create-plan`으로 돌아갑니다. 예를 들어 로컬 저장소를 쓸 수 없는 환경이 드러나면 `TODO-STORE`의 설계 전제가 무너지므로 계속 진행하지 않습니다.

함수 이름이 계획서와 다른 정도의 오차는 멈출 이유가 아닙니다. 그대로 진행하고 기록 줄에 적습니다.

### 만들어진 산출물

| 산출물 | 어디에 |
| --- | --- |
| 커밋 여덟 개 | `TODO/item`과 `TODO/store` 브랜치 |
| 갱신된 계획서 | 로컬의 `docs/plans/2026-09-04-todo-list/` |
| 정적 파일 세 개 | `index.html`, `style.css`, `app.js` |

기능 계획서를 다 끝내면 단계가 `완료`로 바뀌고, 기능 브랜치가 `feature/todo-list`로 병합됩니다. 기본 브랜치로는 병합하지 않습니다. 그 판단은 사용자의 몫입니다.
