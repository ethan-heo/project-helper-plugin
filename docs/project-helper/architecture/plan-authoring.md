# 계획 수립

## 목적과 문제

코드를 곧바로 고치면 구현 결정이 대화 속에 흩어지고, 구현 도중 전제가 바뀌어도 알아차리기 어렵습니다. 이 영역은 사용자와 함께 구현 결정을 좁혀, 구현자가 추가 질문 없이 실행할 수 있는 세 층 계획서로 기록합니다.

## 요구사항과 품질 속성

| 요구사항 | 판정 기준 |
| --- | --- |
| 세 층 구조 | 최상위 문서, 도메인 문서, 기능 계획서가 모두 있습니다 |
| 형식 검증 | `validate-plan.sh <계획 디렉터리>`를 통과합니다 |
| 검토 완료 | `<!-- 사용자 검토 필요 -->` 표시가 남아 있지 않습니다 |
| 인계 가능성 | 항목만 읽고 무엇을 어디에 할지 정할 수 있습니다 |
| 아키텍처 추적 | 최상위 문서에 기준 버전이 있고 설계가 결정 ID를 인용합니다 |

## 개념 모델

| 개념 | 뜻 |
| --- | --- |
| 최상위 문서 | 도메인 목록·공통 설계·선행 관계를 담은 `README.md` |
| 도메인 문서 | 기능 목록을 담은 도메인 디렉터리의 `README.md` |
| 기능 계획서 | 상태 표와 구현 항목을 담은 문서 |
| 단계 | `초안 작성`, `계획 완료`, `완료` 중 하나 |
| 완료 판정 | 항목이 끝났는지 판단하는 하위 줄 |
| 기준 아키텍처 | 계획 확정 시점의 아키텍처 경로와 버전 |

## 책임과 경계

`create-plan`은 준비, 섹션 작성, 문서 경계 긋기와 세 층 이전, 확정을 맡습니다. 준비 단계에서는 기존 문서와 아키텍처 문서를 확인하고, 문서 루트를 판정한 뒤 `<루트>/plans/`를 `.gitignore`에 등록합니다.

여러 계획이 따를 구조 결정은 아키텍처 결정 영역에 넘기고, 이 영역은 결정 ID를 인용만 합니다. 구현과 커밋은 계획 실행 영역이 맡습니다. 계획 실행 영역이 결함을 발견해 돌려보내면, `create-plan`은 요약부터 다시 쓰지 않고 어긋난 곳만 다시 설계합니다.

## 실행 흐름

1. 요구사항을 확인하고 기존 문서를 읽습니다. PRD가 있으면 요구사항의 의도를 먼저 확인합니다.
2. 아키텍처 문서가 없거나 새 구조 결정이 필요하면 같은 대화에서 `create-architecture`를 실행하고, 문서를 확정한 뒤 돌아옵니다.
3. 문서 루트를 판정하고 초안 한 편을 만듭니다.
4. 요약·상태·설계·구현 순서·테스트를 순서대로 사용자와 확정합니다.
5. 구현 순서의 선행 관계와 독립 검증 지점으로 도메인과 기능의 경계를 제안하고, 동의를 받아 세 층 구조로 옮긴 뒤 초안을 지웁니다.
6. 아키텍처 버전을 다시 확인해 최상위 문서에 기록하고, 검증 스크립트를 통과하면 단계를 `계획 완료`로 바꾼 뒤 `/impl-plan`을 안내합니다.

## 계약

| 정보 | 보내는 쪽 | 받는 쪽 |
| --- | --- | --- |
| `계획 완료` 기능 계획서 | 계획 수립 | 계획 실행 |
| 문서 루트 기록 | 최상위 문서 | 계획 실행 |
| 기준 아키텍처 버전 | 최상위 문서 | 계획 실행 |
| 선행 관계 표 | 최상위 문서 | 계획 실행 |
| 구현 항목 ID | 기능 계획서 | 계획 실행, 커밋 학습 |

계획서 형식에는 버전이 없습니다. 형식을 바꿀 때는 계획 실행 영역의 검증이 옛 표기(`- [ ]` 항목, 항목 줄 끝의 완료 판정)를 계속 받아들이도록 함께 고칩니다. 따르는 결정은 AD-002, AD-009, AD-014, AD-015, AD-016, AD-017, AD-018입니다.

## 위험과 미해결 질문

- `create-plan`과 `impl-plan`은 입력 단위가 다른 `validate-plan.sh`를 각자 가집니다. 형식을 바꿀 때 한쪽만 고치면, 확정한 계획서가 구현 직전 검사에서 실패합니다.
- `create-plan` 본문은 추가 작업을 설명하면서 `진행 중` 상태를 언급하지만, 검증 스크립트가 허용하는 단계는 `초안 작성`, `계획 완료`, `완료`뿐입니다.
- 미해결 질문은 없습니다.
