# 계획 실행

## 목적과 문제

확정한 계획을 실행하는 도중에 범위가 늘거나 전제가 바뀐 채로 구현을 이어 가면, 계획서와 실제 코드가 어긋납니다. 이 영역은 `계획 완료` 상태인 기능 계획서의 구현 항목을 하나씩 구현·검증·기록·커밋하고, 전제가 바뀌면 구현을 멈춥니다.

## 요구사항과 품질 속성

| 요구사항 | 판정 기준 |
| --- | --- |
| 입력 전제 | 기능 계획서가 `계획 완료`이고 `validate-plan.sh`를 통과합니다 |
| 선행 완료 | 선행 ID에 해당하는 항목이 체크되어 있습니다 |
| 버전 일치 | 기준 버전과 현재 아키텍처의 주 버전이 같습니다 |
| 커밋 단위 | 항목 하나가 커밋 하나이고 커밋 메시지에 항목 ID가 있습니다 |
| 수정 범위 | 계획서에서 상태 표·체크박스·마지막 갱신·기록 줄만 고칩니다 |
| 병합 한계 | `feature/<주제>`를 기본 브랜치로 병합하지 않습니다 |

## 개념 모델

| 개념 | 뜻 |
| --- | --- |
| 주제 브랜치 | 계획 전체의 작업을 모으는 `feature/<주제>` |
| 기능 브랜치 | 기능 계획서마다 따는 `<도메인>/<기능>` |
| 기록 줄 | 항목을 마친 뒤 붙이는 `- 기록:` 줄 |
| 전제 변경 | 설계가 가정한 사실이 코드와 달라진 상태 |
| 버전 대조 | 기준 버전과 현재 버전의 주 버전 비교 |

## 책임과 경계

`impl-plan`은 재개 위치 판정, 전제·선행·커밋 규칙 확인, 브랜치 준비, 항목 실행, 완료 처리와 병합을 맡습니다.

설계의 결함은 고치지 않고 계획 수립 영역으로 돌려보냅니다. 커밋 메시지 형식은 대상 저장소의 지시사항을 따르며, 지시사항이 없으면 최근 커밋에서 형식을 추정해 사용자에게 확인받습니다. 기본 브랜치 병합은 사용자가 요청할 때만 합니다.

## 실행 흐름

1. 계획서를 찾고 기준 아키텍처의 주 버전을 대조합니다. 주 버전이 다르면 구현을 멈추고 두 버전 사이에 대체된 결정 ID를 알립니다.
2. 이어서 하는 작업이면 작업 트리가 깨끗한지 확인하고, 현재 브랜치로 이어서 할 계획서를 정합니다.
3. 단계·검토 표시·항목 형식·문서 구조를 확인하고 `validate-plan.sh <기능 계획서>`를 실행합니다.
4. 최상위 문서의 선행 관계 표에서 선행 항목이 닫혔는지 읽어서 확인합니다.
5. 커밋 규칙을 확인하고 주제 브랜치와 기능 브랜치를 준비합니다.
6. 체크되지 않은 첫 항목부터 버전 대조, 구현, 테스트, 계획서 기록, 코드 커밋을 반복합니다.
7. 전제가 바뀌는 사실을 발견하면 멈추고 `create-plan`으로 넘깁니다.
8. 모든 항목이 끝나면 단계를 `완료`로 바꾸고, 기능 브랜치를 주제 브랜치에 병합한 뒤 멈춥니다.

## 계약

| 정보 | 보내는 쪽 | 받는 쪽 |
| --- | --- | --- |
| 항목 ID가 담긴 커밋 | 계획 실행 | 커밋 학습 |
| 계획 결함 보고 | 계획 실행 | 계획 수립 |
| 현재 버전과 대체된 결정 | 아키텍처 결정 | 계획 실행 |

주 버전이 다르면 구현을 멈추고, 부 버전만 다르면 진행합니다. 기준 버전 기록이 없는 옛 계획서는 대조하지 않고 진행합니다. 따르는 결정은 AD-009, AD-013, AD-015, AD-016, AD-017, AD-018, AD-019입니다.

## 위험과 미해결 질문

- 계획서 갱신은 커밋하지 않고 로컬에만 남기므로, 다른 기기에서 작업을 이어 가면 체크박스와 기록 줄을 볼 수 없습니다.
- 미해결 질문은 없습니다.
