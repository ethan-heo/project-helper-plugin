# 요구사항 정의

## 목적과 문제

무엇을 왜 만드는지 정하지 않은 채 계획에 들어가면, 계획마다 목적과 성공 기준을 다시 묻게 됩니다. 이 영역은 제품이나 프로젝트 단위의 목적·목표·요구사항을 PRD 한 편으로 확정하고, 범위가 크면 요구사항 묶음별 하위 PRD로 나누어 구체화합니다.

## 요구사항과 품질 속성

| 요구사항 | 판정 기준 |
| --- | --- |
| PRD 확정 | 미해결 질문이 없고 `validate-prd.sh`를 통과합니다 |
| 해법 배제 | PRD에 구현 방식과 기술 선택이 적혀 있지 않습니다 |
| 배정 완전성 | 상위 요구사항이 하위 PRD 한 곳에만 배정됩니다 |
| 계층 구체성 | 하위 PRD가 상위와 같은 여덟 절을 모두 갖춥니다 |

## 개념 모델

| 개념 | 뜻 |
| --- | --- |
| PRD | 목적·목표·요구사항을 담은 여덟 절 문서 |
| 카테고리 순회 | 여덟 카테고리를 순서대로 묻는 질문 방식 |
| 묶음 | 사용자 시나리오 기준으로 모은 요구사항 |
| 하위 PRD | 상위 요구사항 묶음 하나를 맡는 PRD |
| 요구사항 ID | `R3`, `R3-1`처럼 상위를 이어받는 식별자 |

## 책임과 경계

`create-prd`는 카테고리 순회 질문으로 PRD 초안을 채우고 확정합니다. 카테고리별 질문 규칙은 이 스킬만 쓰므로 `create-prd/references/`에 남아 있습니다.

`create-sub-prd`는 확정된 PRD만 받아 묶음을 제안하고, 하위 PRD를 만든 뒤 상위 PRD를 목차로 정리합니다. 새 요구사항을 발굴하지 않고, 하위 PRD를 다시 합치는 일도 하지 않습니다.

두 스킬이 함께 쓰는 양식·서술 규칙·검증 스크립트는 `_shared/prd/`에 있습니다. 구현 방식은 계획 수립 영역이, 여러 계획이 따를 구조는 아키텍처 결정 영역이 맡습니다. 보관 경로는 공유 규칙 영역의 판정을 따릅니다.

## 실행 흐름

1. `create-prd`가 요청이 제품·프로젝트 단위인지 확인하고, 기능 하나의 구현 방식이면 `/create-plan`을 안내한 뒤 끝냅니다.
2. `<루트>/prds/`에 양식을 복사해 초안을 만들고, 경로가 `.gitignore`에 없으면 보관 방식을 사용자에게 확인합니다.
3. 여덟 카테고리를 순서대로 묻고, 넘어갈 조건을 만족할 때마다 해당 절을 채웁니다.
4. 검증 스크립트와 점검 목록을 통과하면 확정하고, `architecture/`의 상태에 따라 `/create-architecture`나 `/create-plan`을 안내합니다.
5. 범위가 크면 `create-sub-prd`가 확정된 PRD의 묶음을 사용자와 정하고, 상위 문서를 자기 이름의 디렉터리 안 `README.md`로 옮긴 뒤 그 옆에 하위 PRD를 만듭니다.
6. 상위 요구사항 표에 `하위 PRD` 열을 더하고, `validate-sub-prd.sh`로 배정과 계층을 검사합니다.

## 계약

| 정보 | 보내는 쪽 | 받는 쪽 |
| --- | --- | --- |
| 확정된 PRD | `create-prd` | `create-sub-prd` |
| 요구사항 ID와 충족 판정 | PRD | 계획 수립 |
| 상위 PRD 출처 줄 | 하위 PRD | 상위 PRD와의 연결 |
| 다음 스킬 안내 | 요구사항 정의 | 아키텍처 결정, 계획 수립 |

PRD에는 버전이 없고 `마지막 갱신` 날짜로 고친 시점을 표시합니다. 따르는 결정은 AD-001, AD-002, AD-004, AD-006, AD-009, AD-010입니다.

## 위험과 미해결 질문

- 하위 PRD를 다시 합치는 절차가 없으므로, 분해를 되돌리려면 문서를 직접 옮기고 링크를 고쳐야 합니다.
- 미해결 질문은 없습니다.
