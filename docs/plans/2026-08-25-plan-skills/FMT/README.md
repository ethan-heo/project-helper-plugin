# FMT — 계획서 규격

## 요약

**목표** — 계획서가 어떻게 생겼는지를 정한다. 다섯 섹션의 표기, 문서를 여러 층으로 나누는 방법, 빈 양식이 여기 속한다.

**배경** — 계획서 형식이 세 스킬의 인터페이스다. 형식이 흔들리면 `plan-implement`가 받는 문서와 `plan-create`가 쓰는 문서가 어긋난다. 처음에는 단일 문서 규격만 있었는데, 계획이 커지면서 읽는 사람이 전체를 머리에 올려야 하는 문제가 드러났다.

**변경점** — 기능 문서 둘. 먼저 계획을 나누는 방법을 만들고, 그 다음 각 문서 안의 표기를 훑을 수 있는 형태로 바꾼다.

## 설계

### 같은 규격을 모든 층에 쓴다

문서를 나눌 때 층마다 다른 형식을 만들지 않는다. 다섯 섹션을 그대로 재귀적으로 쓴다.

이렇게 하는 이유는 형식이 둘이 되면 세 스킬이 둘 다 알아야 하기 때문이다. 같은 다섯 섹션을 쓰면 `plan-implement`와 `plan-verify`가 위층 문서도 그대로 읽을 수 있고, 층이 셋으로 늘어났을 때도 스킬 쪽에 새로 가르칠 것이 없었다.

섹션마다 층에 따라 무엇을 담는지가 달라진다. 그 배치 기준은 `FMT-SPLIT`이, 각 섹션 안의 표기는 `FMT-STRUCT`가 정본을 갖는다.

### 두 기능 문서의 관계

`FMT-SPLIT`이 먼저 두 층(상위와 하위)을 만들었고, `FMT-STRUCT`가 ID 체계를 넣으면서 세 층(최상위·도메인·기능)으로 늘렸다. 층이 늘어난 것은 ID를 도메인-기능-번호로 정한 결과다. 세 조각이 각각 폴더·파일·항목과 맞물리므로, 층을 셋으로 두면 항목마다 도메인과 기능을 따로 고를 필요가 없어진다.

그래서 `FMT-SPLIT`의 "나눌지 판단하는 기준"은 그대로 살아 있고, "몇 층으로 나누는가"만 `FMT-STRUCT`가 덮어썼다. 둘 다 읽을 때는 나중 것이 우선이다.

### 나누는 것이 기본은 아니다

기준은 검증 가능성이다. 그 문서 하나만으로 돌려 볼 수 있는 시나리오가 있는가. 없으면 독립된 조각이 아니다. 구현 항목이 열 개 안쪽이거나 검증 지점이 하나뿐이면 단일 문서가 낫다. 분할 자체가 비용이다. 판단 시점과 세부 기준은 `FMT-SPLIT`에 있다.

## 구현 순서

- [ ] **FMT-SPLIT** 계획 분할 — 나눌지 판단하는 시점과 기준, 층 사이의 배치 원칙, 위층을 누가 갱신하는가. 선행: SKILL-CREATE
- [ ] **FMT-STRUCT** 형식 구조화 — 설계·테스트를 표로 바꾸고, 구현 항목에 ID를 붙이고, 층을 셋으로 늘린다. 선행: FMT-SPLIT

## 테스트

### 통합 시나리오

두 문서에 걸친 것만 여기 둔다.

| ID | 입력 상황 | 기대 동작 |
| --- | --- | --- |
| F1 층 일관 | 세 층으로 나뉜 계획서를 만든다 | 세 문서가 모두 같은 다섯 섹션 규격을 만족한다 |
| F2 스킬 무변경 | 층이 둘에서 셋으로 늘어난 계획서를 `/plan-implement`에 준다 | 위층 문서를 읽는 방식이 층 수와 무관하게 같다 |
| F3 기준 우선순위 | 두 문서가 같은 주제를 다르게 적은 자리를 찾는다 | 층 수는 `FMT-STRUCT`, 나눌지 판단은 `FMT-SPLIT`을 따른다 |
