# REL — 패키징과 최종 검증

## 요약

**목표** — 만들어진 것을 플러그인으로 묶고, 실제로 설치해 발동하는지 확인하고, 실제 과제로 한 바퀴 돌려 보정한다.

**배경** — 스킬은 각각 만들어졌지만 함께 동작해 본 적이 없다. 트리거 경계와 인계 지점은 개별 검증으로 확인되지 않는다. 이 계획 자체를 닫는 일도 여기 있다. `plan-verify`가 만들어지기 전에는 문서를 닫을 수단이 없었기 때문이다.

**변경점** — 기능 문서 하나로 끝난다. 패키징, 트리거 측정, 리허설, 소급 검증이 한 흐름이라 나누지 않았다.

## 설계

이 도메인의 경계는 "만든 뒤에 하는 일"이다. 앞의 네 도메인이 각자 안에서만 검증됐으므로, 여기서는 그것들이 함께 놓였을 때 무엇이 어긋나는지를 본다.

`REL`을 마지막에 두는 것은 순서 문제만이 아니다. 이 계획은 자기 자신을 도구로 닫는 구조라, 앞의 도메인을 닫을 수단인 `plan-verify`가 `SKILL`에서 만들어진 뒤에야 소급 검증이 가능해진다. 그래서 최상위 문서의 진행률이 마지막까지 0으로 남아 있다가 `REL`에서 한꺼번에 오른다.

소급 검증에서 머지는 건너뛴다. 브랜치 규칙(`FLOW-BRANCH`)이 생기기 전에 만들어진 것은 전부 기본 브랜치에 있다. 닫는 것은 문서 상태뿐이다.

## 구현 순서

- [ ] **REL-INTEG** 통합과 리허설 — 플러그인 검증, 트리거 측정, 패키징, 마켓플레이스, 리허설, 소급 검증. 선행: REPO-SETUP, SKILL-NAMING, FMT-STRUCT, FLOW-BRANCH

## 테스트

기능 문서가 하나뿐이라 도메인을 가로지르는 검증이 없다. 최상위의 T1~T4와 e2e를 `REL-INTEG`이 실행한다.
