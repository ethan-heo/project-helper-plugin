# 통합과 리허설

## 요약

**목표** — 세 스킬을 플러그인으로 묶고, 어느 스킬이 남의 요청까지 가져가지는 않는지 측정한 뒤, 실제 과제로 한 바퀴 돌려 보정한다.

**배경** — 스킬은 각각 만들어졌지만 함께 동작해 본 적이 없다. 트리거 경계와 인계 지점은 개별 검증으로 확인되지 않는다.

**변경점** — 플러그인을 패키징하고 트리거 평가셋으로 세 description을 확정한다. 실제 요구사항 하나를 접수부터 '완료'까지 통과시킨 뒤 드러난 문제를 반영한다.

## 설계


### 검증 순서

앞의 도메인들은 각자 안에서만 검증됐다. 여기서는 경계와 인계를 본다.

1. 구조 — 플러그인이 로드되고 세 스킬이 노출되는가.
2. 경계 — 각 요청이 알맞은 스킬로 가는가.
3. 인계 — 한 스킬의 산출물을 다음 스킬이 그대로 받는가.
4. 소급 검증 — 앞의 문서를 모두 `plan-verify`로 닫는다.

4번이 필요한 이유는 이 계획이 자기 자신을 도구로 닫는 구조이기 때문이다. `plan-verify`가 만들어지기 전에는 문서를 닫을 수단이 없었다.

소급 검증에서 머지는 건너뛴다. 브랜치 규칙(`FLOW-BRANCH`)이 생기기 전에 만들어진 것은 전부 기본 브랜치에 있다. 닫는 것은 문서 상태뿐이다.

REL-INTEG-003(리허설)과 REL-INTEG-007(소급 검증)는 사용자가 있어야 한다. 리허설은 사용자가 해법을 직접 내는 성질을 확인하는 것이라 혼자 돌리면 아무것도 증명하지 못하고, 소급 검증은 `plan-verify`가 사용자 승인 없이 닫지 못하게 만들어 두었기 때문이다.

### 트리거 측정

발동해야 할 요청과 발동하면 안 되는 근접 요청을 스킬별로 만들어 여러 차례 실행하고 발동률을 본다. 오탐 후보는 어휘가 겹치는 것으로 고른다. 명백히 무관한 질의는 아무것도 테스트하지 않는다.

| 요청 | 가야 할 곳 |
| --- | --- |
| 계획서 없이 "이거 구현해줘" | `plan-create` |
| "계획서대로 진행해줘" | `plan-implement` |
| "테스트 돌려봐" | 어느 스킬도 아님 |
| "다음 스프린트 계획 좀 잡아줘" | 어느 스킬도 아님 |
| 단순 버그 수정, 코드 리뷰 요청 | 어느 스킬도 아님 |
| '구현 완료' 문서로 "이거 확인 좀" | `plan-verify` |

## 구현 순서

- [x] **REL-INTEG-001** 플러그인 검증 — 매니페스트에 세 스킬이 잡히는지, 각 스킬이 자기 폴더 안만 참조하는지 확인한다. 완료 판정: 세 스킬이 모두 노출되고 끊긴 경로가 없다.
  - 기록: 이름을 바꾼 뒤 다시 돌렸다. 매니페스트, frontmatter의 `name`과 디렉터리 일치, 참조 경로, 딸린 파일이 본문에서 언급되는지, 다른 스킬 폴더를 가리키는지까지 봤다. 평가셋의 `expect` 값이 실제 스킬 이름과 맞는지도 함께 확인하도록 검사에 넣었다.
- [x] **REL-INTEG-002** 트리거 평가셋 작성 및 description 확정 — 위 표를 포함해 스킬별 평가 질의를 만들고, 측정 결과로 세 description을 고친다. 완료 판정: 세 스킬이 서로의 요청을 가져가지 않는다.
  - 기록: `expect` 값과 `/implement` 같은 호출 문구를 새 이름으로 고쳤다. description 자체는 이름이 아니라 요청 문구로 발동을 가르므로 손댈 곳이 없었다. 발동률 측정은 플러그인을 설치한 세션에서만 가능해 여기서는 대조까지만 했다.
- [ ] **REL-INTEG-003** 실제 과제 리허설 — 요구사항 하나를 접수부터 '완료'까지 통과시킨다. 완료 판정: 최상위 문서의 e2e 합격 기준을 만족한다.
- [x] **REL-INTEG-004** 패키징 — 플러그인을 `.plugin` 파일로 묶어 사용자에게 전달한다. 완료 판정: 스킬 셋과 매니페스트만 담기고 계획서·평가셋은 빠진다.
  - 기록: 14개 파일 28KB. 이름 변경 뒤 다시 묶었고 `marketplace.json`도 함께 들어갔다. `docs/`와 `evals/`는 저장소의 작업 기록이지 플러그인 내용이 아니라 제외했다.
- [x] **REL-INTEG-005** 로컬 개발용 마켓플레이스 매니페스트 추가 — `.claude-plugin/marketplace.json`을 만들어 로컬 경로를 마켓플레이스로 등록할 수 있게 한다. 완료 판정: 유효한 JSON이고 `name`·`owner`·`plugins`가 있다.
  - 기록: VS Code 확장에는 `--plugin-dir`에 해당하는 설정이 없고 `/plugins`의 Marketplaces 탭이 로컬 경로를 받는다. 그래서 VS Code에서 쓰려면 이 파일이 있어야 한다. 터미널만 쓸 때는 필요 없어서 처음에 뺐던 것을 되돌렸다. 마켓플레이스 이름은 `project-helpers`다. 플러그인 이름 `project-helper`와 한 글자 차이라 헷갈릴 여지는 있지만, 사용자가 정한 이름이고 실제로 둘을 나란히 쓰는 자리는 `project-helper@project-helpers` 하나뿐이다.
- [x] **REL-INTEG-006** 마켓플레이스 구조를 문서 형태로 맞춤 — 플러그인을 `plugins/project-helper/`로 옮기고 저장소 루트는 마켓플레이스만 담게 한다. 완료 판정: `marketplace.json`의 `source`가 실제 플러그인 디렉터리를 가리키고 그 안에 `plugin.json`과 `skills/`가 있다.
  - 기록: VS Code에서 설치까지 했는데 스킬이 안 나왔다. `source`를 `"./"`로 두어 저장소 루트 자체를 플러그인으로 삼았는데, 문서의 예시는 전부 하위 디렉터리를 가리키고 루트를 가리키는 형태는 예시가 없다. 지원 여부를 확인할 수 없어 문서와 같은 구조로 바꿨다. 이제 마켓플레이스와 플러그인이 층이 달라 서로 섞이지 않는다.
- [ ] **REL-INTEG-007** 소급 검증 — 앞의 문서를 모두 `plan-verify`로 닫는다. 선행: `FMT-SPLIT`. 완료 판정: 최상위 문서의 진행률이 5 / 5가 된다.
