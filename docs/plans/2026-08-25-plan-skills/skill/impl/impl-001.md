# plan-implement 스킬

## 요약

**목표** — '계획 확정' 상태의 계획서를 받아 구현 순서를 하나씩 실행하고, 항목마다 커밋하며 상태를 진행시키는 스킬을 만든다.

**배경** — 계획을 세워도 구현이 계획을 벗어나면 문서가 결정의 기록이 아니라 결과의 요약이 된다. 구현할 때의 규칙을 계획 스킬과 분리해 두어야 자세가 섞이지 않는다.

**변경점** — `plugins/project-helper/skills/plan-implement/`에 본문과 참조 문서 하나를 둔다. 계획서 형식은 `plan-create`를 참조하지 않고, 받는 문서가 만족해야 할 전제만 자기 본문에 적는다.

| 항목 | 값 |
| --- | --- |
| 단계 | 구현 완료 |
| 마지막 갱신 | 2026-08-26 |
| 구현 진행률 | 2 / 2 |

## 설계

### 받는 문서의 전제

시작할 때 확인한다. 하나라도 어긋나면 진행하지 않고 어긋난 지점을 사용자에게 알린다.

- 상태 표의 단계가 `계획 확정`이다.
- 미해결 검토 표시(`<!-- 사용자 검토 필요 -->`)가 없다.
- 구현 순서에 `- [ ] **ID** 제목 — 설명` 형태의 항목이 있다.
- 각 항목만 읽고 무엇을 어디에 할지 정해진다.

마지막 조건이 인계 점검의 읽는 쪽 대응이다. 손으로 쓴 계획서나 다른 경로로 들어온 문서는 `plan-create`의 인계 점검을 거치지 않았을 수 있다.

### 진행 절차

1. 전제를 확인한다.
2. 단계를 `구현 중`으로 바꾼다.
3. 체크되지 않은 첫 항목을 구현한다.
4. 그 항목의 단위 테스트를 통과시킨다.
5. 커밋한다. 메시지 형식은 프로젝트 지시사항에서 찾아 따르고, 없으면 사용자에게 확인한다.
6. 체크박스를 채우면서 진행률과 마지막 갱신을 같은 동작으로 고치고, 무엇이 왜 바뀌었는지 기록 한 줄을 붙인다.
7. 남은 항목이 있으면 3번으로. 없으면 단계를 `구현 완료`로 바꾸고 `/plan-verify`를 안내한다.

6번에서 체크와 진행률을 묶는 것이 진행률이 실제와 어긋나는 것을 막는 유일한 장치다. 검사 스크립트를 두지 않기로 했으므로 절차가 그 역할을 한다.

### 계획의 결함을 발견하면 멈춘다

구현 중 전제가 틀렸다는 것이 드러나면 구현 순서를 그 자리에서 고치지 않는다. 진행을 멈추고, 단계를 `계획 확정`으로 되돌리고, 무엇이 어긋났는지 보고한 뒤 `plan-create`로 넘긴다. 계획서를 구현에 맞춰 사후 수정하면 문서가 근거를 잃는다.

검토했으나 기각: 사소한 것은 그 자리에서 고치고 진행하는 방안 — "사소함"의 경계를 스킬이 판단하게 되고, 그 판단이 반복되면 계획서가 조용히 구현을 따라간다.

### 하지 않는 것

- `완료` 표시. `plan-verify`의 몫이다.
- 상위 문서 갱신. 검증되지 않은 것이 상위에서 완료로 보이면 안 된다. 읽기만 한다.

## 구현 순서

- [x] **SKILL-IMPL-001** 구현 규칙 문서 작성 — `plan-implement/references/execution.md`에 전제 확인, 진행 절차, 커밋 메시지 규칙 탐색, 진행률 갱신, 결함 시 복귀 절차를 적는다. 완료 판정: 커밋 규칙이 없는 저장소에서 어떻게 하는지가 적혀 있다.
  - 기록: 계획에 없던 두 가지를 넣었다. 하나는 모호한 항목을 하나씩 만날 때마다 묻지 않고 시작 전에 모아서 짚는 것이고, 다른 하나는 "결함"과 "몰랐던 사실"을 가르는 기준이다. 설계의 전제가 바뀌는지로 갈린다. 이 구분이 없으면 함수 이름이 다른 정도로도 계획으로 되돌아가게 된다.
- [x] **SKILL-IMPL-002** 스킬 본문 작성 — 골격과 본문을 함께 만든다. 완료 판정: 상태가 '계획 확정'이 아닌 문서를 주면 진행하지 않고 알린다.
  - 기록: 본문 77줄. "하지 않는 것"을 따로 절로 뺐다. 완료 표시·상위 갱신·계획서 수정·범위 확장은 모두 진행하다 보면 자연스러워 보이는 행동이라, 절차 안에 섞어 두면 묻힌다. 항목이 끝날 때마다 사용자에게 알리는 것도 절차에 넣었다. 알리지 않으면 사용자가 변경을 따라올 수 없다.

## 테스트

### 단위 검증

- frontmatter가 파싱되고 `name`, `description`이 있다.
- `references/execution.md`가 본문에서 참조되고 끊긴 경로가 없다.
- 본문이 200줄 안팎이고 스킬 폴더 바깥을 참조하지 않는다.

### 통합 시나리오

- **S1 정상 진행** — '계획 확정' 문서를 준다. 항목마다 커밋하고 체크와 진행률을 함께 갱신하는가. 기록 줄을 남기는지, 모두 끝나면 '구현 완료'로 바꾸고 멈추는지 본다.
- **S2 전제 위반** — 단계가 '완료'인 문서, 검토 표시가 남은 문서를 각각 준다. 진행하지 않고 어긋난 지점을 알리는가.
- **S3 모호한 항목** — "인증 처리 개선" 같은 항목이 든 문서를 준다. 구현을 시작하기 전에 그 자리를 짚는가.
- **S4 계획 결함** — 구현 중 전제가 틀린 상황을 만든다. 구현 순서를 임의로 고치지 않고 멈추는가, '계획 확정'으로 되돌리고 보고하는가.
- **S5 규칙 부재** — 커밋 규칙이 없는 저장소에서 실행한다. 임의로 정하지 않고 사용자에게 묻는가.
- **S6 완료 표시 금지** — 모든 항목을 끝낸 뒤에도 '완료'로 바꾸지 않고 `/plan-verify`를 안내하는가.
