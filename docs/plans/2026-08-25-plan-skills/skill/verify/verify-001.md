# plan-verify 스킬

## 요약

**목표** — '구현 완료' 상태의 계획서를 받아 테스트 시나리오와 변경점을 사용자와 확인하고, 승인을 받아 문서를 닫는 스킬을 만든다.

**배경** — 구현한 주체가 합격 판정까지 내리면 검증이 형식만 남는다. 그리고 사용자가 변경점을 이해하지 못한 채 작업이 끝나면 계획서를 쓴 목적이 사라진다.

**변경점** — `plugins/project-helper/skills/plan-verify/`에 본문과 참조 문서 하나를 둔다. 상위 문서가 있는 경우의 갱신 규칙도 여기서 구현한다.

## 설계

### 판정하지 않는다

`plan-verify`는 통과 여부를 스스로 선언하지 않는다. 시나리오 실행 결과와 실제 변경 내역을 증거로 내놓고, 판정은 사용자가 한다. 구현과 검증을 다른 스킬로 나눈 이유가 여기 있으므로, 이 성질이 무너지면 분리가 의미를 잃는다.

### 절차

1. 전제를 확인한다. 단계가 `구현 완료`이고, 모든 구현 항목이 체크돼 있으며, 진행률이 체크 수와 맞는가.
2. 테스트 섹션의 시나리오를 하나씩 실행하고 결과를 보여 준다.
3. 계획서의 변경점과 실제 변경 내역을 대조해 차이를 짚는다.
4. 구현 항목별 기록 줄을 모아 무엇이 왜 바뀌었는지 사용자에게 보여 준다.
5. 사용자가 승인하면 단계를 `완료`로 바꾼다.
6. 상위 문서가 있으면 그 문서에서 이 문서를 가리키는 항목을 체크하고 진행률을 고친다.

4번이 "구현 후 사용자가 변경점을 이해할 수 있어야 한다"는 목적이 실제로 실현되는 자리다. 코드 diff를 그대로 붙이는 것이 아니라, 항목별 기록과 실제 변경을 이어 붙여 읽을 수 있는 형태로 만든다.

### 되돌림

- 시나리오가 실패하거나 항목이 덜 됐으면 단계를 `구현 중`으로 되돌리고 남은 작업을 특정한다.
- 계획 자체가 문제였으면 `계획 확정`으로 되돌리고 `plan-create`로 넘긴다.

### 상위 문서 갱신

하위 문서를 `완료`로 닫는 시점에만 상위를 건드린다. 상위 문서의 구현 항목 하나가 하위 문서 하나를 가리키므로, 파일명으로 대응 항목을 찾는다. 상위의 항목이 모두 닫히면 상위 문서의 단계도 `완료`가 되는데, 이때도 사용자 승인을 받는다.

갱신을 `plan-implement`가 아니라 `plan-verify`가 맡는 이유는 `FMT-SPLIT`의 설계에 있다. 여기서는 그 규칙을 구현한다.

## 구현 순서

- [x] **SKILL-VERIFY-001** 검증 규칙 문서 작성 — `plan-verify/references/verification.md`에 시나리오 실행, 변경 내역 대조, 증거 제시 형태, 되돌림 조건, 상위 문서 갱신을 적는다. 완료 판정: 상위 문서가 있는 경우와 없는 경우가 모두 적혀 있다.
  - 기록: 변경 요약을 만드는 법에 형식 예시를 넣었다. "왜 / 무엇이 / 영향" 세 줄로 쪼개지 않으면 결국 diff 요약이 되어 버린다. 계획서를 쓴 목적이 실현되는 자리라 여기에 분량을 썼다.
- [x] **SKILL-VERIFY-002** 스킬 본문 작성 — 골격과 본문을 함께 만든다. 완료 판정: 사용자 승인 없이는 '완료'로 바꾸지 않는다.
  - 기록: 본문 79줄. "이 스킬이 할 말이 아닌 문장"을 예로 넣었다. 판정하지 말라는 지시만으로는 실제 대화에서 "모두 통과했으니 완료로 바꾸겠습니다"가 자연스럽게 나오기 때문이다.

## 테스트

### 단위 검증

- frontmatter가 파싱되고 `name`, `description`이 있다.
- `references/verification.md`가 본문에서 참조되고 끊긴 경로가 없다.
- 본문이 200줄 안팎이고 스킬 폴더 바깥을 참조하지 않는다.

### 통합 시나리오

- **S1 검증 통과** — '구현 완료' 문서를 준다. 시나리오 결과와 변경 요약을 제시하는가, 사용자 승인 전에 '완료'로 바꾸지 않는가.
- **S2 검증 미달** — 시나리오 하나가 실패하도록 만든다. '구현 중'으로 되돌리는가, 남은 작업을 특정하는가.
- **S3 전제 위반** — 단계가 '구현 중'인 문서, 진행률과 체크 수가 어긋난 문서를 각각 준다. 진행하지 않고 알리는가.
- **S4 상위 갱신** — 상위 문서가 있는 하위 문서를 닫는다. 상위의 해당 항목이 체크되고 진행률이 오르는가, 다른 항목은 건드리지 않는가.
- **S5 상위 없음** — 단일 계획서를 닫는다. 상위를 찾으려다 멈추지 않는가.
- **S6 변경점 설명** — 제시된 변경 요약만 읽고 무엇이 왜 바뀌었는지 알 수 있는가. 코드 diff 나열에 그치지 않는가.
