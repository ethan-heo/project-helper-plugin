# 지시 형식 정리

## 요약

**목표** — 스킬 본문의 지시사항을 훑어서 알아볼 수 있게 만든다. 명령과 판정 기준과 근거를 한 문단에 섞지 않고, 본문과 참조가 같은 것을 두 번 말하지 않게 한다.

**배경** — 세 스킬 본문의 산문 비율이 32~48%다. 명령·분기·근거가 한 문단에 녹아 있어 무엇을 하라는 것인지 찾으려면 문단을 다 읽어야 한다. `plan-implement`는 본문 여덟 절과 `references/execution.md` 열두 절이 주제 단위로 거의 하나씩 짝을 이뤄, 같은 절차를 두 곳에서 설명하고 형식을 고칠 때 두 곳을 따라 고쳐야 한다.

**변경점** — 지시 블록의 모양을 명령·분기·근거 세 층으로 고정해 저장소 규약에 적는다. 본문에는 명령과 분기만 남기고 근거는 참조로 내린다. 참조 파일은 읽을 시점을 절 단위로 밝힌다.

## 설계

### 결정 요약

| 결정 | 택한 것 | 근거 | 기각한 대안 |
| --- | --- | --- | --- |
| 지시 블록의 모양 | 명령 → 분기 표 → 근거 | 훑는 쪽은 굵은 첫 줄만, 판단이 필요하면 표까지, 왜인지 궁금할 때만 산문까지 읽는다 | 전부 표로 — 근거가 한 칸에 눌려 죽는다 / 지금처럼 산문 — 판정 기준이 문장 속에 묻힌다 |
| 근거를 어디에 둘까 | 참조 파일 | 본문은 스킬이 켜질 때마다 통째로 올라간다. 매번 필요하지 않은 근거가 본문에 있으면 정작 명령이 묻힌다 | 본문에 함께 — 지금 상태다. 두 곳이 같은 것을 두 번 말한다 |
| 본문에 근거를 한 줄도 안 남길까 | 그 자리에서 판단이 갈리는 것만 남긴다 | 참조를 읽지 않은 상태에서도 위험한 분기는 알아야 한다 | 전부 내린다 — 참조를 안 열면 근거 없이 실행한다 |
| 세 스킬을 한 번에 고칠까 | 하나씩 | 본문 구조를 바꾸면 트리거 문구와 절차가 함께 흔들린다. 하나 고치고 결과를 본 뒤 다음으로 간다 | 한 커밋에 셋 — 되돌릴 단위가 커진다 |

### 지시 블록의 세 층

각 절은 이 순서를 지킨다.

```
### <절 제목>

**<명령 한 문장>**

| <조건> | <한다> |
| --- | --- |
| ... | ... |

<왜 그렇게 하는지 한 문단. 없으면 생략한다.>
```

명령은 한 문장이고 굵게 쓴다. 두 문장이 필요하면 절을 나눌 때다. 분기가 둘 이상이면 표로 쓰고 하나뿐이면 명령 문장 안에 넣는다. 근거는 맨 뒤에 두고, 참조 파일에 같은 내용이 있으면 본문에서 지운다.

### 본문과 참조의 역할

| | 본문(`SKILL.md`) | 참조(`references/`) |
| --- | --- | --- |
| 담는 것 | 명령, 분기, 그 자리에서 갈리는 판단 | 근거, 예외, 실패 처리, 형식 예시 |
| 읽는 시점 | 스킬이 켜질 때 통째로 | 절 단위로, 필요한 시점에 |
| 분량 기준 | 절마다 여섯 줄 안쪽 | 제한 없음 |

참조 파일 표에는 "시작할 때 한 번" 대신 어느 절을 언제 읽는지 적는다. 지금처럼 뭉뚱그려 두면 전부 읽거나 아무것도 안 읽거나 둘 중 하나가 된다.

### 예외 상황

| 상황 | 처리 |
| --- | --- |
| 근거가 한 줄이고 참조로 옮길 만큼이 아니다 | 본문에 그대로 둔다. 참조 파일이 한 줄짜리 절로 늘어나는 쪽이 더 나쁘다 |
| 분기가 하나뿐이다 | 표를 만들지 않고 명령 문장에 넣는다 |
| 절 제목만으로 명령이 분명하다 | 그래도 굵은 줄을 생략하지 않는다. 제목은 훑을 때 건너뛰는 자리다 |
| 명령이 없는 절 | "왜 이 스킬이 있는가"처럼 자세를 설명하는 절은 이 규칙 밖이다 |

## 구현 순서

- [x] **SKILL-SHAPE-001** 규약에 지시 형식 추가 — `CLAUDE.md`의 스킬 파일 규약에 세 층 구조와 본문·참조 역할 분담을 적는다. 완료 판정: 새 스킬을 쓸 때 이 규약만 보고 절 하나의 모양을 정할 수 있다.
  - 기록: 규약을 스킬 안이 아니라 `CLAUDE.md`에 뒀다. 이 저장소가 스킬을 만드는 저장소라 스킬 본문의 모양은 저장소 규약이고, 스킬 안에 두면 스킬마다 자기 형식을 따로 갖게 된다. 계획서에 있던 예외 표는 옮기지 않았다. 규약에는 지킬 것만 두고, 왜 그렇게 정했는지와 예외 판단은 이 계획서가 갖는다.
- [x] **SKILL-SHAPE-002** `plan-implement` 적용 — 본문 여덟 절을 세 층으로 다시 쓰고 `execution.md`와 겹치는 근거를 내린다. 선행: SKILL-SHAPE-001. 완료 판정: 본문 산문 비율이 30% 아래로 내려가고, 같은 주제를 본문과 참조가 두 번 설명하지 않는다.
  - 기록: 산문 46%에서 29%로, 표는 3줄에서 43줄로 바뀌었다. 산문에 녹아 있던 분기가 표로 올라온 결과다. 참조에서 두 절을 없앴다. "끝냈을 때"는 본문 8번이 그대로 담고 있었고, "상위 문서가 있는 경우"는 선행 확인과 같은 이야기라 그쪽으로 합쳤다. "항목 하나를 끝내는 절차"는 절차가 본문으로 올라가면서 남은 것이 근거뿐이라 제목을 "한 커밋에 담는 이유"로 바꿨다. 본문 줄 수는 84줄로 늘었는데, 산문을 표로 펴면 줄은 늘고 읽는 양은 준다.
- [x] **SKILL-SHAPE-003** `plan-verify` 적용 — `verification.md`와 함께 같은 작업을 한다. 선행: SKILL-SHAPE-002. 완료 판정: 위와 같다.
  - 기록: 산문 48%에서 28%로 내려갔다. 처음 다시 썼을 때는 33%에서 멈췄는데, 절차 절만 따로 재 보니 39%로 오히려 `plan-implement`보다 높았다. 분기가 하나뿐인 절이 다섯이라 표 없이 명령과 산문만 남은 탓이었다. 그 다섯 절의 산문을 보니 참조에 그대로 있는 문장이 섞여 있었다. 두 번 말하지 않는다는 기준으로 다시 훑어 걷어내니 29%가 됐다. 비율을 재는 것이 중복을 찾는 데 쓸모가 있었다. 참조에서는 "판정하지 않는다"와 "되돌림" 두 절을 없앴다. 앞은 본문의 자세 설명과 같은 이야기였고, 뒤는 본문 표가 그대로 담고 있었다.
- [x] **SKILL-SHAPE-004** `plan-create` 적용 — 참조가 셋이라 읽을 시점을 절 단위로 나눈다. 선행: SKILL-SHAPE-003. 완료 판정: 세 스킬의 참조 파일 표가 어느 절을 언제 읽는지 가리킨다.
  - 기록: 산문 32%에서 25%로 내려갔다. 참조 표는 파일 셋의 절을 절차 번호에 붙여 열 줄이 됐다. `facilitation.md`만 예외로 세 절을 시작할 때 한꺼번에 읽게 뒀다. 대화 내내 쓰는 자세라 필요한 시점을 따로 짚을 수 없다. 옮기다가 `facilitation.md`의 "왜 사용자가 답을 내야 하는가"가 본문 첫 절과 거의 같은 문장인 것을 찾아 참조에서 뺐다. 이 자세는 스킬이 켜질 때마다 컨텍스트에 있어야 하는 것이라 본문 쪽을 남겼다.
