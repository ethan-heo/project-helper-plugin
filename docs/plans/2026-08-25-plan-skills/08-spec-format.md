# 슬라이스 8: 계획서 형식 구조화

## 요약

**목표** — 계획서에서 훑을 수 있는 부분을 표로 바꿔, 산문을 다 읽지 않고도 무엇이 정해졌는지 알 수 있게 한다.

**배경** — 지금 계획서는 설계와 테스트가 통째로 산문이다. 결정이 무엇이었는지 알려면 문단을 다 읽어야 하고, 시나리오는 한 줄에 입력·기대·시점이 다 들어가 있어 눈으로 훑기 어렵다. 기능명세서 작성 지침에서 쓸 만한 원칙 셋을 가져온다.

**변경점** — 설계 앞에 결정 요약 표를 두고, 예외 상황을 최소 세 개 적게 하고, 테스트 시나리오를 표로 바꾼다. 구현 항목에는 도메인-기능-번호 형태의 ID를 붙인다.

## 설계

### 결정 요약

| 결정 | 택한 것 | 근거 | 기각한 대안 |
| --- | --- | --- | --- |
| 명세서 형식을 얼마나 가져올까 | 원칙 셋만 | 계획서는 "왜 그렇게 정했는가"를 담는 문서다. 10개 필드를 통째로 옮기면 명세서가 된다 | 10개 필드 전부 — 근거와 기각 대안이 들어갈 자리가 사라진다 |
| 설계를 표로 바꿀까 | 표 + 산문 | 훑을 사람은 표만 보고, 파고들 사람은 아래 산문을 읽는다 | 설계 전체를 표로 — 근거가 한 칸에 눌려 죽는다 |
| 구현 항목을 표로 바꿀까 | 바꾸지 않는다 | 체크박스가 진행 상태를 나르고 세 스킬이 그 표기에 물려 있다 | 체크 열이 있는 표 — 이득보다 파급이 크다 |
| 항목 ID 체계 | 도메인-기능-번호 | 커밋 메시지와 검증 기록에서 항목을 가리킬 수 있다 | 일련번호만 — 슬라이스를 넘나들면 무엇을 가리키는지 모른다 |
| 번호 형식을 남길까 | 남기지 않는다 | 형식이 둘이면 문서마다 어느 쪽인지 판별해야 한다 | 상위는 번호, 슬라이스는 ID — 처음 정했다가 뒤집었다. 한 계획 안에서 두 형식을 쓰는 셈이었다 |
| 기존 계획서에 소급 적용할까 | 하지 않는다 | 이미 닫힌 판단의 기록이다. 형식만 바꾸려고 손대면 이력이 흐려진다 | 전부 새 형식으로 — 파급이 크고 얻는 게 없다 |

### 상위 문서도 ID를 쓴다

처음에는 상위를 번호로 두려 했다. 슬라이스 목록에는 도메인이랄 것이 없고 파일 이름이 이미 식별자 노릇을 한다고 봤다. 뒤집었다. 한 계획 안에서 상위와 하위가 다른 형식을 쓰면, 읽는 쪽이 문서마다 어느 형식인지 먼저 판별해야 한다.

상위의 ID는 그 슬라이스가 다루는 영역에서 딴다. `REPO-SETUP-001`, `SKILL-CREATE-002` 같은 식이다.

**대신 상위 문서에 ID 용어 표를 둔다.** 도메인 코드는 계획마다 다르게 정해지므로, 무엇이 무엇을 뜻하는지 한 곳에 모아 두지 않으면 `FMT`가 형식인지 포맷터인지 알 수 없다.

### 예외를 몇 개 적게 할 것인가

원문 지침은 최소 3~5개다. 그대로 쓰되 강제하지는 않는다. 코드 변경이 아닌 계획은 예외랄 것이 없을 수 있다. 그때는 "해당 없음"과 그 이유를 적는다. 빈칸으로 두면 생각하지 않은 것인지 없는 것인지 구분되지 않는다.

### 예외 상황

| 상황 | 처리 |
| --- | --- |
| 결정이 한둘뿐인 작은 계획 | 결정 요약 표를 생략하고 산문만 쓴다. 두 줄짜리 표는 번잡하다 |
| 시나리오가 한둘뿐인 계획 | 표 대신 목록을 쓴다. 같은 이유다 |
| 도메인이 불분명한 항목 | 대상 파일이 속한 디렉터리에서 딴다. 그것도 애매하면 계획서 주제를 도메인으로 쓴다 |
| 기존 계획서를 이어서 작업할 때 | 그 문서의 기존 형식을 따른다. 한 문서 안에서 형식이 섞이지 않게 한다 |

## 구현 순서

- [x] **FMT-SPEC-001** 규격에 새 형식 반영 — `plan-format.md`에 결정 요약 표, 예외 표, 시나리오 표, 항목 ID 표기를 적는다. 완료 판정: 네 가지가 모두 예시와 함께 있고 생략 조건이 명시돼 있다.
  - 기록: 표마다 "이럴 땐 만들지 마라"를 붙였다. 형식을 주면 무조건 채우려 드는데, 두 줄짜리 표는 산문보다 읽기 나쁘다. 예외 세 개를 뽑는 요령(잘못된 입력·전제가 깨진 상태·바깥의 실패)도 함께 적었다. 숫자만 주면 억지로 채우게 된다.
- [x] **FMT-SECT-002** 작성 기준과 통과 조건 갱신 — `sections.md`의 설계·테스트 절에 새 형식을 반영한다. 완료 판정: 설계 통과 조건이 "예외가 적혀 있거나 해당 없음이 밝혀져 있다"를 포함한다.
  - 기록: 설계 절의 "담을 것"을 표 뒤 산문 몫으로 다시 나눴다. 표와 산문이 같은 것을 두 번 말하면 표를 만든 뜻이 없다. 근거는 표에 한 줄, 한 줄로 안 되는 것만 아래 산문으로 간다.
- [x] **FMT-TMPL-003** 빈 양식 갱신 — `plan-template.md`를 새 형식으로 바꾼다. 완료 판정: 양식만 복사해도 표 뼈대가 들어 있다.
  - 기록: 표 아래마다 "이럴 땐 지워라"를 꺾쇠 안에 넣었다. 빈 양식은 채우라는 신호로 읽히므로, 지워도 된다는 말을 양식 안에 두지 않으면 두 줄짜리 표가 그대로 남는다.
- [x] **SKL-PREM-004** 두 스킬의 전제 갱신 — `plan-implement`는 항목 ID 표기를, `plan-verify`는 시나리오 표를 읽도록 고친다. 완료 판정: 옛 표기와 새 표기를 모두 받아들이고 어느 쪽인지 판별해 진행한다.
  - 기록: 계획에 없던 것을 하나 넣었다. ID 형식이면 커밋 메시지에 그 ID를 넣게 했다. ID를 만든 이유가 "문서 밖에서 항목을 가리키기 위해"인데 커밋에 안 넣으면 그 자리가 없어진다. 프로젝트 커밋 규칙과 부딪히면 규칙을 따르고 ID는 본문에 넣는다.

- [ ] **FMT-ONLY-005** 번호 형식 폐기 — 규격에서 번호 형식을 옛 형식으로 낮추고, 상위 문서의 구현 항목과 선행 표기도 ID를 쓰게 한다. 완료 판정: 규격이 ID 하나만 정식으로 다루고, 번호 형식은 옛 문서를 만났을 때의 처리로만 남는다.
- [ ] **FMT-GLOSS-006** ID 용어 표 — 상위 문서에 도메인 코드 사전을 두도록 규격에 넣고, 이 계획의 상위 문서에 실제로 만든다. 완료 판정: 상위 문서만 읽고도 각 도메인 코드가 무엇을 가리키는지 알 수 있다.
