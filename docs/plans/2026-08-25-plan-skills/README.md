# 계획서 작성 스킬 구축 계획

## 요약

**목표** — 기술적 문제를 사용자가 직접 풀어내도록 돕고, 그 과정과 결론을 계획서로 남기는 스킬을 만든다. AI는 해법을 대신 내놓지 않고, 경험 많은 엔지니어 검토자로서 질문·반박·기록을 맡는다. 계획이 확정된 뒤에는 같은 문서가 구현과 검증의 기준이 된다.

**배경** — 요구사항을 던지면 AI가 곧바로 해법과 코드를 내놓는 방식은 빠르지만, 사용자에게 판단의 흔적이 남지 않는다. 왜 그 구조를 택했는지 모른 채 변경이 쌓이고, 구현 후 검증도 "돌아가니까 됐다" 수준에 머문다.

**변경점** — `project-helper-plugin` 저장소에 플러그인 골격을 만들고 스킬 세 개를 추가한다.

| 이름 | 역할 | 다루는 상태 |
| --- | --- | --- |
| `create-plan` | 사용자와 함께 계획서를 작성하고, 필요하면 슬라이스로 나눈다 | → 계획 확정 |
| `implement` | 계획서의 구현 순서를 하나씩 실행한다 | 계획 확정 → 구현 중 → 구현 완료 |
| `verify` | 테스트 시나리오와 변경점을 사용자와 확인하고 슬라이스를 닫는다 | 구현 완료 → 완료 |

세 스킬은 서로의 파일을 참조하지 않는다. 계획서 한 편을 주고받되, 형식의 정본은 문서를 쓰는 `create-plan`이 갖고 나머지 둘은 자기가 읽고 고치는 부분만 전제로 선언한다.

## 상태

| 항목 | 값 |
| --- | --- |
| 단계 | 구현 중 |
| 마지막 갱신 | 2026-08-25 |
| 구현 진행률 | 0 / 6 ("구현 순서" 참고) |

슬라이스 01과 02는 구현이 끝났지만 아직 검증되지 않았다. 슬라이스를 닫는 도구가 `verify`이고 그 `verify`를 이 계획으로 만들고 있기 때문이다. 05까지 만든 뒤 01~04를 소급 검증한다.

## 설계

### 1. 왜 스킬을 셋으로 나누는가

한 스킬로 묶으면 정반대의 자세를 한 지시서에 담게 된다. 계획 단계에서 AI는 뒤로 물러서서 질문만 하고, 구현 단계에서는 앞에 나서서 코드를 쓴다. 같은 문서 안에서 두 태도를 전환하라고 지시하면 어느 쪽도 선명해지지 않는다.

나누면 세 가지를 얻는다.

- **상태 전환이 구조로 보장된다.** '계획 확정 → 구현 중'이 "사용자가 지시하면"이라는 문장이 아니라 `/implement` 호출이라는 행위로 고정된다. '완료' 표시는 `/verify`를 거치지 않으면 일어날 수 없다.
- **AI가 자기 일을 자기가 합격시키지 않는다.** 구현한 주체와 검증을 진행하는 주체를 분리한다. `verify`는 판정하지 않고 증거를 내놓는 쪽이며, 판정은 사용자가 한다.
- **컨텍스트가 필요한 만큼만 로드된다.** 계획을 쓰는 동안 커밋 규칙이 컨텍스트에 있을 이유가 없다.

### 2. 스킬은 자기 폴더 안만 참조한다

계획서 형식이 세 스킬의 인터페이스가 되므로 공용 규격 파일을 하나 두는 방법도 있다. 쓰지 않는다.

세 스킬이 필요로 하는 부분이 애초에 다르다. `create-plan`은 문서를 쓰므로 표기 전부가 필요하고, `implement`는 단계와 진행률과 체크박스만, `verify`는 단계와 체크 수와 테스트 섹션만 본다. 공용 규격은 각자에게 필요 없는 부분까지 매번 읽히게 만든다. 또 스킬이 자기 폴더 바깥을 참조하면 하나만 떼어 갔을 때 깨진다.

그래서 형식의 정본은 `create-plan/references/plan-format.md`가 갖고, `implement`와 `verify`는 받는 문서가 만족해야 할 전제와 자기가 고치는 자리만 자기 본문에 적는다. **제어는 참조가 아니라 제약으로 한다.** 전제를 만족하지 않는 문서는 받지 않는다.

형식을 바꿀 때 세 군데를 봐야 하는 것이 이 선택의 비용이다. 잊지 않도록 규격 문서 앞머리에 그 사실을 적어 둔다.

### 3. 계획서 규격

다섯 섹션(`## 요약`, `## 상태`, `## 설계`, `## 구현 순서`, `## 테스트`)을 이 문자열, 이 순서로 둔다. 상태 표는 단계·마지막 갱신·구현 진행률 세 행이고, 단계 값은 `계획 확정`, `구현 중`, `구현 완료`, `완료` 중 하나다.

형식의 정본은 `skills/create-plan/references/plan-format.md`다. 표기 세부와, 검사 스크립트를 두지 않기로 한 근거는 슬라이스 2에 있다.

### 4. 계획을 슬라이스로 나눈다

이 계획을 여섯 슬라이스로 나눴다. 같은 다섯 섹션 규격을 상위와 슬라이스 두 층위에 그대로 쓴다. 상위의 구현 항목 하나가 슬라이스 문서 하나이고, 진행률은 검증까지 끝난 슬라이스 수다. 상위 문서는 `verify`가 슬라이스를 닫는 시점에만 갱신한다.

나누는 시점과 기준, 두 층위의 역할 분담, 상위 갱신을 `verify`가 맡는 이유는 슬라이스 3이 정본이다.

### 5. 상태 전환

| 전환 | 주체 | 조건 |
| --- | --- | --- |
| → 계획 확정 | 사용자 | 다섯 섹션 통과, 미해결 검토 표시 없음 |
| 계획 확정 → 구현 중 | `implement` | `/implement` 호출 |
| 구현 중 진행 | `implement` | 항목 완료 → 테스트 → 커밋 → 체크와 진행률 갱신 |
| 구현 중 → 계획 확정 | `implement` | 계획의 결함 발견 |
| 구현 중 → 구현 완료 | `implement` | 모든 항목 체크 |
| 구현 완료 → 구현 중 | `verify` | 검증 미달 |
| 구현 완료 → 완료 | `verify` | 사용자 승인. 상위 문서가 있으면 함께 갱신 |

### 6. 이해 가능성

배경을 모르는 독자가 읽는다고 가정한다. 내부 약어와 코드명은 첫 등장에서 한 번 풀어쓴다. 설계에는 결론만이 아니라 근거와 기각한 대안을 함께 남긴다. 구현 중에는 각 항목을 끝낼 때 무엇이 왜 바뀌었는지 한두 줄을 남기고, 이 기록이 `verify` 단계에서 사용자에게 제시된다.

### 7. 스킬 사이의 경계

계획서의 유무와 상태를 유일한 판별 기준으로 삼는다. 각 스킬은 시작할 때 상태를 확인하고, 자기 차례가 아니면 알맞은 스킬을 안내한다.

트리거 문구 초안과 오탐 후보, 측정 방법은 슬라이스 6이 정본이다.

### 8. 예상 실패 모드

- **AI가 대신 설계를 끝내 버린다.** 가장 큰 위험이다. 금지 문구를 나열하는 대신 SKILL.md 본문 앞머리에 "왜 사용자가 직접 답을 내야 하는가"를 먼저 설명한다.
- **세 스킬의 경계가 흐려진다.** 계획서 유무와 상태를 유일한 판별 기준으로 삼고, 각 스킬이 시작할 때 상태를 확인해 맞지 않으면 알맞은 스킬을 안내한다.
- **진행률이 실제와 어긋난다.** 체크와 진행률 갱신을 한 단계로 묶고, `verify`가 시작할 때 다시 대조한다.
- **과분할.** 슬라이스가 잘면 문서 관리 비용이 내용보다 커진다. 검증 가능성을 기준으로 삼아 억제한다.

## 테스트

### 통합 시나리오

슬라이스를 넘나드는 것만 여기 둔다. 슬라이스 안에서 끝나는 검증은 각 문서에 있다.

- **T1 인계** — `create-plan`이 확정한 문서를 `/implement`가 그대로 받아 진행하는가. 문서만 보고 무엇을 어디에 할지 정해지는가.
- **T2 복귀** — `implement`가 계획의 결함을 발견해 '계획 확정'으로 되돌린 문서를 `create-plan`이 이어받아 고치는가. 요약부터 다시 쓰지 않는가.
- **T3 슬라이스 닫기** — `verify`가 슬라이스 문서를 '완료'로 바꾸면서 상위 문서의 체크와 진행률을 함께 고치는가.
- **T4 경계** — 계획서 없이 "구현해줘", '계획 확정' 문서로 "검증해줘" 같은 요청에서 각 스킬이 자기 차례가 아님을 알아채고 알맞은 스킬을 안내하는가.

### e2e

실제 저장소의 요구사항 하나를 접수부터 '완료' 표시까지 통과시킨다. 합격 기준은 문서가 만들어졌는지가 아니라, 작업에 참여하지 않은 사람이 계획서만 읽고 무엇이 왜 바뀌었는지 설명할 수 있는지다. 슬라이스 6에서 한다.

### 회귀

스킬을 수정할 때마다 각 슬라이스의 대표 시나리오와 T1을 다시 돌린다.
