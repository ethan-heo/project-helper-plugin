# 계획서 작성 스킬 구축 계획

## 요약

**목표** — 기술적 문제를 사용자가 직접 풀어내도록 돕고, 그 과정과 결론을 계획서로 남기는 스킬을 만든다. AI는 해법을 대신 내놓지 않고, 경험 많은 엔지니어 검토자로서 질문·반박·기록을 맡는다. 계획이 확정된 뒤에는 같은 문서가 구현과 검증의 기준이 된다.

**배경** — 요구사항을 던지면 AI가 곧바로 해법과 코드를 내놓는 방식은 빠르지만, 사용자에게 판단의 흔적이 남지 않는다. 왜 그 구조를 택했는지 모른 채 변경이 쌓이고, 구현 후 검증도 "돌아가니까 됐다" 수준에 머문다.

**변경점** — `project-helper-plugin` 저장소에 플러그인 골격을 만들고 스킬 세 개를 추가한다.

| 이름 | 역할 | 다루는 상태 |
| --- | --- | --- |
| `plan-create` | 사용자와 함께 계획서를 작성하고, 필요하면 여러 문서로 나눈다 | → 계획 확정 |
| `plan-implement` | 계획서의 구현 순서를 하나씩 실행한다 | 계획 확정 → 구현 중 → 구현 완료 |
| `plan-verify` | 테스트 시나리오와 변경점을 사용자와 확인하고 문서를 닫는다 | 구현 완료 → 완료 |

작업은 브랜치로 격리한다. 계획 묶음마다 하나, 나뉜 문서마다 하나를 쓰고, 사용자 검증을 통과한 것만 상위 브랜치에 머지된다. 이름 규칙과 근거는 `FLOW-BRANCH`가 정본이다.

## 상태

| 항목 | 값 |
| --- | --- |
| 단계 | 구현 중 |
| 마지막 갱신 | 2026-08-26 |
| 구현 진행률 | 0 / 5 ("구현 순서" 참고) |

구현이 끝난 기능 문서가 여럿이지만 아직 닫힌 도메인은 없다. 문서를 닫는 도구가 `plan-verify`인데 그 `plan-verify`를 이 계획으로 만들고 있기 때문이다. `REL` 도메인까지 끝낸 뒤 앞의 것들을 소급 검증한다.

## 설계

### ID 용어

구현 항목의 ID는 도메인-기능-번호로 쓰고, 세 조각이 문서 계층과 그대로 맞물린다. 도메인은 폴더, 기능은 파일, 번호는 그 파일 안의 항목이다.

| 층 | 문서 | 항목이 가리키는 것 | 항목의 ID |
| --- | --- | --- | --- |
| 최상위 | `README.md` | 도메인 하나 | `SKILL` |
| 도메인 | `SKILL/README.md` | 기능 문서 하나 | `SKILL-CREATE` |
| 기능 | `SKILL/SKILL-CREATE.md` | 실제 구현 항목 | `SKILL-CREATE-001` |

도메인 코드의 뜻은 여기서만 관리한다. 아래층 문서에는 표를 두지 않는다. 새 도메인을 만들면 이 표에 한 줄을 더한다.

| 도메인 | 뜻 |
| --- | --- |
| `REPO` | 저장소와 플러그인 구조 |
| `SKILL` | 스킬 본문과 참조 문서 |
| `FMT` | 계획서 규격, 작성 기준, 빈 양식 |
| `FLOW` | 스킬 사이의 흐름 — 브랜치, 선행, 상태 전환 |
| `REL` | 패키징, 배포, 최종 검증 |

번호는 기능 문서 안에서 1부터 센다. 번호가 순서를 뜻하지는 않는다. 중간에 항목이 끼어들어도 뒤가 밀리지 않아야 커밋에 적힌 ID가 계속 같은 항목을 가리킨다.

### 계획서 규격

다섯 섹션(`## 요약`, `## 상태`, `## 설계`, `## 구현 순서`, `## 테스트`)을 이 문자열, 이 순서로 둔다. 세 층 모두 같은 규격을 쓴다. 상태 표는 단계·마지막 갱신·구현 진행률 세 행이고, 단계 값은 `계획 확정`, `구현 중`, `구현 완료`, `완료` 중 하나다.

형식의 정본은 `plugins/project-helper/skills/plan-create/references/plan-format.md`다. 표기 세부는 `FMT` 도메인이 다룬다.

### 상태 전환

| 전환 | 주체 | 조건 |
| --- | --- | --- |
| → 계획 확정 | 사용자 | 다섯 섹션 통과, 미해결 검토 표시 없음 |
| 계획 확정 → 구현 중 | `plan-implement` | `/plan-implement` 호출 |
| 구현 중 진행 | `plan-implement` | 항목 완료 → 테스트 → 커밋 → 체크와 진행률 갱신 |
| 구현 중 → 계획 확정 | `plan-implement` | 계획의 결함 발견 |
| 구현 중 → 구현 완료 | `plan-implement` | 모든 항목 체크 |
| 구현 완료 → 구현 중 | `plan-verify` | 검증 미달 |
| 구현 완료 → 완료 | `plan-verify` | 사용자 승인. 위층 문서가 있으면 한 층 올려 갱신 |

### 이해 가능성

배경을 모르는 독자가 읽는다고 가정한다. 내부 약어와 코드명은 첫 등장에서 한 번 풀어쓴다. 설계에는 결론만이 아니라 근거와 기각한 대안을 함께 남긴다. 구현 중에는 각 항목을 끝낼 때 무엇이 왜 바뀌었는지 한두 줄을 남기고, 이 기록을 나중에 `plan-verify`가 사용자에게 보여 준다.

### 예상 실패 모드

- **AI가 대신 설계를 끝내 버린다.** 가장 큰 위험이다. 금지 문구를 나열하는 대신 SKILL.md 본문 앞머리에 "왜 사용자가 직접 답을 내야 하는가"를 먼저 설명한다.
- **세 스킬의 경계가 흐려진다.** 계획서 유무와 상태를 유일한 판별 기준으로 삼고, 각 스킬이 시작할 때 상태를 확인해 맞지 않으면 알맞은 스킬을 안내한다.
- **진행률이 실제와 어긋난다.** 체크와 진행률 갱신을 한 동작으로 묶고, `plan-verify`가 시작할 때 다시 대조한다.
- **과분할.** 문서가 잘면 관리 비용이 내용보다 커진다. 검증 가능성을 기준으로 삼아 막는다.

## 구현 순서

- [ ] **REPO** 저장소와 플러그인 구조 — 스킬을 담을 그릇과 저장소 규약.
- [ ] **SKILL** 스킬 본문과 참조 문서 — 세 스킬의 본체와 이름. 선행: REPO
- [ ] **FMT** 계획서 규격 — 형식, 작성 기준, 빈 양식, 문서를 층으로 나누는 방법. 선행: REPO
- [ ] **FLOW** 스킬 사이의 흐름 — 브랜치, 선행 확인, 커밋 단위. 선행: SKILL
- [ ] **REL** 패키징과 최종 검증 — 플러그인으로 묶고 실제 과제로 한 바퀴 돌린다. 선행: REPO, SKILL, FMT, FLOW

`SKILL`과 `FMT`는 서로를 선행으로 적지 않았다. 실제로 번갈아 진행됐기 때문이다. 규격을 만들어 스킬에 반영하고, 스킬을 쓰다 규격의 구멍을 찾아 다시 규격으로 돌아가는 식이었다. 두 도메인 사이의 실제 순서는 기능 문서 단위로 갈리므로 각 도메인 문서의 선행 표기를 본다.

## 테스트

### 통합 시나리오

도메인을 넘나드는 것만 여기 둔다. 도메인 안에서 끝나는 검증은 각 도메인 문서에 있다.

| ID | 입력 상황 | 기대 동작 |
| --- | --- | --- |
| T1 인계 | `plan-create`가 확정한 문서를 `/plan-implement`에 준다 | 문서만 보고 무엇을 어디에 할지 정해진다. 되묻지 않고 진행한다 |
| T2 복귀 | `plan-implement`가 '계획 확정'으로 되돌린 문서를 `/plan-create`에 준다 | 요약부터 다시 쓰지 않고 어긋난 자리만 고친다 |
| T3 층 올리기 | 기능 문서 하나를 `/plan-verify`로 닫는다 | 도메인 문서의 체크와 진행률이 함께 오른다. 그 도메인이 다 닫히면 최상위까지 올라간다 |
| T4 경계 | 계획서 없이 "구현해줘", '계획 확정' 문서로 "검증해줘"를 준다 | 각 스킬이 자기 차례가 아님을 알아채고 알맞은 스킬을 안내한다 |

### e2e

실제 저장소의 요구사항 하나를 접수부터 '완료' 표시까지 통과시킨다. 합격 기준은 문서가 만들어졌는지가 아니라, 작업에 참여하지 않은 사람이 계획서만 읽고 무엇이 왜 바뀌었는지 설명할 수 있는지다. `REL-INTEG`에서 한다.

### 회귀

스킬을 수정할 때마다 각 도메인의 대표 시나리오와 T1을 다시 돌린다.
