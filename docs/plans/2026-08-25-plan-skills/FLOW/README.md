# FLOW — 스킬 사이의 흐름

## 요약

**목표** — 세 스킬이 이어질 때 무엇이 어디에 쌓이고 누가 먼저인지를 정한다. 브랜치, 선행 확인, 커밋 단위가 여기 속한다.

**배경** — 스킬 각각이 무엇을 하는지는 `SKILL`에서 정했지만, 스킬 사이의 자리는 비어 있었다. 모든 작업이 한 브랜치에 쌓이고, 선행 관계는 문서에 문장으로만 적혀 있어 아무도 확인하지 않았다. 다른 계획을 하다 돌아왔을 때 어디를 이어서 해야 하는지 판단할 근거도 없었다.

**변경점** — 기능 문서 하나로 끝난다. 브랜치 규칙과 선행 표기를 규격에 넣고, 두 스킬이 그 규칙을 실제로 따르게 하는 일이다.

## 설계

이 도메인의 경계는 "한 스킬 안에서 끝나지 않는 것"이다. `plan-implement`가 항목을 어떻게 구현하는가는 `SKILL`이고, 그 결과물이 어느 브랜치에 쌓여 누구에게 넘어가는가는 여기다. 계획서에 선행을 어떤 문자열로 적는가는 `FMT`가 규격을 갖고, 그 문자열을 읽어 진행 여부를 가르는 절차는 여기가 갖는다.

이렇게 나눈 이유는 브랜치 규칙이 두 스킬에 동시에 걸리기 때문이다. 브랜치를 만드는 쪽은 `plan-implement`, 머지하는 쪽은 `plan-verify`인데 규칙이 하나라도 어긋나면 둘 다 깨진다. 한쪽 스킬 문서에 규칙을 두면 다른 쪽이 그것을 모른 채 고칠 수 있다. 규칙과 근거는 `FLOW-BRANCH`가 정본이다.

## 구현 순서

- [ ] **FLOW-BRANCH** 브랜치 전략과 선행 확인 — 브랜치 규칙, 선행 표기와 확인 절차, 커밋 원자성, 재개 절차. 선행: SKILL-IMPL, SKILL-VERIFY

## 테스트

기능 문서가 하나뿐이라 도메인을 가로지르는 검증이 없다. 검증 항목은 `FLOW-BRANCH`에 있다.
