# 슬라이스 7: 통합과 리허설

## 요약

**목표** — 세 스킬을 플러그인으로 묶고, 서로를 잠식하지 않는지 측정하고, 실제 과제로 한 바퀴 돌려 보정한다.

**배경** — 스킬은 각각 만들어졌지만 함께 동작해 본 적이 없다. 트리거 경계와 인계 지점은 개별 검증으로 확인되지 않는다.

**변경점** — 플러그인을 패키징하고, 트리거 평가셋으로 세 description을 확정하고, 실제 요구사항 하나를 접수부터 '완료'까지 통과시킨 뒤 드러난 문제를 반영한다.

## 설계

### 검증 순서

앞 슬라이스들은 각자 안에서만 검증됐다. 여기서는 경계와 인계를 본다.

1. 구조 — 플러그인이 로드되고 세 스킬이 노출되는가.
2. 경계 — 각 요청이 알맞은 스킬로 가는가.
3. 인계 — 한 스킬의 산출물을 다음 스킬이 그대로 받는가.
4. 소급 검증 — 슬라이스 1~6을 `verify`로 닫는다.

4번이 필요한 이유는 이 계획이 자기 자신을 도구로 닫는 구조이기 때문이다. `verify`가 만들어지기 전에는 슬라이스를 닫을 수단이 없었다.

### 트리거 측정

발동해야 할 요청과 발동하면 안 되는 근접 요청을 스킬별로 만들어 여러 차례 실행하고 발동률을 본다. 오탐 후보는 어휘가 겹치는 것으로 고른다. 명백히 무관한 질의는 아무것도 테스트하지 않는다.

| 요청 | 가야 할 곳 |
| --- | --- |
| 계획서 없이 "이거 구현해줘" | `create-plan` |
| "계획서대로 진행해줘" | `implement` |
| "테스트 돌려봐" | 어느 스킬도 아님 |
| "다음 스프린트 계획 좀 잡아줘" | 어느 스킬도 아님 |
| 단순 버그 수정, 코드 리뷰 요청 | 어느 스킬도 아님 |
| '구현 완료' 문서로 "이거 확인 좀" | `verify` |

## 구현 순서

- [x] **1. 플러그인 검증** — 매니페스트에 세 스킬이 잡히는지, 각 스킬이 자기 폴더 안만 참조하는지 확인한다. 완료 판정: 세 스킬이 모두 노출되고 끊긴 경로가 없다.
  - 기록: 매니페스트, frontmatter의 name 일치, 참조 무결성, 딸린 파일이 본문에서 언급되는지, 다른 스킬 폴더를 가리키는지까지 한 번에 확인했다. 검사 코드는 일회성으로 돌리고 저장소에 남기지 않았다 — 규격 검사 스크립트를 걷어낸 것과 같은 이유다.
- [x] **2. 트리거 평가셋 작성 및 description 확정** — 위 표를 포함해 스킬별 평가 질의를 만들고, 측정 결과로 세 description을 고친다. 완료 판정: 세 스킬이 서로를 잠식하지 않는다.
  - 기록: 질의 20개를 `evals/trigger-eval.json`에 두고 세 description과 대조했다. 두 군데가 비어 있었다. `implement`에 재개 문구("어제 하던 계획 이어서")가 없어 재개 요청이 계획 스킬로 갈 여지가 있었고, `create-plan`의 "기술적 문제"가 원인 조사나 단순 수정까지 끌어올 수 있어 제외 문구를 붙였다. 발동률 측정은 플러그인을 설치한 세션에서만 가능하므로 여기서는 대조까지만 했다.
- [ ] **3. 실제 과제 리허설** — 요구사항 하나를 접수부터 '완료'까지 통과시킨다. 완료 판정: 상위 문서의 e2e 합격 기준을 만족한다.
- [ ] **4. 소급 검증과 패키징** — 슬라이스 1~6을 `verify`로 닫고, `.plugin` 파일로 묶는다. 완료 판정: 상위 문서의 진행률이 7 / 7이 된다.

## 테스트

### 통합 시나리오

상위 문서의 테스트 섹션에 있는 T1~T4를 여기서 실행한다. 슬라이스를 넘나드는 검증이므로 정본은 상위에 두고, 이 슬라이스는 실행과 결과 기록을 맡는다. T4의 판정 기준은 위 트리거 표다.

### e2e

항목 3의 리허설이 e2e다. 합격 기준은 상위 문서의 테스트 섹션에 있다.
