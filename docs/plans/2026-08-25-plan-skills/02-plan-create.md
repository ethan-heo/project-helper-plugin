# 슬라이스 2: plan-create 스킬

## 요약

**목표** — 사용자가 해법을 직접 설계하도록 이끌면서 계획서 다섯 섹션을 순서대로 채우는 스킬을 만든다.

**배경** — AI가 계획서를 혼자 쓰면 문서는 빨리 나오지만 사용자에게 판단이 남지 않는다. 구현이 끝난 뒤 코드가 왜 그 모양인지 설명할 수 없고, 고칠 수도 검토할 수도 없다.

**변경점** — `skills/plan-create/`에 본문과 참조 문서 셋, 빈 양식 하나를 두었다. 진행 중에 규격 검사 스크립트와 공용 디렉터리를 만들었다가 둘 다 걷어냈다.

## 설계

### 역할 분담

| | 사용자 | AI |
| --- | --- | --- |
| 위치 | 저자, 결정권자 | 검토자, 기록자 |
| 하는 일 | 해법 선택, 순서 승인, 계획 확정 | 코드베이스 조사, 질문, 반례 제시, 문서화 |
| 하지 않는 일 | — | 사용자 대신 설계를 확정하는 것 |

조사는 AI가 맡는다. 사용자를 생각하게 만드는 것과 사용자에게 잡일을 미루는 것은 다르다.

### 개입은 3단계로 제한한다

질문 → 힌트 → 선택지 순서로만 내려가고, 내려가는 신호는 사용자의 말이다. 선택지를 내놓을 때도 어느 쪽이 낫다고 결론 내지 않고, 사용자가 고른 뒤 그 이유를 물어 설계에 기록한다. 이유를 물어야 사용자가 근거를 언어화하고, 그 문장이 문서에 남는다.

사용자 주도가 받아 적기가 되지 않도록 반박도 함께 넣는다. 반례로 짚는다. 판단이 아니라 결과를 말하고, 사용자가 근거를 대면 물러선다. 같은 곳을 세 번 짚었는데도 그대로 가겠다면 우려를 한 줄 남기고 진행한다.

### 확정 전 인계 점검

구현할 때는 계획서만 보고 진행한다. 계획을 세우며 오갔지만 문서에 옮겨 적히지 않은 판단은 그 시점에 사라진다. 규격 검사로는 잡히지 않는다. 형식은 멀쩡한데 내용이 비어 있는 경우이기 때문이다.

그래서 확정 직전에 항목마다 묻는다. 이 항목만 읽고 무엇을 어디에 할지 정해지는가 → 아니면 근거가 설계에 있는가 → 그것도 없으면 대화에만 있는 결정이므로 문서로 옮긴다.

### 파일 구성

```
skills/plan-create/
├── SKILL.md                      역할, 절차, 경계
├── assets/plan-template.md       빈 양식
└── references/
    ├── plan-format.md            표기 규격 (정본)
    ├── sections.md               섹션별 작성 기준과 통과 조건
    └── facilitation.md           질문·개입·반박·축약 요청 처리
```

본문에는 절차와 경계만 두고 판정 기준은 참조 파일로 뺀다. 본문은 스킬이 켜질 때마다 전부 컨텍스트에 올라가므로, 매번 필요하지 않은 규칙까지 본문에 두면 비용이 붙고 정작 중요한 지시가 묻힌다.

검토했으나 기각: 규격 검사 스크립트(`check_plan_format.py`) — 만들었다가 걷어냈다. 세 스킬 모두 같은 모델이 읽으므로 형식을 기계로 판별할 실익이 없고, 규격을 바꿀 때마다 따라 고쳐야 하며 오탐이 진짜 문제를 가린다. 정작 위험한 "형식은 멀쩡한데 내용이 빈" 경우는 스크립트로 잡히지 않는다.

검토했으나 기각: 공용 디렉터리 `shared/` — 만들었다가 걷어냈다. 근거는 상위 문서의 설계 2절에 있다. 되살릴 조건: 세 스킬이 정말 같은 전체 규격을 필요로 하게 되고, 중복된 서술이 실제로 어긋나기 시작할 때.

## 구현 순서

- [x] **1. 계획서 규격과 양식 작성** — 규격 문서, 빈 양식, 검사 스크립트를 만든다. 완료 판정: 이 계획서 자체를 검사 스크립트에 넣어 통과한다.
  - 기록: 검사기가 이 계획서에서 두 건을 잡아냈다. 진행률 뒤 괄호 주석을 허용하도록 규격을 넓혔고, 규격을 설명하는 예시 안의 검토 표시를 실제 표시로 세던 오탐을 고쳤다.
- [x] **2. 스킬 골격 생성** — frontmatter와 섹션 목차. 완료 판정: 플러그인 로드 시 스킬 목록에 이름이 보인다.
  - 기록: description에 "코드 변경이 필요한"을 앞세우고 일정·업무 계획은 대상이 아니라고 못 박았다. 이름이 짧아진 만큼 범위를 좁히는 일을 description이 맡아야 하기 때문이다.
- [x] **3. 섹션 기준 문서 작성** — `references/sections.md`. 완료 판정: 섹션별 통과 조건과 분량 기준이 적혀 있다.
  - 기록: 각 섹션에 "담을 것"과 "담지 않을 것"을 나눠 적고, 항목이 모호한지 스스로 판별할 수 있는 신호를 넣었다.
- [x] **4. 진행 방식 문서 작성** — `references/facilitation.md`. 완료 판정: 3단계 개입과 축약 요청 처리가 적혀 있다.
  - 기록: 계획에 없던 "검토자로서 반박하기"를 추가했다. 사용자 주도만 강조하면 받아 적기만 하게 되어, 검토자를 맡는다는 목적이 빠지기 때문이다.
- [x] **5. 본문 작성** — 이유 → 절차 → 참조 연결. 완료 판정: 본문 200줄 안팎, 참조 파일마다 읽을 시점이 명시돼 있다.
  - 기록: 본문은 70줄로 끝났다. 개입 방식과 섹션 기준을 참조 파일로 뺀 덕이다.
- [x] **6. 확정 전 인계 점검 추가** — 완료 판정: 대화에서만 오간 결정이 빠진 계획서를 주면 확정 전에 그 자리를 짚는다.
  - 기록: 항목별 세 질문과 문서 전체 점검 세 가지를 넣었다. 실제 판정은 통합 시나리오와 슬라이스 6의 리허설에서 한다.
- [x] **7. 규격 검사 스크립트 제거** — 완료 판정: 플러그인 어디에도 스크립트를 실행하라는 지시가 없다.
  - 기록: 형식 판별에 스크립트가 필요 없다고 판단했다. 기계적으로 어긋나는 지점은 진행률과 체크 수 하나뿐이라, 체크와 진행률 갱신을 한 동작으로 묶는 것으로 대신한다.
- [x] **8. 공용 디렉터리 해체** — 완료 판정: 어떤 스킬도 자기 폴더 바깥을 참조하지 않는다.
  - 기록: 빈 양식과 표기 규격을 `plan-create` 안으로 옮겼다. `${CLAUDE_PLUGIN_ROOT}`가 SKILL.md 본문에서 해석되는지 확인해야 하던 미검증 항목도 함께 사라졌다.

## 테스트

### 단위 검증

- frontmatter가 파싱되고 `name`, `description`이 있다. (확인함)
- 참조 파일이 모두 본문에서 언급되고 끊긴 경로가 없다. (확인함)
- 빈 양식이 규격의 다섯 섹션과 상태 표를 그대로 담는다. (확인함)
- 스킬 폴더 바깥을 가리키는 경로가 없다. (확인함)

### 통합 시나리오

- **S1 정상 계획 수립** — "로그인 실패 시 재시도 로직을 넣고 싶다" 수준의 요구사항을 준다. 다섯 섹션이 순서대로 채워지는가. AI가 먼저 해법을 확정해 버리지 않는지, 기각한 대안이 남는지 본다.
- **S2 막힘 경로** — 사용자가 "모르겠다"를 반복한다. 질문 → 힌트 → 선택지 순서로 내려가는가. 최종 선택을 사용자가 하고, 그 이유가 문서에 남는가.
- **S3 축약 요청** — "그냥 빨리 진행해줘"를 준다. 한 번 짚어 주는가. 초안에 검토 필요 표시를 남기는지, 그 표시가 남은 채로 '계획 확정'으로 넘어가지 않는지 본다.
- **S4 반박** — 사용자가 구멍 있는 설계를 제시한다. 반례로 짚는가, 사용자가 근거를 대면 물러서는가.
- **S5 인계 점검** — 대화에서만 오간 결정이 문서에 빠진 상태로 확정하려 한다. 확정 전에 그 자리를 짚는가.
