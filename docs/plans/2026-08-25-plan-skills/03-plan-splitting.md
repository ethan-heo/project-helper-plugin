# 슬라이스 3: 계획 분할 기능

## 요약

**목표** — `create-plan`이 큰 계획을 슬라이스 여러 개로 나누어 쓰도록 확장한다.

**배경** — 계획서 하나에 모든 내용이 들어가면 읽는 사람이 전체를 머리에 올려야 하고, 사이클이 길어져 잘못된 판단이 늦게 드러난다. 이 계획 자체가 증거다. 규격 검사 스크립트와 공용 디렉터리는 구현이 한참 진행된 뒤에야 걸렸다.

**변경점** — `create-plan`에 분할 판단과 상위/하위 문서 작성 절차를 넣는다. 규격은 새로 만들지 않고 기존 다섯 섹션을 두 층위에 그대로 쓴다.

## 설계

### 나눌지 판단하는 시점과 기준

설계를 끝낸 다음에 판단한다. 요구사항을 받은 직후에는 나눌 근거가 없다. 무엇을 만들지가 보여야 경계가 드러난다.

기준은 검증 가능성이다. **그 슬라이스 하나만으로 돌려 볼 수 있는 시나리오가 있는가.** 없으면 독립된 조각이 아니라 앞뒤에 붙어야 할 부분이다.

나누지 않아도 되는 경우가 더 많다. 구현 항목이 열 개 안쪽이거나 검증 지점이 하나뿐이면 단일 문서가 낫다. 분할 자체가 비용이다.

### 구조

같은 규격을 두 층위에 재귀적으로 쓴다. 새 형식을 만들지 않는 것이 요점이다.

```
docs/plans/<날짜>-<주제>/
├── README.md          상위
├── 01-<이름>.md
└── 02-<이름>.md
```

| | 상위 문서 | 슬라이스 문서 |
| --- | --- | --- |
| 요약 | 전체 목표·배경·변경점 | 이 슬라이스의 것 |
| 상태 | 진행률 = 검증까지 끝난 슬라이스 수 | 진행률 = 완료된 구현 항목 수 |
| 설계 | 슬라이스를 관통하는 판단만 | 이 슬라이스의 설계 |
| 구현 순서 | 항목 하나 = 슬라이스 하나 | 실제 구현 항목 |
| 테스트 | 슬라이스를 넘나드는 것만 | 이 슬라이스 안에서 끝나는 것 |

번호가 순서다. 앞 슬라이스에 의존하면 항목 설명에 적는다.

검토했으나 기각: 상위 문서에 전용 형식을 두는 방안 — 형식이 둘이 되면 세 스킬이 둘 다 알아야 한다. 같은 다섯 섹션을 쓰면 `implement`와 `verify`가 상위 문서도 그대로 읽을 수 있다.

### 상위와 하위에 무엇을 두는가

나누기만 하면 같은 내용이 양쪽에 적히기 쉽다. 상위를 쓸 때 슬라이스에서 요약을 끌어올리는 대신 같은 문단을 다시 쓰게 되기 때문이다. 실제로 이 계획을 나눈 직후 상위와 슬라이스 사이에 문단 단위 중복이 세 곳 생겼다.

배치 기준은 하나다. **여러 슬라이스에 걸친 판단만 상위에 둔다.** 한 슬라이스의 산출물 사양은 그 슬라이스가 정본을 갖는다. 같은 판단이 양쪽에 필요하면 상위에는 결론 한 줄, 하위에 근거 전문을 둔다.

참조는 하위에서 상위 방향으로만 한다. 상위가 하위를 가리키기 시작하면 읽는 사람이 문서 사이를 계속 오가야 한다.

형태가 닮은 것은 중복이 아니다. 같은 종류의 산출물을 만드는 슬라이스들은 구현 항목과 단위 검증 문구가 비슷해진다. 여기서 한쪽을 참조로 바꾸면 슬라이스가 단독으로 읽히지 않는다.

### 상위 문서를 누가 갱신하는가

`verify`가 슬라이스를 '완료'로 닫는 시점에 상위의 체크와 진행률을 함께 고친다. `implement`는 상위를 건드리지 않는다. 검증되지 않은 것이 상위에서 완료로 보이면 전체 진행 상황이 실제보다 앞서 보인다.

이 규칙은 `verify` 쪽 구현이므로 슬라이스 5에서 만든다. 여기서는 상위 문서가 그렇게 갱신된다는 전제로 형식만 정한다.

## 구현 순서

- [x] **1. 분할 판단 기준 문서화** — `create-plan/references/sections.md`에 나눌지 판단하는 시점과 기준, 나누지 않는 경우를 적는다. 완료 판정: 항목 수와 검증 지점으로 판단할 수 있는 기준이 적혀 있다.
  - 기록: 잘못된 분할의 전형(파일을 만드는 단계와 그 파일을 쓰는 단계를 가르는 것)을 예로 넣었다. "독립된 기능"이라는 말만으로는 판별이 안 되고, 돌려 볼 시나리오가 있는지를 물어야 갈린다.
- [x] **2. 상위/하위 문서 작성 규격 추가** — `create-plan/references/plan-format.md`에 디렉터리 구조, 두 층위의 섹션별 차이, 번호와 의존 표기, 상위·하위 배치 원칙을 적는다. 완료 판정: 상위 문서도 기존 다섯 섹션 규격을 그대로 만족하고, 같은 판단을 양쪽에 적지 않는 기준이 적혀 있다.
  - 기록: 배치 기준을 판단 종류별 표로 정리했다. "상위에는 요약, 하위에는 세부"라고만 적으면 어디까지가 요약인지 매번 다르게 갈리기 때문이다. 형태가 닮은 것과 중복을 구분하는 문장도 함께 넣었다.
- [ ] **3. `create-plan` 절차에 분할 단계 삽입** — 설계 통과 뒤 분할 판단, 나눌 경우 상위 문서부터 쓰고 슬라이스로 내려가는 순서를 `SKILL.md`에 넣는다. 완료 판정: 나누지 않기로 한 경우 기존 단일 문서 흐름이 그대로 유지된다.

## 테스트

### 단위 검증

- 항목 1~3: 각 파일이 `SKILL.md`에서 참조되고 끊긴 경로가 없다.
- 항목 3: 본문 분량 기준(200줄 안팎)을 넘지 않는다.

### 통합 시나리오

- **S1 나누지 않는 경우** — 구현 항목이 대여섯 개로 끝나는 요구사항을 준다. 분할을 제안하지 않고 단일 문서로 끝내는가.
- **S2 나누는 경우** — 검증 지점이 셋 이상인 요구사항을 준다. 설계를 끝낸 뒤에 분할을 제안하는가, 제안 시점이 설계 전이 아닌가.
- **S3 경계 판단** — 슬라이스 후보 중 하나가 단독으로 검증 불가능한 조각일 때, 앞뒤와 합치자고 짚는가.
- **S4 상위 문서 형식** — 만들어진 상위 문서가 다섯 섹션 규격을 그대로 만족하는가. 구현 항목이 슬라이스 파일을 가리키는가.
- **S5 중복 회피** — 나눈 결과에서 상위와 슬라이스에 같은 문단이 반복되지 않는가. 슬라이스의 산출물 사양이 상위로 끌려 올라가지 않는가.
