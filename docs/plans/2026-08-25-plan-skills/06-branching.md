# 슬라이스 6: 브랜치 전략과 선행 확인

## 요약

**목표** — 계획 진행을 브랜치로 격리하고, 슬라이스 사이의 선행 관계를 실제로 확인해 순서를 지키게 한다.

**배경** — 지금은 모든 작업이 한 브랜치에 쌓인다. 검증되지 않은 코드가 기본 브랜치에 섞이고, 어느 슬라이스가 어디까지 들어갔는지 이력으로 구분되지 않는다. 선행 관계도 상위 문서에 문장으로만 적혀 있을 뿐 아무도 확인하지 않아, 뒤 슬라이스를 먼저 시작해도 막히지 않는다.

**변경점** — 브랜치 규칙과 선행 표기를 규격에 넣고, `implement`가 브랜치를 만들고 선행을 확인하며, `verify`가 승인 후 머지한다.

## 설계

### 브랜치 구조

| 브랜치 | 단위 | 기점 |
| --- | --- | --- |
| `feature/<주제>` | 계획 묶음 하나 | 기본 브랜치 |
| `slice/<주제>/NN-<이름>` | 슬라이스 하나 | `feature/<주제>` |

접두사를 `feature/`와 `slice/`로 나눈 이유는 git이 브랜치를 파일로 저장하기 때문이다. `feature/plan-skills`가 있으면 `feature/plan-skills/01-foundation`은 만들 수 없다. 상위 이름이 파일인데 그 아래에 디렉터리를 두려는 꼴이라 거부된다. 실제로 확인했다.

계획서를 나누지 않은 경우에는 `feature/<주제>` 하나만 쓰고 slice 브랜치를 만들지 않는다.

**누가 언제 만드는가**

- `feature/<주제>` — `implement`가 첫 호출에서 없으면 만든다. 기점은 기본 브랜치.
- `slice/<주제>/NN-<이름>` — `implement`가 슬라이스를 시작할 때 `feature`에서 딴다.
- 머지 — `verify`가 사용자 승인 후 slice를 feature로 `--no-ff` 머지한다. 슬라이스 단위가 이력에 남아야 나중에 어디까지 검증됐는지 볼 수 있다.
- `feature` → 기본 브랜치 — 스킬이 하지 않는다. 사용자가 판단할 몫이다.

검토했으나 기각: 슬라이스마다 기본 브랜치에서 따는 방안 — 선행 슬라이스의 결과 위에서 작업할 수 없다. 선행이 끝났다는 사실과 그 코드가 손에 있다는 사실이 어긋난다.

### 계획서는 어디에 커밋되나

계획 묶음 전체는 `feature`에 둔다. 슬라이스 문서의 상태 변경은 그 slice 브랜치에서 하고, 상위 `README.md` 갱신은 머지가 끝난 뒤 `feature`에서 한다.

상위를 slice 브랜치에서 고치면 슬라이스마다 같은 파일의 같은 자리를 고치게 되어 머지할 때마다 충돌한다. 머지 후에 고치면 충돌이 생기지 않는다.

### 선행 표기

상위 문서의 구현 항목에 고정 표기를 쓴다. 선행이 없으면 생략한다.

```
- [ ] **3. 계획 분할 기능** — create-plan을 확장한다. 선행: 02 → `03-plan-splitting.md`
```

"슬라이스 2에 의존"처럼 문장으로 적으면 형태가 매번 달라져 확인할 수 없다.

### 선행 확인

`implement`가 슬라이스 문서를 열 때 같은 폴더의 `README.md`를 읽는다. 파일명으로 자기 항목을 찾고, `선행:`에 적힌 번호의 항목이 상위에서 체크됐는지 본다.

| 선행 상태 | 처리 |
| --- | --- |
| 상위에서 체크됨 (검증까지 끝남) | 진행한다 |
| 미체크지만 그 슬라이스 문서가 `구현 완료` | 검증 전이라는 점을 알리고 사용자가 진행 여부를 정한다 |
| 그 외 | 진행하지 않고 어느 슬라이스가 먼저인지 알린다 |

원칙은 검증까지 끝난 것 위에서만 쌓는 것이다. 예외를 두는 이유는 검증이 사용자의 시간을 필요로 해서 미뤄질 수 있고, 그때 전체가 멈추면 쓸 수 없기 때문이다. 예외로 진행하면 뒤에 쌓은 것이 앞의 검증 결과에 영향을 받는다는 점을 알린다.

상위 문서가 없으면(단일 계획서) 확인을 건너뛴다.

`implement`는 상위를 **읽기만** 한다. 쓰는 것은 여전히 `verify`의 몫이다.

## 구현 순서

- [ ] **1. 브랜치 규격과 선행 표기 추가** — `create-plan/references/plan-format.md`에 브랜치 이름 규칙, 계획서가 커밋되는 위치, 상위 항목의 `선행:` 표기를 적는다. 완료 판정: 이름 충돌이 왜 생기는지와 회피 방법이 적혀 있다.
- [ ] **2. `implement`에 브랜치 생성과 선행 확인 추가** — `execution.md`와 `SKILL.md`에 브랜치를 만드는 시점, 선행 확인 절차, 예외 처리를 넣는다. 완료 판정: 선행이 닫히지 않은 슬라이스를 주면 진행하지 않는다.
- [ ] **3. `verify`에 머지 절차 추가** — `verification.md`와 `SKILL.md`에 승인 후 머지, 머지 뒤 상위 갱신 순서를 넣는다. 선행: 슬라이스 5. 완료 판정: 승인 없이는 머지하지 않는다.

## 테스트

### 단위 검증

- 항목 1~3: 각 참조 파일이 해당 `SKILL.md`에서 참조되고 끊긴 경로가 없다.
- 항목 2, 3: 본문이 200줄 안팎이고 스킬 폴더 바깥을 참조하지 않는다.

### 통합 시나리오

- **S1 브랜치 생성** — 계획 묶음으로 `/implement`를 처음 호출한다. `feature/<주제>`와 `slice/<주제>/01-...`이 생기는가, 이름 충돌 없이 만들어지는가.
- **S2 선행 미완** — 선행이 닫히지 않은 슬라이스를 시작하려 한다. 진행하지 않고 어느 슬라이스가 먼저인지 알리는가.
- **S3 선행이 구현 완료** — 선행 슬라이스가 `구현 완료`인 상태로 다음을 시작하려 한다. 검증 전임을 알리고 사용자에게 선택을 넘기는가, 임의로 진행하지 않는가.
- **S4 단일 계획서** — 나누지 않은 계획서로 실행한다. 상위를 찾으려다 멈추지 않는가, slice 브랜치를 만들지 않는가.
- **S5 머지** — `/verify` 승인 후 slice가 feature로 머지되는가, 상위 갱신이 머지 뒤 feature에서 일어나는가.
- **S6 기본 브랜치** — 어느 단계에서도 feature를 기본 브랜치에 머지하지 않는가.
