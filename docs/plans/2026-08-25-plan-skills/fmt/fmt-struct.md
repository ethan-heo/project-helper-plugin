# 계획서 형식 구조화

## 요약

**목표** — 계획서에서 훑을 수 있는 부분을 표로 바꿔, 산문을 다 읽지 않고도 무엇이 정해졌는지 알 수 있게 한다.

**배경** — 지금 계획서는 설계와 테스트가 통째로 산문이다. 결정이 무엇이었는지 알려면 문단을 다 읽어야 하고, 시나리오는 한 줄에 입력·기대·시점이 다 들어가 있어 눈으로 훑기 어렵다. 기능명세서 작성 지침에서 쓸 만한 원칙 셋을 가져온다.

**변경점** — 설계 앞에 결정 요약 표를 두고, 예외 상황을 최소 세 개 적게 하고, 테스트 시나리오를 표로 바꾼다. 구현 항목에는 도메인-기능-번호 형태의 ID를 붙이고, 그 세 조각에 맞춰 계획서를 세 층으로 나눈다.

## 설계

### 결정 요약

| 결정 | 택한 것 | 근거 | 기각한 대안 |
| --- | --- | --- | --- |
| 명세서 형식을 얼마나 가져올까 | 원칙 셋만 | 계획서는 "왜 그렇게 정했는가"를 담는 문서다. 10개 필드를 통째로 옮기면 명세서가 된다 | 10개 필드 전부 — 근거와 기각 대안이 들어갈 자리가 사라진다 |
| 설계를 표로 바꿀까 | 표 + 산문 | 훑을 사람은 표만 보고, 파고들 사람은 아래 산문을 읽는다 | 설계 전체를 표로 — 근거가 한 칸에 눌려 죽는다 |
| 구현 항목을 표로 바꿀까 | 바꾸지 않는다 | 체크박스가 진행 상태를 나르고 세 스킬이 그 표기에 물려 있다 | 체크 열이 있는 표 — 이득보다 파급이 크다 |
| 항목 ID 체계 | 도메인-기능-번호 | 커밋 메시지와 검증 기록에서 항목을 가리킬 수 있다 | 일련번호만 — 문서를 넘나들면 무엇을 가리키는지 모른다 |
| 번호를 어디서 세나 | 도메인-기능 조합 안에서 | 항목을 중간에 끼워 넣어도 뒤가 밀리지 않는다. 조합마다 항목이 하나면 전부 001이고 그게 맞다 | 문서 전체 일련번호, 도메인 단위 번호 — 둘 다 항목을 끼워 넣으면 커밋에 적힌 ID가 다른 항목을 가리키게 된다 |
| 번호 형식을 남길까 | 남기지 않는다 | 형식이 둘이면 문서마다 어느 쪽인지 판별해야 한다 | 상위는 번호, 하위는 ID — 처음 정했다가 뒤집었다. 한 계획 안에서 두 형식을 쓰는 셈이었다 |
| 규격 설명을 계획서에 둘까 | 두지 않는다 | 읽는 사람은 계획서에서 이 계획의 내용을 찾는다. 규칙이 섞이면 어디까지가 계획이고 어디부터가 도구 사용법인지 갈리지 않는다 | 편의를 위해 요약해 둔다 — 규격을 고칠 때 따라 고쳐야 할 자리가 계획서 수만큼 는다 |
| 파일 이름의 대소문자 | 소문자 | 저장소의 다른 경로가 모두 소문자다. 대소문자를 구분하지 않는 파일 시스템에서 대문자 폴더는 이름만 바꾸는 rename이 한 번에 먹지 않는다 | ID 그대로 대문자 — 경로가 눈에 튀고 옮길 때 임시 이름을 거쳐야 한다 |
| 기존 계획서에 소급 적용할까 | 구조는 옮기고 내용은 그대로 둔다 | 규격만 있고 그 규격으로 만든 계획서가 하나도 없으면 검증할 표본이 없다. 각 문서가 적어 둔 판단과 기록은 손대지 않는다 | 전혀 손대지 않는다 — 처음 그렇게 정했다가 뒤집었다 / 내용까지 새로 쓴다 — 이력이 흐려진다 |

### 상위 문서도 ID를 쓴다

처음에는 상위를 번호로 두려 했다. 하위 문서 목록에는 도메인이랄 것이 없고 파일 이름이 이미 식별자 노릇을 한다고 봤다. 뒤집었다. 한 계획 안에서 상위와 하위가 다른 형식을 쓰면, 읽는 쪽이 문서마다 어느 형식인지 먼저 판별해야 한다.

상위의 ID는 그 문서가 다루는 영역에서 딴다. `REPO-SETUP`, `SKILL-CREATE` 같은 식이다.

**대신 상위 문서에 ID 용어 표를 둔다.** 도메인 코드는 계획마다 다르게 정해지므로, 무엇이 무엇을 뜻하는지 한 곳에 모아 두지 않으면 `FMT`가 형식인지 포맷터인지 알 수 없다.

### 예외를 몇 개 적게 할 것인가

원문 지침은 최소 3~5개다. 그대로 쓰되 강제하지는 않는다. 코드 변경이 아닌 계획은 예외랄 것이 없을 수 있다. 그때는 "해당 없음"과 그 이유를 적는다. 빈칸으로 두면 생각하지 않은 것인지 없는 것인지 구분되지 않는다.

### 예외 상황

| 상황 | 처리 |
| --- | --- |
| 결정이 한둘뿐인 작은 계획 | 결정 요약 표를 생략하고 산문만 쓴다. 두 줄짜리 표는 번잡하다 |
| 시나리오가 한둘뿐인 계획 | 표 대신 목록을 쓴다. 같은 이유다 |
| 도메인이 불분명한 항목 | 대상 파일이 속한 디렉터리에서 딴다. 그것도 애매하면 계획서 주제를 도메인으로 쓴다 |
| 기존 계획서를 이어서 작업할 때 | 그 문서의 기존 형식을 따른다. 한 문서 안에서 형식이 섞이지 않게 한다 |

## 구현 순서

- [x] **FMT-STRUCT-001** 규격에 새 형식 반영 — `plan-format.md`에 결정 요약 표, 예외 표, 시나리오 표, 항목 ID 표기를 적는다. 완료 판정: 네 가지가 모두 예시와 함께 있고 생략 조건이 명시돼 있다.
  - 기록: 표마다 "이럴 땐 만들지 마라"를 붙였다. 형식을 주면 무조건 채우려 드는데, 두 줄짜리 표는 산문보다 읽기 나쁘다. 예외 세 개를 뽑는 요령(잘못된 입력·전제가 깨진 상태·바깥의 실패)도 함께 적었다. 숫자만 주면 억지로 채우게 된다.
- [x] **FMT-STRUCT-002** 작성 기준과 통과 조건 갱신 — `sections.md`의 설계·테스트 절에 새 형식을 반영한다. 완료 판정: 설계 통과 조건이 "예외가 적혀 있거나 해당 없음이 밝혀져 있다"를 포함한다.
  - 기록: 설계 절의 "담을 것"을 표 뒤 산문 몫으로 다시 나눴다. 표와 산문이 같은 것을 두 번 말하면 표를 만든 뜻이 없다. 근거는 표에 한 줄, 한 줄로 안 되는 것만 아래 산문으로 간다.
- [x] **FMT-STRUCT-003** 빈 양식 갱신 — `plan-template.md`를 새 형식으로 바꾼다. 완료 판정: 양식만 복사해도 표 뼈대가 들어 있다.
  - 기록: 표 아래마다 "이럴 땐 지워라"를 꺾쇠 안에 넣었다. 빈 양식은 채우라는 신호로 읽히므로, 지워도 된다는 말을 양식 안에 두지 않으면 두 줄짜리 표가 그대로 남는다.
- [x] **FMT-STRUCT-004** 두 스킬의 전제 갱신 — `plan-implement`는 항목 ID 표기를, `plan-verify`는 시나리오 표를 읽도록 고친다. 완료 판정: 옛 표기와 새 표기를 모두 받아들이고 어느 쪽인지 판별해 진행한다.
  - 기록: 계획에 없던 것을 하나 넣었다. ID 형식이면 커밋 메시지에 그 ID를 넣게 했다. ID를 만든 이유가 "문서 밖에서 항목을 가리키기 위해"인데 커밋에 안 넣으면 그 자리가 없어진다. 프로젝트 커밋 규칙과 부딪히면 규칙을 따르고 ID는 본문에 넣는다.

- [x] **FMT-STRUCT-005** 번호 형식 폐기 — 규격에서 번호 형식을 옛 형식으로 낮추고, 상위 문서의 구현 항목과 선행 표기도 ID를 쓰게 한다. 완료 판정: 규격이 ID 하나만 정식으로 다루고, 번호 형식은 옛 문서를 만났을 때의 처리로만 남는다.
  - 기록: 상위를 번호로 두려던 처음 판단을 뒤집었다. 파일 이름이 식별자 노릇을 한다고 봤는데, 결국 한 계획 안에 형식이 둘이 되어 읽는 쪽이 문서마다 판별해야 했다. 선행 표기도 ID로 바꿨다.
- [x] **FMT-STRUCT-006** ID 용어 표 — 상위 문서에 도메인 코드 사전을 두도록 규격에 넣고, 이 계획의 상위 문서에 실제로 만든다. 완료 판정: 상위 문서만 읽고도 각 도메인 코드가 무엇을 가리키는지 알 수 있다.
  - 기록: 도메인 코드는 계획마다 새로 정해지므로 사전이 없으면 `FMT`가 형식인지 포맷터인지 알 수 없다. 이 계획의 상위 문서에 다섯 코드를 적었다. 처음에는 하위 문서에도 각자 표를 뒀는데, 그러면 같은 코드가 문서마다 다르게 설명될 수 있어 FMT-STRUCT-007에서 상위로 모았다.
- [x] **FMT-STRUCT-007** 용어 표를 상위 문서에서만 관리 — 하위 문서의 용어 표를 없애고 상위 표가 전체 도메인을 덮게 한다. 완료 판정: 하위 문서에 용어 표가 없고, 상위 표에 실제로 쓰이는 도메인이 모두 있다.
  - 기록: 상위 표의 "쓰는 곳" 열을 개별 ID에서 문서 단위로 바꿨다. ID를 나열하면 항목이 늘거나 번호가 바뀔 때마다 표를 고쳐야 하는데, 문서는 잘 바뀌지 않는다. 이번 재번호 때 실제로 그 열을 두 번 고쳤다.
- [x] **FMT-STRUCT-008** 문서를 ID로 가리키게 함 — 본문에서 "슬라이스 6"처럼 번호로 가리키던 것을 ID로 바꾸고, 하위 문서 제목에서도 번호를 뺀다. 완료 판정: 계획서 어디에도 문서를 번호로 가리키는 곳이 없다.
  - 기록: 고치면서 네 곳이 이미 어긋나 있는 것을 찾았다. 통합 문서가 6→7→8→9로 밀리는 동안 본문 참조는 따라가지 못했다. 제목의 "슬라이스 N:"도 같은 이유로 뺐다. 파일 이름이 순서를 나타내고 상위 문서가 ID와 파일을 짝지어 주므로 제목에 번호를 둘 이유가 없다. 구현 항목 표기는 완료된 문서를 그대로 두라는 지시에 따라 손대지 않았고, 본문 참조만 고쳤다.
- [x] **FMT-STRUCT-009** 3단 구조를 `plan-create` 규격에 반영 — 계획을 도메인 폴더와 기능 문서로 나누고, 층마다 ID 조각이 하나씩 확정되게 한다. 완료 판정: `plan-create`의 규격·기준·본문에 세 층이 적혀 있고 "슬라이스"라는 말이 남아 있지 않다.
  - 기록: 기능 문서의 파일 이름을 ID로 쓴다(`AUTH-LOGIN` → `auth/auth-login.md`). 그러면 위층 항목에 파일 포인터를 적을 필요가 없어진다. ID가 곧 경로이기 때문이다. 순서 번호도 파일 이름에서 뺐다. 중간에 하나가 끼어들 때마다 뒤가 밀리는 문제가 이 계획에서 네 번 났다. ID 세 조각이 계층 셋과 그대로 맞물린다. 도메인은 폴더, 기능은 파일, 번호는 그 파일 안의 항목이다. 그래서 "번호는 조합 안에서 센다"가 "이 문서 안에서 1부터 센다"로 줄었고, 조합이 겹칠 걱정도 사라졌다. 폴더와 파일이 도메인·기능을 정해 주므로 항목마다 조합을 고민할 일이 없어졌다. 도메인이 하나뿐이면 최상위를 만들지 않고 도메인 문서가 그 자리를 대신하되, 폴더는 만든다. 나중에 도메인이 늘면 최상위만 얹으면 된다.
- [ ] **FMT-STRUCT-010** `plan-implement`와 `plan-verify`를 3단에 맞춤 — 전제, 선행 확인, 브랜치 이름, 위층 갱신 절차를 세 층에 맞게 고친다. 완료 판정: 위층 갱신이 한 번에 한 층씩 올라가고, 두 스킬에 "슬라이스"라는 말이 남아 있지 않다.
- [x] **FMT-STRUCT-011** 이 계획서를 세 층으로 재구성 — 계획서를 도메인 폴더와 기능 문서로 옮기고 구현 항목의 ID를 문서마다 다시 맨다. 완료 판정: 세 층이 모두 다섯 섹션 규격을 만족하고 문서 사이의 참조가 전부 ID로 이어진다.
  - 기록: 규격만 있고 그 규격으로 만든 계획서는 하나도 없는 상태를 없앴다. 옮기면서 세 가지가 드러났다. 기능 문서가 하나뿐인 도메인(`REPO`, `FLOW`, `REL`)은 도메인 문서에 쓸 말이 적어, 설계에 그 도메인의 경계만 적고 검증은 기능 문서에 있다고 밝히는 형태로 정리했다. 문서 하나를 가리키던 ID(`SKILL-CREATE-001`)가 기능 ID(`SKILL-CREATE`)로 한 조각 짧아져 문서 사이의 참조가 전부 바뀌었다. `SKILL-NAMING`에서는 옛 이름을 일괄 치환할 때 망가진 문장 넷도 함께 고쳤다.
- [x] **FMT-STRUCT-012** 규격 설명을 계획서에서 걷어냄 — 규격에 "규격을 계획서에 옮겨 적지 않는다"를 넣고, 이 계획의 문서에서 해당 문구를 지운다. 완료 판정: 계획서에 ID 짓는 법, 층 구성, 섹션에 무엇을 담는가를 설명하는 문장이 없다.
  - 기록: 걷어내고 보니 최상위의 ID 용어 절은 도메인 코드 표 하나만 남았다. 층 구조 설명도 번호 세는 법도 전부 규격 쪽 내용이었다. 규격을 만드는 계획이라 설계에 형식이 나오는 것은 맞지만, "이렇게 써라"로 적힌 문장은 계획이 아니라 사용법이었다. 그 구분을 규격에 예외로 적어 두었다.
- [x] **FMT-STRUCT-013** 파일과 폴더 이름을 소문자로 — 규격에 소문자 규칙을 넣고 이 계획의 도메인 폴더와 기능 문서 이름을 바꾼다. 완료 판정: `README.md`를 뺀 모든 경로가 소문자이고, 본문의 ID는 대문자 그대로다.
  - 기록: 대소문자를 구분하지 않는 파일 시스템에서는 `REPO`를 `repo`로 한 번에 바꿀 수 없다. 임시 이름을 거쳐 두 번 옮겨야 하고, 그 사이 git 인덱스만 소문자로 바뀌고 디스크 이름은 대문자로 남는 상태가 생긴다. 규격에 소문자로 적어 두면 처음부터 그 상황이 없다.
