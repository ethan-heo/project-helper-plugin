# 계획서 작성 스킬 구축 계획

## 요약

**목표** — 기술적 문제를 사용자가 직접 풀어내도록 돕고, 그 과정과 결론을 계획서 한 편으로 남기는 스킬을 만든다. AI는 해법을 대신 내놓지 않고, 경험 많은 엔지니어 검토자로서 질문·반박·기록을 맡는다. 계획이 확정된 뒤에는 같은 문서가 구현과 검증의 기준이 된다.

**배경** — 요구사항을 던지면 AI가 곧바로 해법과 코드를 내놓는 방식은 빠르지만, 사용자에게 판단의 흔적이 남지 않는다. 왜 그 구조를 택했는지 모른 채 변경이 쌓이고, 구현 후 검증도 "돌아가니까 됐다" 수준에 머문다. 문서를 순서대로 채우면서 생각을 끝까지 밀어붙이게 만드는 장치가 필요하다.

**변경점** — `project-helper-plugin` 저장소에 플러그인 골격을 만들고 스킬 세 개와 공용 규격 하나를 추가한다.

| 이름 | 역할 | 다루는 상태 |
| --- | --- | --- |
| `create-plan` | 사용자와 함께 계획서를 작성한다 | → 계획 확정 |
| `implement` | 계획서의 구현 순서를 하나씩 실행한다 | 계획 확정 → 구현 중 → 구현 완료 |
| `verify` | 테스트 시나리오와 변경점을 사용자와 확인한다 | 구현 완료 → 완료 |
| `shared/plan-format` | 세 스킬이 공유하는 계획서 규격과 빈 양식 | — |

세 스킬을 나눈 이유는 설계 1절에 있다. 계획서는 사람이 읽는 문서인 동시에 세 스킬 사이의 인계 문서이므로, 형식을 규격으로 고정한다.

## 상태

| 항목 | 값 |
| --- | --- |
| 단계 | 구현 중 |
| 마지막 갱신 | 2026-08-25 |
| 구현 진행률 | 0 / 13 ("구현 순서" 참고) |

## 설계

### 1. 왜 스킬을 셋으로 나누는가

한 스킬로 묶으면 정반대의 자세를 한 지시서에 담게 된다. 계획 단계에서 AI는 뒤로 물러서서 질문만 하고, 구현 단계에서는 앞에 나서서 코드를 쓴다. 같은 문서 안에서 두 태도를 전환하라고 지시하면 어느 쪽도 선명해지지 않는다.

나누면 세 가지를 얻는다.

- **상태 전환이 구조로 보장된다.** '계획 확정 → 구현 중'이 "사용자가 지시하면"이라는 문장이 아니라 `/implement` 호출이라는 행위로 고정된다. 마찬가지로 '완료' 표시는 `/verify`를 거치지 않으면 일어날 수 없다.
- **AI가 자기 일을 자기가 합격시키지 않는다.** 구현한 주체와 검증을 진행하는 주체를 분리한다. `verify`는 판정하지 않고 증거를 내놓는 쪽이며, 판정은 사용자가 한다.
- **컨텍스트가 필요한 만큼만 로드된다.** 계획을 쓰는 동안 커밋 규칙이 컨텍스트에 있을 이유가 없다.

대신 계획서 형식이 세 스킬의 인터페이스가 된다. 표기가 어긋나면 `implement`가 문서를 읽지 못한다. 그래서 규격을 먼저 고정하고(구현 순서 2번), 세 스킬이 같은 파일을 참조한다.

### 2. 파일 구성

```
project-helper-plugin/
├── .claude-plugin/
│   └── plugin.json            # 플러그인 매니페스트
├── CLAUDE.md                  # 커밋 규칙, 계획서 경로 규칙
├── README.md
├── docs/plans/                # 생성된 계획서
├── shared/
│   ├── plan-format.md         # 계획서 규격 (세 스킬 공통)
│   ├── plan-template.md       # 빈 양식
│   └── check_plan_format.py   # 규격 준수 검사
└── skills/
    ├── create-plan/
    │   ├── SKILL.md
    │   └── references/
    │       ├── sections.md       # 섹션별 작성 기준과 통과 조건
    │       └── facilitation.md   # 질문·개입 방식
    ├── implement/
    │   ├── SKILL.md
    │   └── references/execution.md    # 진행, 커밋, 상태 갱신, 복귀
    └── verify/
        ├── SKILL.md
        └── references/verification.md # 검증 절차, 증거 제시 방식
```

스킬은 3단계로 로드된다. 이름과 description은 항상 컨텍스트에 있고, SKILL.md 본문은 스킬이 켜질 때 전부 올라가며, references는 필요할 때만 읽힌다. 본문에 모든 규칙을 넣으면 매 호출마다 비용이 붙고 정작 중요한 지시가 묻힌다. 그래서 본문에는 역할·절차·참조 위치만 두고 세부 판정 기준은 references로 뺀다. 본문은 각각 200줄 안팎을 목표로 한다.

`shared/`를 스킬 바깥에 두는 것은 정의를 한 곳에만 두기 위해서다. 각 SKILL.md는 `${CLAUDE_PLUGIN_ROOT}/shared/...` 형태로 이 파일을 가리킨다. 플러그인 내부 경로를 절대 경로로 박으면 설치 위치가 바뀔 때 깨지므로, 이 변수를 쓰는 것이 플러그인 규약이다.

### 3. 계획서 규격 (`shared/plan-format.md`)

읽는 쪽이 기계적으로 판별할 수 있어야 하므로 다음을 고정한다.

| 요소 | 규격 |
| --- | --- |
| 섹션 제목 | `## 요약`, `## 상태`, `## 설계`, `## 구현 순서`, `## 테스트` — 문자열과 순서 고정 |
| 상태 표 | 2열(항목/값), 3행(단계, 마지막 갱신, 구현 진행률) |
| 단계 값 | `계획 확정`, `구현 중`, `구현 완료`, `완료` 중 하나 |
| 마지막 갱신 | `YYYY-MM-DD` |
| 진행률 | `n / m` |
| 구현 항목 | `- [ ] **n. 제목** — 설명` / 완료 시 `- [x]` |

`implement`와 `verify`는 시작할 때 규격을 확인한다. 만족하지 않으면 추측해서 진행하지 않고 어긋난 지점을 사용자에게 알린다. 형식을 임의로 해석하고 진행하면 상태가 실제와 어긋난 채 커밋이 쌓인다.

### 4. `create-plan` — 계획서 작성

**역할 분담**

| | 사용자 | AI |
| --- | --- | --- |
| 위치 | 저자, 결정권자 | 검토자, 기록자 |
| 하는 일 | 해법 선택, 구현 순서 승인 | 코드베이스 조사, 질문, 반례 제시, 문서 작성 |
| 하지 않는 일 | — | 사용자 대신 설계를 확정하는 것 |

AI가 먼저 답을 내놓으면 계획서는 완성되지만 목적은 달성되지 않는다. 그래서 개입을 3단계로 제한한다.

1. **질문** — "이 요구사항에서 가장 먼저 깨질 것 같은 부분은 어디인가요?"
2. **힌트** — 사용자가 막혔다고 말하면 답 대신 볼 곳을 가리킨다. "기존 A 모듈이 같은 문제를 어떻게 처리하는지 보면 실마리가 있습니다."
3. **선택지** — 그래도 막히면 2~3개 안을 트레이드오프와 함께 늘어놓는다. 어느 쪽이 낫다고 결론 내지 않고, 사용자가 고른 뒤 고른 이유를 문서에 기록한다.

다음 단계로 내려가는 조건은 사용자의 신호다. AI가 스스로 판단해 건너뛰지 않는다.

**축약 요청 처리** — 사용자가 "그냥 빨리 진행해줘"라고 하면, 직접 설계하지 않으면 구현 후 변경점을 파악하기 어렵다는 점을 한 번 짚는다. 그래도 원하면 AI가 초안을 쓰되, 사용자가 결정하지 않은 항목에 `<!-- 사용자 검토 필요 -->` 표시를 남긴다. 표시가 남아 있는 문서는 '계획 확정'으로 넘어갈 수 없다.

**섹션 진행과 통과 조건** — 문서는 위에서부터 순서대로 채운다.

| 섹션 | 통과 조건 |
| --- | --- |
| 요약(가제) | 목표와 배경에 사용자가 동의. 변경점은 비워 둔다 |
| 상태 | 자동 생성 |
| 설계 | 해법이 하나로 좁혀지고, 기각한 대안과 기각 사유가 적혀 있다 |
| 구현 순서 | 모든 항목이 한 커밋 단위이고 완료 판정 기준이 있다 |
| 테스트 | 모든 구현 항목이 최소 하나의 검증에 대응된다 |
| 요약(확정) | 변경점이 설계·구현 순서와 일치한다 |

변경점은 설계와 구현 순서가 나온 뒤에야 정확히 쓸 수 있다. 그래서 요약은 가제로 시작해 마지막에 확정한다.

**문서 위치** — 기본 경로는 `docs/plans/YYYY-MM-DD-<주제>.md`다. 대상 프로젝트의 지시사항(CLAUDE.md, AGENTS.md 등)에 다른 규칙이 있으면 그쪽이 우선한다.

### 5. `implement` — 구현 진행

`/implement`로 호출한다. 대상은 상태가 '계획 확정'인 계획서다.

1. 규격을 확인하고, 상태가 '계획 확정'이며 미해결 검토 표시가 없는지 본다.
2. 상태를 '구현 중'으로 바꾼다.
3. 체크되지 않은 첫 항목을 구현한다.
4. 해당 항목의 단위 테스트를 통과시킨다.
5. 커밋한다. 메시지 형식은 프로젝트 지시사항(CLAUDE.md, CONTRIBUTING 등)에서 읽어 따르고, 규칙을 찾지 못하면 사용자에게 확인한 뒤 진행한다. 이 저장소의 규칙은 Conventional Commits이며 CLAUDE.md에 적는다.
6. 체크박스를 채우고, 진행률과 마지막 갱신을 고치고, 무엇이 왜 바뀌었는지 한두 줄을 남긴다.
7. 남은 항목이 있으면 3번으로, 없으면 상태를 '구현 완료'로 바꾸고 `/verify`를 안내한다.

**계획의 결함을 발견하면 멈춘다.** 구현 중 전제가 틀렸다는 것이 드러나면 구현 순서를 그 자리에서 고치지 않는다. 진행을 멈추고, 상태를 '계획 확정'으로 되돌리고, 무엇이 어긋났는지 보고한 뒤 `create-plan`으로 넘긴다. 계획서를 구현에 맞춰 사후 수정하면 문서가 근거를 잃고 결정의 기록이 아니라 결과의 요약이 된다.

`implement`는 '완료'를 표시하지 않는다.

### 6. `verify` — 검증

`/verify`로 호출한다. 대상은 상태가 '구현 완료'인 계획서다.

1. 테스트 섹션의 시나리오를 하나씩 실행하고 결과를 보여 준다.
2. 계획서의 변경점과 실제 변경 내역을 대조해 차이를 짚는다.
3. 구현 항목별 변경 요약을 사용자에게 제시한다.
4. 사용자가 승인하면 상태를 '완료'로 바꾼다.
5. 미달 항목이 있으면 상태를 '구현 중'으로 되돌리고, 계획 자체가 문제면 '계획 확정'으로 되돌린다.

`verify`는 판정하지 않는다. 통과 여부를 스스로 선언하는 대신 실행 결과와 변경 내역을 증거로 내놓고, 판정은 사용자가 한다. 구현한 주체가 합격 판정까지 내리면 검증 단계가 형식만 남기 때문이다.

### 7. 상태 전환 정리

| 전환 | 주체 | 조건 |
| --- | --- | --- |
| → 계획 확정 | 사용자 | 다섯 섹션 통과, 미해결 검토 표시 없음 |
| 계획 확정 → 구현 중 | `implement` | `/implement` 호출 |
| 구현 중 진행 | `implement` | 항목 완료 → 테스트 → 커밋 → 체크 → 진행률 갱신 |
| 구현 중 → 계획 확정 | `implement` | 계획의 결함 발견 |
| 구현 중 → 구현 완료 | `implement` | 모든 항목 체크 |
| 구현 완료 → 구현 중 | `verify` | 검증 미달 |
| 구현 완료 → 완료 | `verify` | 사용자 승인 |

### 8. 이해 가능성

배경을 모르는 독자가 읽는다고 가정한다. 내부 약어와 코드명은 첫 등장에서 한 번 풀어쓴다. 설계에는 결론만이 아니라 근거와 기각한 대안을 함께 남긴다 — 몇 주 뒤 같은 논의를 다시 하지 않기 위해서다. 구현 중에는 각 항목을 끝낼 때 무엇이 왜 바뀌었는지 한두 줄을 남기고, 이 기록이 `verify` 단계에서 사용자에게 제시된다.

### 9. 트리거 description 초안

세 스킬이 서로를 잠식하지 않도록 계획서의 유무와 상태를 경계로 삼는다. 이름이 짧아진 만큼 범위를 좁히는 일은 description이 맡는다. 특히 `create-plan`은 "계획"이라는 말이 일정이나 프로젝트 계획까지 끌어올 수 있으므로, 대상이 코드 변경이라는 점을 앞에 둔다.

- **create-plan** — 코드 변경이 필요한 요구사항이나 기술적 문제를 받았을 때, 곧바로 구현하지 말고 먼저 구현 계획서를 만들 때 사용한다. 사용자가 해법을 직접 설계하도록 질문으로 이끌고, 다섯 섹션을 순서대로 채운다. "계획서 쓰자", "설계 좀 같이 해보자", "어떻게 구현할지 정리하자" 같은 요청, 그리고 구조 변경이나 여러 단계가 필요한 작업 요청에서 사용한다. 일정 수립, 업무 계획, 문서 작성 계획에는 사용하지 않는다.
- **implement** — 이미 작성된 계획서가 있고 상태가 '계획 확정'일 때, 구현 순서를 하나씩 실행하기 위해 사용한다. 계획서가 없는 상태의 "구현해줘"에는 사용하지 않는다.
- **verify** — 상태가 '구현 완료'인 계획서를 사용자와 함께 검증하고 '완료'로 넘길 때 사용한다.

### 10. 예상 실패 모드

- **AI가 대신 설계를 끝내 버린다.** 가장 큰 위험이다. 금지 문구를 나열하는 대신 SKILL.md 본문 앞머리에 "왜 사용자가 직접 답을 내야 하는가"를 먼저 설명한다.
- **세 스킬의 경계가 흐려진다.** 계획서 유무와 상태를 유일한 판별 기준으로 삼고, 각 스킬이 시작할 때 상태를 확인한 뒤 맞지 않으면 알맞은 스킬을 안내한다.
- **문서가 길어져 아무도 읽지 않는다.** 섹션마다 분량 기준을 두어 억제한다.
- **규격이 조용히 어긋난다.** `check_plan_format.py`를 두어 사람 눈이 아니라 스크립트가 판별하게 한다.

## 구현 순서

- [ ] **1. 저장소 및 플러그인 골격** — git 초기화, `.claude-plugin/plugin.json`, `README.md`, `CLAUDE.md`(커밋 규칙과 계획서 경로 규칙), `.gitignore`를 만든다. 완료 판정: `plugin.json`이 유효한 JSON이고 `name`이 kebab-case다.
- [ ] **2. 계획서 규격과 양식 작성** — `shared/`에 `plan-format.md`, `plan-template.md`, `check_plan_format.py`를 만든다. 완료 판정: 이 계획서 자체를 검사 스크립트에 넣어 통과한다.
- [ ] **3. `create-plan` 골격 생성** — frontmatter(name, description 초안)와 섹션 목차만 넣는다. 완료 판정: 플러그인 로드 시 스킬 목록에 이름이 보인다.
- [ ] **4. 섹션 기준 문서 작성** — `references/sections.md`에 섹션별 작성 기준, 통과 조건, 분량 기준, 기각한 대안을 남기는 방식을 적는다.
- [ ] **5. 진행 방식 문서 작성** — `references/facilitation.md`에 역할 분담, 3단계 개입, 축약 요청 처리, 상황별 질문 예시를 적는다.
- [ ] **6. `create-plan` 본문 작성** — 사용자가 직접 설계해야 하는 이유 → 진행 절차 → 참조 파일 연결 순으로 쓴다. 완료 판정: 본문 200줄 안팎, 참조 파일마다 읽어야 할 시점이 명시돼 있다.
- [ ] **7. 구현 규칙 문서 작성** — `implement/references/execution.md`에 진행 절차, 커밋 단위, 커밋 메시지 규칙 탐색 절차, 진행률 갱신, 계획 결함 시 복귀 절차를 적는다.
- [ ] **8. `implement` 스킬 작성** — 골격과 본문을 함께 만든다. 완료 판정: 상태가 '계획 확정'이 아닌 문서를 주면 진행하지 않고 알린다.
- [ ] **9. 검증 규칙 문서 작성** — `verify/references/verification.md`에 시나리오 실행, 변경 내역 대조, 증거 제시 방식, 되돌림 조건을 적는다.
- [ ] **10. `verify` 스킬 작성** — 골격과 본문을 함께 만든다. 완료 판정: 사용자 승인 없이는 '완료'로 바꾸지 않는다.
- [ ] **11. 플러그인 검증 및 패키징** — 매니페스트에 세 스킬이 잡히는지, `${CLAUDE_PLUGIN_ROOT}` 참조가 해석되는지 확인하고 `.plugin` 파일로 묶는다.
- [ ] **12. 트리거 평가셋 작성 및 description 확정** — 발동해야 할 요청과 발동하면 안 되는 근접 요청을 스킬별로 만들고, 측정 결과로 세 description을 고친다.
- [ ] **13. 실제 과제 리허설 및 보정** — 실제 요구사항 하나로 계획 확정부터 완료까지 돌려 보고, 드러난 문제를 반영한다.

각 항목을 끝낼 때마다 커밋하고 다음으로 넘어간다. 커밋 메시지 형식은 Conventional Commits를 따른다.

## 테스트

### 단위 검증

| 대상 | 확인 내용 |
| --- | --- |
| 항목 1 | `plugin.json`이 유효한 JSON이고 `name`이 kebab-case다 |
| 항목 2 | 규격을 만족하는 문서는 통과하고, 섹션 누락·단계 값 오타·진행률 형식 오류는 각각 걸러진다 |
| 항목 3, 8, 10 | frontmatter가 파싱되고 `name`, `description`이 존재한다 |
| 항목 4, 5, 7, 9 | 각 참조 파일이 해당 SKILL.md에서 참조되고, 끊긴 경로가 없다 |
| 항목 6, 8, 10 | 본문 분량 기준을 지키고, 참조 파일마다 읽어야 할 시점이 명시돼 있다 |
| 항목 11 | 세 스킬이 모두 노출되고 `${CLAUDE_PLUGIN_ROOT}` 경로가 해석된다 |

### 통합 시나리오

항목 6 완료 시점부터 S1~S3을, 항목 8 이후 S4~S6을, 항목 10 이후 S7~S8을 실행할 수 있다.

- **S1 정상 계획 수립** — "로그인 실패 시 재시도 로직을 넣고 싶다" 수준의 요구사항을 준다. 다섯 섹션이 순서대로 채워지는가, AI가 먼저 해법을 확정해 버리지 않는가, 기각한 대안이 남는가.
- **S2 막힘 경로** — 사용자가 "모르겠다"를 반복한다. 질문 → 힌트 → 선택지 순서로 내려가는가, 최종 선택을 사용자가 하는가, 선택 이유가 문서에 남는가.
- **S3 축약 요청** — "그냥 빨리 진행해줘"를 준다. 한 번 짚어 주는가, 초안에 검토 필요 표시를 남기는가, 표시가 남은 채로 '계획 확정'으로 넘어가지 않는가.
- **S4 인계** — '계획 확정' 문서로 `/implement`를 호출한다. 항목마다 커밋하고 진행률을 갱신하는가, 모두 끝나면 '구현 완료'로 바꾸고 멈추는가, '완료'를 스스로 표시하지 않는가.
- **S5 계획 결함** — 구현 중 전제가 틀린 상황을 만든다. 구현 순서를 임의로 고치지 않고 멈추는가, 상태를 '계획 확정'으로 되돌리고 보고하는가.
- **S6 규격 위반 문서** — 상태 표가 깨진 계획서를 `/implement`에 준다. 추측해서 진행하지 않고 어긋난 지점을 알리는가.
- **S7 검증 통과** — '구현 완료' 문서로 `/verify`를 호출한다. 시나리오 실행 결과와 변경 요약을 제시하는가, 사용자 승인 전에 '완료'로 바꾸지 않는가.
- **S8 검증 미달** — 시나리오 하나가 실패하도록 만든다. 상태를 '구현 중'으로 되돌리는가, 남은 작업을 특정하는가.
- **S9 규칙 부재** — 커밋 규칙과 문서 경로 규칙이 없는 저장소에서 실행한다. 임의로 정하지 않고 사용자에게 묻는가.

### 트리거 테스트

항목 12에서 스킬별로 발동해야 할 요청과 발동하면 안 되는 근접 요청을 만들어 각각 여러 차례 실행하고 발동률을 본다. 세 스킬이 서로를 잠식하는지가 핵심이므로, 오탐 후보는 어휘가 겹치는 것들로 고른다.

- 계획서 없이 "이거 구현해줘" → `implement`가 아니라 `create-plan`
- "계획서대로 진행해줘" → `create-plan`이 아니라 `implement`
- "테스트 돌려봐" → `verify`가 아니라 일반 처리
- "다음 스프린트 계획 좀 잡아줘", "이번 주 작업 계획" → `create-plan`이 아니라 일반 처리
- 단순 버그 수정, 코드 리뷰 요청 → 셋 다 발동하지 않음

### e2e

항목 13에서 실제 저장소의 요구사항 하나를 접수부터 '완료' 표시까지 통과시킨다. 합격 기준은 문서가 만들어졌는지가 아니라, 작업에 참여하지 않은 사람이 계획서만 읽고 무엇이 왜 바뀌었는지 설명할 수 있는지다.

### 회귀

스킬을 수정할 때마다 S1, S2, S4를 다시 돌린다. 이 셋이 각각 사용자 주도, 개입 제한, 상태 전환이라는 핵심 성질을 지킨다.
