# 학습 진행

## 목적과 문제

사용자가 과제를 받고, 막히면 힌트를 얻고, 완성하면 피드백을 받는 동작을 어느 스킬이 맡는지 정합니다. 동작의 경계가 모호하면 요청하지 않은 힌트나 정답이 응답에 섞이고, 사용자가 들여야 할 노력이 줄어듭니다.

## 요구사항과 품질 속성

| 요구사항 | 판정 기준 |
| --- | --- |
| 동작마다 스킬 하나 | 과제 생성·힌트·피드백이 각각 다른 스킬에서만 일어난다 |
| 요청한 동작만 수행 | `hint`를 부르지 않은 응답에 힌트가 없다 |
| 정답 코드 미제공 | 어느 스킬의 응답에도 과제를 완성하는 코드가 없다 |
| 과제 중복 방지(R3) | 같은 디렉터리에서 같은 기술로 낸 과제의 만들 대상이 서로 겹치지 않는다 |

## 개념 모델

| 개념 | 뜻 |
| --- | --- |
| 과제 | 만들 대상과 완성 조건을 적은 구현 과제 하나 |
| 과제 정보 | 과제 폴더에 기록한 기술·만들 대상·완성 조건 |

## 책임과 경계

| 스킬 | 맡는 일 | 요구사항 |
| --- | --- | --- |
| `study [기술]` | 배울 범위 구체화와 겹치지 않는 과제·의존성 설명 제시 | R1, R2, R3, R4 |
| `hint` | 과제 폴더의 과제에 대한 정답 코드 없는 힌트 제시 | R5 |
| `review` | 과제 폴더의 완성 조건 충족 여부와 고칠 곳 제시 | R6 |

과제 폴더를 만들고 의존성을 설치하는 방식은 [학습 작업 공간](learning-workspace.md)이 정합니다. 결과에 원칙을 반영하는 방식은 [학습 기조](learning-principles.md)가 정합니다.

## 실행 흐름

1. 사용자가 `study [기술]`을 부르면 배울 범위를 질문으로 구체화합니다.
2. `study`가 현재 디렉터리의 과제 정보를 읽어 같은 기술의 과제를 확인합니다.
3. 겹치지 않는 과제로 과제 폴더를 만들고, 과제와 의존성 설명을 제시합니다.
4. 사용자가 과제 폴더에서 직접 구현하고, 막히면 그 폴더에서 `hint`를 부릅니다.
5. 완성하면 그 폴더에서 `review`를 불러 피드백을 받습니다.
6. 같은 기술로 더 연습하려면 상위 디렉터리에서 `study [기술]`을 다시 부릅니다.

`hint`와 `review`는 과제 정보와 과제 폴더의 코드를 함께 읽습니다. 새 세션에서도 부른 위치만으로 대상 과제가 정해집니다.

## 계약

| 정보 | 보내는 쪽 | 받는 쪽 |
| --- | --- | --- |
| 과제 정보 | `study` | `hint`, `review`, 이후의 `study` |

과제 정보는 과제 폴더 안에만 둡니다(AD-004). 필드 구성은 계획서에서 정합니다.

## 위험과 미해결 질문

| 위험·질문 | 내용 |
| --- | --- |
| 과제 폴더 밖에서의 호출 | 과제 정보가 없는 위치에서 부르면 대상 과제를 정할 수 없음 |
| 하위 폴더에서의 호출 | 과제 폴더의 하위 폴더에서 불렀을 때 과제 폴더를 찾는 방법 미정 |
| 기술 이름의 표기 차이 | `WebRTC Signaling`과 `WebRTC 시그널링`을 같은 기술로 판정하는 방법 미정 |
