# 계획서 규격

이 스킬이 만드는 계획서의 표기 규격이다. 여기가 정본이다.

계획서는 사람이 읽는 문서인 동시에 `implement`와 `verify`가 상태를 판별하는 근거다. 두 스킬은 이 파일을 읽지 않고 각자 자기가 만지는 부분만 전제로 들고 있다. 그래서 아래 표기를 흔들면 그쪽에서 문서를 해석하지 못한다. 형식을 바꿔야 한다면 두 스킬의 본문도 함께 본다.

## 파일 위치

기본 경로는 `docs/plans/YYYY-MM-DD-<주제>.md`다. 대상 프로젝트의 지시사항(`CLAUDE.md`, `AGENTS.md` 등)에 다른 규칙이 있으면 그쪽이 우선한다.

## 섹션 구성

다섯 섹션을 이 문자열, 이 순서로 둔다. 섹션을 추가하거나 이름을 바꾸지 않는다.

```
## 요약
## 상태
## 설계
## 구현 순서
## 테스트
```

문서 맨 위에 `# <제목>` 한 줄을 둘 수 있다. 각 섹션 안의 소제목(`###`)은 자유롭게 쓴다.

## 상태 표

`## 상태` 아래에 이 표를 둔다. 행 순서와 항목 이름은 고정이다.

```
| 항목 | 값 |
| --- | --- |
| 단계 | 계획 확정 |
| 마지막 갱신 | 2026-08-25 |
| 구현 진행률 | 3 / 13 |
```

| 항목 | 허용 값 |
| --- | --- |
| 단계 | `계획 확정`, `구현 중`, `구현 완료`, `완료` 중 하나 |
| 마지막 갱신 | `YYYY-MM-DD` 형식의 실제 날짜 |
| 구현 진행률 | `n / m` — n은 체크된 항목 수, m은 전체 항목 수 |

## 구현 순서 항목

`## 구현 순서` 아래에 체크박스 목록을 둔다. 번호는 1부터 빠짐없이 이어진다.

```
- [ ] **3. `create-plan` 골격 생성** — frontmatter와 섹션 목차를 넣는다. 완료 판정: 스킬 목록에 이름이 보인다.
```

항목을 끝내면 체크를 채우고, 바로 아래에 두 칸 들여쓴 기록 한 줄을 붙인다. 기록은 무엇이 왜 바뀌었는지를 남기는 자리이며, 나중에 `verify`가 사용자에게 보여 준다.

```
- [x] **3. `create-plan` 골격 생성** — frontmatter와 섹션 목차를 넣는다. 완료 판정: 스킬 목록에 이름이 보인다.
  - 기록: description을 코드 변경 범위로 좁혔다. "계획"이라는 말이 일정 계획까지 끌어오기 때문이다.
```

기록 줄은 항목 수에 포함되지 않는다.

## 여러 문서로 나눌 때

나눌지 판단하는 기준은 `sections.md`의 "나눌지 판단하기"에 있다. 여기서는 나누기로 했을 때의 형식만 다룬다.

**새 형식을 만들지 않는다.** 같은 다섯 섹션을 상위와 슬라이스 두 층위에 그대로 쓴다. 형식이 둘이 되면 `implement`와 `verify`가 둘 다 알아야 하는데, 하나로 두면 상위 문서도 그대로 읽힌다.

```
docs/plans/<날짜>-<주제>/
├── README.md          상위
├── 01-<이름>.md       슬라이스
└── 02-<이름>.md
```

파일명의 번호가 순서다. 앞 슬라이스에 의존하면 상위의 항목 설명에 적는다.

### 두 층위의 차이

| 섹션 | 상위 문서 | 슬라이스 문서 |
| --- | --- | --- |
| 요약 | 전체 목표·배경·변경점 | 이 슬라이스의 것 |
| 상태 | 진행률 = 검증까지 끝난 슬라이스 수 | 진행률 = 완료된 구현 항목 수 |
| 설계 | 여러 슬라이스에 걸친 판단만 | 이 슬라이스의 설계 |
| 구현 순서 | 항목 하나 = 슬라이스 문서 하나 | 실제 구현 항목 |
| 테스트 | 슬라이스를 넘나드는 것만 | 이 슬라이스 안에서 끝나는 것 |

상위의 구현 항목은 슬라이스 파일을 가리킨다.

```
- [ ] **2. `create-plan` 스킬** — 계획서를 함께 쓰는 스킬 본체. 슬라이스 1에 의존. → `02-create-plan.md`
```

### 무엇을 어디에 둘 것인가

나누기만 하면 같은 내용이 양쪽에 적히기 쉽다. 상위를 쓸 때 슬라이스에서 요약을 끌어올리는 대신 같은 문단을 다시 쓰게 되기 때문이다.

기준은 하나다. **여러 슬라이스에 걸친 판단만 상위에 둔다.** 한 슬라이스의 산출물 사양은 그 슬라이스가 정본을 갖는다. 같은 판단이 양쪽에 필요하면 상위에는 결론 한 줄, 하위에 근거 전문을 둔다.

| 판단 | 정본 | 반대쪽에 남는 것 |
| --- | --- | --- |
| 전체 구조를 왜 이렇게 잡았는가 | 상위 | 슬라이스는 필요하면 가리킨다 |
| 이 슬라이스의 산출물을 왜 이렇게 만드는가 | 슬라이스 | 상위는 결론 한 줄 |
| 슬라이스를 넘나드는 시나리오 | 상위 | 실행하는 슬라이스가 가리킨다 |
| 한 슬라이스 안에서 끝나는 시나리오 | 슬라이스 | 상위에는 두지 않는다 |

참조는 하위에서 상위 방향으로만 한다. 상위가 하위를 가리키기 시작하면 읽는 사람이 문서 사이를 계속 오가야 한다.

형태가 닮은 것은 중복이 아니다. 같은 종류의 산출물을 만드는 슬라이스들은 구현 항목과 단위 검증 문구가 비슷해진다. 여기서 한쪽을 참조로 바꾸면 슬라이스가 단독으로 읽히지 않는다.

### 선행 표기

상위 문서의 구현 항목에 선행 슬라이스를 적는다. 없으면 생략한다.

```
- [ ] **3. 계획 분할 기능** — create-plan을 확장한다. 선행: 02 → `03-plan-splitting.md`
```

`선행:` 뒤에는 슬라이스 번호를 쉼표로 나열한다. "슬라이스 2에 의존"처럼 문장으로 적으면 형태가 매번 달라져 읽는 쪽이 확인할 수 없다.

### 브랜치

작업은 브랜치로 격리한다.

| 브랜치 | 단위 | 기점 |
| --- | --- | --- |
| `feature/<주제>` | 계획 묶음 하나 | 기본 브랜치 |
| `slice/<주제>/NN-<이름>` | 슬라이스 하나 | `feature/<주제>` |

접두사를 `feature/`와 `slice/`로 나눈 것은 취향이 아니라 제약이다. git은 브랜치를 파일로 저장하므로 `feature/plan-skills`가 있으면 `feature/plan-skills/01-foundation`을 만들 수 없다. 상위 이름이 파일인데 그 아래에 디렉터리를 두려는 꼴이라 거부된다.

계획서를 나누지 않았으면 `feature/<주제>` 하나만 쓰고 slice 브랜치를 만들지 않는다.

**계획서가 커밋되는 위치**

- 계획 묶음 전체 — `feature/<주제>`
- 슬라이스 문서의 상태 변경 — 그 slice 브랜치
- 상위 `README.md` 갱신 — 머지가 끝난 뒤 `feature/<주제>`

상위를 slice 브랜치에서 고치면 슬라이스마다 같은 파일의 같은 자리를 고치게 되어 머지할 때마다 충돌한다.

**커밋 단위** — 코드 변경과 계획서 갱신을 한 커밋에 담는다. 그러면 커밋 하나가 곧 구현 항목 하나이고, 계획서의 체크 상태가 그 브랜치의 커밋 이력과 항상 일치한다. 커밋과 문서 갱신을 나누면 그 사이에 중단됐을 때 "코드는 들어갔는데 체크는 안 된" 상태가 남는다.

여기서 따라오는 성질이 있다. **계획서의 진행 상태는 브랜치에 종속된다.** 같은 계획서를 다른 브랜치에서 열면 다른 상태로 보이는 것이 정상이고, 어긋난 것이 아니다.

### 상위 문서의 갱신

`verify`가 슬라이스를 `완료`로 닫는 시점에만 상위의 체크와 진행률을 고친다. `implement`는 상위를 건드리지 않는다. 검증되지 않은 것이 상위에서 완료로 보이면 전체 진행 상황이 실제보다 앞서 보이기 때문이다.

## 미해결 검토 표시

사용자가 결정하지 않은 채 AI가 초안을 채운 자리에는 `<!-- 사용자 검토 필요 -->`를 남긴다. 이 표시가 하나라도 남아 있으면 단계를 `계획 확정`으로 올릴 수 없다.

## 확인

확정 전에 이 규격과 대조해 표기를 확인한다. `implement`와 `verify`도 받은 문서가 자기 전제를 만족하는지 시작할 때 본다.

검사 스크립트는 두지 않는다. 세 스킬 모두 같은 모델이 읽으므로 표기가 조금 어긋나도 뜻은 통하고, 스크립트를 두면 규격을 바꿀 때마다 따라 고쳐야 하는 데다 오탐이 진짜 문제를 가린다. 정작 위험한 쪽은 형식이 멀쩡한데 내용이 비어 있는 경우다. 그건 어차피 스크립트로 잡히지 않는다.

기계적으로 어긋나기 쉬운 지점은 하나다. **진행률과 체크된 항목 수의 일치.** 그래서 항목을 체크하는 동작과 진행률을 고치는 동작을 한 동작으로 묶어 두고, `verify`가 시작할 때 다시 대조한다.

빈 양식 `assets/plan-template.md`는 값 자리에 자리표시자가 들어 있다. 양식이지 문서가 아니므로 그대로 둔다.
