# 검증 규칙

## 판정하지 않는다

이 스킬은 통과 여부를 스스로 선언하지 않는다. 실행 결과와 실제 변경 내역을 증거로 내놓고, 판정은 사용자가 한다.

구현한 쪽과 검증하는 쪽을 나눈 이유가 여기 있다. 같은 자리에서 "다 됐습니다"라고 말하면 검증이 형식만 남는다. "테스트가 모두 통과했으니 완료로 바꾸겠습니다"는 이 스킬이 할 말이 아니다. "네 개 중 세 개가 통과했고 하나는 이렇게 실패했습니다. 어떻게 하시겠습니까"가 할 말이다.

## 받는 문서의 전제

| 확인 | 어긋났을 때 |
| --- | --- |
| 단계가 `구현 완료` | `계획 확정`·`구현 중`이면 구현이 남았다고 알린다. `완료`면 이미 닫힌 문서라고 알린다 |
| 모든 구현 항목이 체크돼 있다 | 체크되지 않은 항목을 짚는다 |
| 진행률이 체크된 수와 맞다 | 어느 쪽이 맞는지 사용자에게 확인한다. 임의로 고치지 않는다 |
| `## 테스트`에 시나리오가 있다 | 무엇으로 검증할지 사용자에게 묻는다 |

## 시나리오 실행

`## 테스트`의 항목을 위에서부터 하나씩 실행한다.

- 자동으로 돌릴 수 있는 것은 돌리고 출력을 그대로 보여 준다. 요약해서 "통과"라고만 쓰지 않는다.
- 사람이 봐야 하는 것은 무엇을 어떻게 확인하면 되는지 알려 주고 사용자의 판단을 받는다.
- 실행할 수 없는 것은 왜 못 하는지 적는다. 조용히 건너뛰지 않는다.

결과는 시나리오 이름과 함께 목록으로 정리한다. 어느 것이 확인됐고 어느 것이 남았는지 한눈에 보여야 한다.

## 변경 내역 대조

계획서의 `## 요약`에 적힌 변경점과 실제로 들어간 변경을 맞춰 본다.

- 계획서에 적혔는데 실제로 없는 것. 빠뜨렸거나 계획이 바뀌었는데 문서에 반영되지 않았다.
- 실제로 있는데 계획서에 없는 것. 범위가 넘쳤다는 뜻이므로, 구현 항목에 없던 변경이 들어갔다면 짚는다.

차이를 발견하면 어느 쪽이 맞는지 사용자에게 묻는다. 문서를 실제에 맞춰 고치는 것은 사용자가 정할 일이다.

## 변경 요약

**이 스킬에서 가장 중요한 산출물이다.** 계획서를 쓴 목적이 "구현 후 사용자가 변경점을 이해할 수 있게 하는 것"이었고, 그것이 실현되는 자리가 여기다.

각 구현 항목의 기록 줄과 실제 변경을 이어 붙여 읽을 수 있는 형태로 만든다.

```
3. auth/session.py에 만료 검사 추가
   왜: 재시도 중에 세션이 끊기면 조용히 실패하던 문제. 기록에 적힌 대로 만료를 먼저 보는 쪽으로 갔다.
   무엇이: session.py에 is_expired()가 생기고, retry() 진입부에서 이걸 먼저 본다.
   영향: 만료된 세션으로 들어오면 이제 예외 대신 재로그인 안내가 나간다.
```

diff를 그대로 붙이지 않는다. 사용자가 diff를 읽을 수 있었다면 이 단계가 필요 없었다. 무엇이 바뀌었는지보다 **왜 그렇게 됐고 무엇이 달라지는지**를 쓴다.

항목이 많으면 묶어서 정리하되, 사용자가 "이건 왜 이렇게 했지"라고 물을 만한 항목은 따로 세운다.

## 승인

시나리오 결과와 변경 요약을 보여 준 뒤 사용자에게 묻는다. 승인을 받으면 단계를 `완료`로 바꾼다.

**승인 없이 `완료`로 바꾸지 않는다.** 사용자가 답하지 않았거나 "일단 알겠다" 정도로 넘어갔으면 아직 승인이 아니다. 이 표시는 사용자의 책임이 걸리는 자리다.

## 머지

계획서가 슬라이스 문서이고 `slice/<주제>/NN-<이름>` 브랜치에서 작업했다면, 닫는 시점에 `feature/<주제>`로 머지한다.

**순서가 중요하다.**

1. slice 브랜치에서 슬라이스 문서의 단계를 `완료`로 바꾸고 커밋한다.
2. `feature/<주제>`로 옮겨 slice 브랜치를 `--no-ff`로 머지한다.
3. 머지가 끝난 뒤 `feature`에서 상위 `README.md`를 갱신하고 커밋한다.

상위 갱신을 3번으로 미루는 이유는 충돌 때문이다. 슬라이스마다 상위의 같은 파일, 같은 표를 고치므로 slice 브랜치에서 고치면 머지할 때마다 부딪힌다. 머지 후 feature에서 한 번만 고치면 부딪힐 일이 없다.

`--no-ff`를 쓰는 것은 슬라이스 단위가 이력에 남아야 나중에 어디까지 검증됐는지 볼 수 있기 때문이다.

**하지 않는 것**

- 승인 전 머지. 사용자가 `완료`를 승인하지 않았으면 머지도 하지 않는다.
- `feature` → 기본 브랜치 머지. PR이나 리뷰 절차를 거치는 저장소가 많고, 그 판단은 사용자 몫이다. 상위 문서까지 `완료`가 되어도 feature는 그대로 남는다. 사용자에게 feature가 준비됐다는 것만 알린다.
- 충돌을 임의로 해결하는 것. 머지가 충돌하면 멈추고 무엇이 부딪혔는지 보여 준다.

계획서를 나누지 않아 `feature/<주제>` 하나만 있었다면 머지할 대상이 없다. 문서를 닫기만 하고 브랜치는 건드리지 않는다.

되돌리는 경우(`구현 중`이나 `계획 확정`으로) 머지하지 않는다. slice 브랜치에 그대로 둔다.

## 상위 문서 갱신

계획서가 디렉터리 안의 슬라이스 문서라면(같은 폴더에 `README.md`가 있고 그 구현 항목이 이 파일을 가리킨다면), 머지가 끝난 뒤 `feature` 브랜치에서 상위를 갱신한다.

1. 상위의 구현 항목 중 이 파일을 가리키는 것을 찾는다.
2. 체크를 채우고 기록 줄을 붙인다. 기록에는 이 슬라이스에서 무엇이 확인됐는지 한 줄을 남긴다.
3. 진행률을 고친다.
4. 모든 슬라이스가 닫혔으면 상위 문서의 단계도 `완료`로 바꿀지 사용자에게 묻는다. 여기서도 스스로 바꾸지 않는다.

상위 문서가 없으면 이 절차를 건너뛴다. 찾다가 멈추지 않는다.

## 되돌림

| 상황 | 처리 |
| --- | --- |
| 시나리오가 실패했거나 빠진 구현이 있다 | 단계를 `구현 중`으로 되돌리고, 해당 항목의 체크를 풀고, 남은 작업을 특정한다 |
| 계획 자체가 틀렸다 | 단계를 `계획 확정`으로 되돌리고 무엇이 어긋났는지 보고한 뒤 계획 스킬로 넘긴다 |

되돌릴 때도 이미 들어간 커밋은 건드리지 않는다. 되돌리는 것은 상태와 체크뿐이다.
