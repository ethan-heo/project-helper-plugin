# create-docs

## 역할과 목적

`create-docs`는 이미 구현이 끝난 결과를 개발 문서로 남긴다. PRD에서 의도를, 계획서에서 결정을, 코드에서 사실을 가져와 세 층 구조의 문서로 정리한다. 사용자는 도메인 이름과 재생성 범위의 결정권자이고, AI는 조사·작성·보고를 맡는다.

## 실행 원칙

**코드를 사실로 삼고, 근거를 찾지 못한 자리는 추측으로 채우지 않는다.**

사용자가 이 스킬을 명시하면 뒤따르는 답변은 기본적으로 문서 작성의 입력으로 해석한다. 질문이 스킬의 개념이나 사용법만 묻는 설명 요청이면 작성을 진행하지 않고 일반 답변을 제공한다.

이 스킬은 구현이 끝난 뒤에 실행한다. 계획서의 상태가 `완료`가 아니면 문서를 만들지 않는다. 도메인 경계는 계획서의 구조를 그대로 따르고 새로 정하지 않는다.

기존 문서가 있으면 전체를 다시 생성한다. 그러므로 덮어쓰기 전에 대상 목록을 사용자에게 보이고 동의를 받는다.

## 참조 문서 규칙

이 문서가 `create-docs`의 실행 지시사항을 정하는 기준 문서다. 작업을 시작할 때 이 문서를 먼저 읽고, 아래 표의 절차에 진입할 때 지정된 참조 문서만 읽는다.

| 문서 유형 | 역할 | 적용 범위 |
| --- | --- | --- |
| `SKILL.md` | 실행 절차와 분기 | `create-docs` 전체 |
| `../_shared/docs-root.md` | 문서 루트 판정 규칙 | 준비와 배치 |
| `references/structure.md` | 보관 경로, 세 층 배치, 도메인 대응 | 준비와 배치 |
| `references/sections.md` | 문서별 필수 항목과 서술 규칙 | 문서를 채울 때 |
| `assets/` | 개발 문서 양식 일곱 편 | 파일을 만들 때 |
| `scripts/validate-docs.sh` | 필수 파일과 절 구성 검증 | 확정 직전 |

참조 문서는 본문에 없는 실행 범위를 추가하지 않는다.

## 작성 절차

### 0. 진입 조건을 확인한다

**대상 계획서를 찾고, 구현이 끝났는지 확인한다.**

| 순서 | 할 일 |
| --- | --- |
| 1 | 계획서 저장 경로에서 대상 계획을 찾는다. 후보가 여럿이면 사용자에게 고르게 한다 |
| 2 | 기능 계획서의 상태 표를 읽는다 |
| 3 | 같은 계획의 PRD를 찾는다 |

| 확인 결과 | 할 일 |
| --- | --- |
| 모든 기능 계획서의 단계가 `완료`이다 | 다음으로 진행한다 |
| 단계가 `계획 완료`인 계획서가 있다 | 문서를 만들지 않고 `/impl-plan`으로 구현을 먼저 마치도록 안내한다 |
| 계획서를 찾지 못한다 | 경로를 사용자에게 확인한다 |
| PRD를 찾지 못한다 | 코드와 계획서만으로 쓰되, 근거에 PRD가 없다는 점을 사용자에게 알린다 |

### 1. 배치를 정한다

**[`structure.md`](references/structure.md)를 읽고 보관 경로와 도메인 디렉터리를 정한다.**

계획서의 도메인 하나가 문서 디렉터리 하나에 대응한다. 도메인 이름이 영문 코드뿐이면 한글 이름을 사용자에게 확인받는다.

| 상황 | 할 일 |
| --- | --- |
| 보관 경로에 기존 문서가 있다 | 덮어쓸 파일 목록을 보이고 동의를 받는다. 동의 전에는 아무것도 쓰지 않는다 |
| 동의를 받지 못한다 | 보관 경로를 다시 확인하거나 작업을 중단한다 |

정한 배치를 사용자에게 보여 확인받은 다음 파일을 만든다.

### 2. 도메인을 순회한다

**[`sections.md`](references/sections.md)를 읽고, 도메인마다 문서 네 편을 차례로 채운다.**

한 도메인 안에서는 `01_도메인_개요.md`, `02_도메인_모델.md`, `03_API_명세.md`, `04_도메인_특화_가이드.md` 순서로 쓴다. 앞 문서에서 정한 용어를 뒤 문서가 그대로 사용한다.

| 순서 | 할 일 |
| --- | --- |
| 1 | 계획서의 해당 도메인 문서와 기능 계획서를 읽는다 |
| 2 | 그 도메인에 해당하는 코드를 읽어 모델·엔드포인트·의존성을 확인한다 |
| 3 | 양식을 복사해 항목을 채운다 |
| 4 | 근거를 찾지 못한 자리에 미확인 주석을 남긴다 |

| 상황 | 할 일 |
| --- | --- |
| 코드와 계획서의 기술이 어긋난다 | 코드를 본문에 쓰고, 어긋난 지점을 따로 모아 둔다 |
| 해당 사항이 없는 절이다 | 절을 지우지 않고 "해당 없음"과 그 이유를 적는다 |
| 계획서에 없는 도메인이 코드에 있다 | 문서를 만들지 않고 발견 사실만 기록한다 |

한 도메인을 끝낼 때마다 무엇을 썼는지 사용자에게 한두 줄로 알린다.

### 3. 상위 두 층을 쓴다

**도메인 문서를 모두 채운 뒤 글로벌 아키텍처 가이드와 공통 인프라 문서를 쓴다.**

도메인 문서에서 반복된 내용을 상위로 올리고, 도메인 문서에는 참조 경로만 남긴다. 도메인 목록과 도메인 간 통신은 도메인 문서가 확정된 뒤에야 정확해지므로 순서를 지킨다.

### 4. 확정한다

**형식 검증과 미해결 정리를 마친 뒤에만 확정한다.**

| 순서 | 할 일 |
| --- | --- |
| 1 | `scripts/validate-docs.sh <보관 경로>`로 필수 파일과 절 구성, 미확인 잔존 여부를 검사한다 |
| 2 | 미확인 주석을 모아 사용자에게 한 번에 묻고, 답변을 반영하거나 "해당 없음"으로 정리한다 |
| 3 | 코드와 계획서가 어긋난 지점을 목록으로 보고한다 |

| 결과 | 할 일 |
| --- | --- |
| 검증이 실패한다 | 확정하지 않고 해당 문서를 고친다 |
| 미확인이 남아 있다 | 확정하지 않는다. 사용자가 초안 상태로 마무리하기를 요청하면 초안임을 문서에 표시한다 |
| 어긋난 지점이 계획의 전제를 흔든다 | 문서를 확정하되 `/create-plan`으로 계획을 고칠 것을 안내한다 |
| 모두 통과한다 | 문서를 확정하고 생성한 파일 목록을 알린다 |

## 경계

- 계획서가 없거나 구현이 끝나지 않았으면 이 스킬이 아니다.
- 요구사항을 정하는 일은 `create-prd`, 구현 방식을 정하는 일은 `create-plan`이다.
- 문서를 쓰는 과정에서 코드를 고치지 않는다. 고칠 곳을 발견하면 알리되 손대지 않는다.
- 계획서에서 수정하는 것은 없다. 이 스킬은 개발 문서만 만든다.
