# plan-create

## 왜 이 스킬이 있는가

계획서를 빨리 완성하는 것이 목적이라면 혼자 쓰는 편이 낫다. 그렇게 만든 계획서로 구현하면 사용자는 코드가 왜 그 모양인지 모르는 채 결과를 받는다. 나중에 고칠 수도, 판단할 수도, 남에게 설명할 수도 없다.

그래서 이 스킬에서 성과는 좋은 계획서가 아니라 **사용자가 스스로 낸 결론이 담긴 계획서**다. 질문이 몇 번 오간 것은 비효율이 아니라 이 작업의 본체다.

자리는 이렇다. 사용자는 저자이자 결정권자, 당신은 검토자이자 기록자다. 조사는 당신이 맡는다. 사용자를 생각하게 만드는 것과 사용자에게 잡일을 미루는 것은 다르다. 관련 파일을 찾고 기존 처리 방식을 읽고 제약을 확인해 재료로 내놓되, 그 재료로 무엇을 만들지는 사용자가 정한다.

시작하기 전에 `references/facilitation.md`의 "역할"과 "3단계 개입"을 읽는다. 이 스킬의 실제 동작은 대부분 그 문서에 있다. 나머지 참조는 필요한 시점에 읽는다. 어느 절을 언제 읽는지는 맨 아래 표에 있다.

## 진행 절차

### 0. 준비

**요구사항과 저장소를 확인한 다음, 빈 양식을 복사해 문서 하나를 만든다.**

| 순서 | 할 일 |
| --- | --- |
| 1 | 요구사항을 확인한다. 무엇을 원하는지 불분명하면 여기서 한 번 좁힌다 |
| 2 | 관련 파일, 기존 처리 방식, 제약을 찾아 둔다. 여기서 해법을 만들지는 않는다 |
| 3 | 프로젝트 지시사항에서 계획서를 둘 경로를 찾는다. 규칙이 없으면 `docs/plans/`를 쓴다 |
| 4 | `assets/plan-template.md`를 복사해 `YYYY-MM-DD-<주제>.md` 하나를 만든다 |

나눌지는 구현 순서가 나온 뒤에 정하므로 여기서는 한 편으로 시작한다.

### 1~6. 섹션 채우기

**위에서부터 순서대로 채우고, 섹션마다 통과 조건을 만족했는지 사용자에게 확인받은 뒤 다음으로 넘어간다.**

| 순서 | 섹션 | 지킬 것 |
| --- | --- | --- |
| 1 | 요약(가제) | 목표와 배경만 쓴다. 변경점은 비워 둔다 |
| 2 | 상태 | 규격대로 자동 생성. 단계 `계획 확정`, 진행률 `0 / 0` |
| 3 | 설계 | 해법과 근거. 기각한 대안과 그 사유까지 |
| 4 | 구현 순서 | 한 항목 = 한 커밋 = 되돌릴 수 있는 최소 단위 |
| 4-1 | (분할 판단) | 나눌지 정하고, 나눈다면 위층부터 쓴다 |
| 5 | 테스트 | 모든 구현 항목이 최소 하나의 검증에 대응 |
| 6 | 요약 확정 | 변경점을 채우고 설계·구현 순서와 대조 |

사용자의 답을 받아 문서에 반영한 형태로 보여 준 뒤 다음으로 넘어간다. 문서가 자라는 것이 보여야 사용자가 자기 판단이 쌓이는 것을 느낀다. 변경점을 마지막에 채우는 이유는 설계와 구현 순서가 나오기 전에는 무엇이 달라지는지 정확히 쓸 수 없기 때문이다.

### 4-1. 나눌지 판단하기

**구현 순서를 채운 다음 한 번 멈추고 나눌지 정한다.**

| 판단 | 할 일 |
| --- | --- |
| 나누지 않는다 | 5번 테스트로 간다 |
| 나눈다 | 도메인과 기능의 경계 안을 사용자에게 보이고, 동의를 받은 뒤 디렉터리 구조로 옮긴다 |

어디서 자를지는 무엇을 먼저 검증하고 싶은지에 달렸고, 그건 사용자가 판단할 몫이다. 옮길 때는 위층부터 쓰고 아래로 내려가며, 위 두 층에는 목록과 여러 문서에 걸친 판단만 남긴다.

### 7. 확정

**아래 넷을 거치고 사용자의 승인을 받은 뒤에만 단계를 `계획 확정`으로 바꾼다.**

| 순서 | 할 일 |
| --- | --- |
| 1 | 규격과 대조해 표기를 확인한다 |
| 2 | 미해결 검토 표시가 남아 있으면 그 자리를 사용자와 정리한다. 하나라도 남으면 확정할 수 없다 |
| 3 | 인계 점검을 한다. 항목마다 "이것만 읽고 무엇을 어디에 할지 정해지는가"를 묻는다 |
| 4 | 구현 진행률의 전체 수를 구현 항목 수로 맞춘다 |

스스로 확정하지 않는다. 이 지점이 사용자의 책임이 실제로 걸리는 자리이기 때문이다. 승인을 받으면 계획서를 커밋하고 `/plan-implement`로 진행한다고 안내한다.

## 경계

- 이미 계획서가 있고 상태가 `계획 확정`이면 이 스킬이 아니라 `/plan-implement`다.
- 상태가 `구현 완료`면 `/plan-verify`다.
- `plan-implement`가 계획의 결함을 발견해 상태를 `계획 확정`으로 되돌린 경우, 이 스킬로 돌아와 해당 부분을 사용자와 다시 설계한다. 이때 요약부터 다시 쓰지 않고 어긋난 곳만 고친다.
