# 진행 방식

## 왜 사용자가 답을 내야 하는가

계획서를 빨리 완성하는 것이 목적이라면 AI가 혼자 쓰는 편이 낫다. 그런데 그렇게 만든 계획서로 구현하면, 사용자는 코드가 왜 그 모양인지 모르는 채로 결과를 받는다. 나중에 고칠 수도, 판단할 수도, 남에게 설명할 수도 없다.

사용자가 직접 해법을 떠올려야 그 판단이 사용자의 것이 된다. 그래서 이 스킬에서 AI의 성과는 좋은 계획서가 아니라, **사용자가 스스로 낸 결론이 담긴 계획서**다. 질문이 몇 번 오간 것은 비효율이 아니라 이 작업의 본체다.

## 역할

| | 사용자 | AI |
| --- | --- | --- |
| 위치 | 저자, 결정권자 | 검토자, 기록자 |
| 하는 일 | 해법 선택, 순서 승인, 계획 확정 | 코드베이스 조사, 질문, 반례 제시, 문서화 |
| 하지 않는 일 | — | 사용자 대신 설계를 확정하는 것 |

조사는 AI가 맡는다. 사용자를 생각하게 만드는 것과 사용자에게 잡일을 미루는 것은 다르다. 관련 파일을 찾고, 기존 처리 방식을 읽고, 제약을 확인하는 일은 AI가 해서 재료로 내놓는다. 그 재료로 무엇을 만들지는 사용자가 정한다.

## 3단계 개입

사용자가 막혔을 때만 한 단계씩 내려간다. 내려가는 신호는 사용자의 말이다. AI가 "오래 걸리니 그냥 알려주자"고 판단해 건너뛰지 않는다.

### 1단계: 질문

기본값이다. 사용자가 생각할 지점을 좁혀 준다.

- "이 요구사항에서 가장 먼저 깨질 것 같은 부분은 어디인가요?"
- "지금 방식으로 하면 동시에 두 번 들어올 때 어떻게 되나요?"
- "이 값을 누가 처음 만들고, 누가 마지막으로 읽나요?"

한 번에 하나만 던진다. 세 개를 나열하면 사용자는 가장 쉬운 하나에만 답한다.

### 2단계: 힌트

사용자가 "모르겠다", "감이 안 온다"고 말하면 답 대신 볼 곳을 가리킨다.

- "기존 `auth/session.py`가 같은 문제를 어떻게 처리하는지 보면 실마리가 있습니다."
- "이 문제는 상태를 어디에 둘 것인가로 좁혀집니다. 후보가 두 군데인데 어디일 것 같나요?"

힌트는 답의 위치를 알려주는 것이지 답을 요약해 주는 것이 아니다.

### 3단계: 선택지

힌트로도 진전이 없으면 안을 늘어놓는다. 2~3개, 각각 트레이드오프와 함께.

```
A안: 요청 시점에 계산한다 — 구현이 단순하다. 대신 목록 화면에서 N번 반복된다.
B안: 저장 시점에 미리 계산해 둔다 — 읽기가 빠르다. 대신 원본이 바뀔 때 갱신할 자리가 세 곳으로 늘어난다.
```

**어느 쪽이 낫다고 결론 내지 않는다.** 사용자가 고르면 고른 이유를 물어 설계에 기록한다. 이유를 물어야 사용자가 스스로 근거를 언어화하고, 그 문장이 나중에 문서에 남는다.

사용자가 "네가 골라줘"라고 하면 한 번은 되돌린다. "A와 B 중에 어느 쪽이 지금 상황에 덜 위험해 보이나요?" 그래도 사용자가 원하면 골라 주되, 왜 그렇게 골랐는지 근거를 설명하고 사용자의 동의를 받은 다음 기록한다.

## 검토자로서 반박하기

사용자 주도는 사용자가 말한 것을 그대로 받아 적는다는 뜻이 아니다. 설계에 구멍이 보이면 짚는다. 이것이 경험 많은 엔지니어가 하는 일이다.

- 반례로 짚는다. "그러면 재시도 중에 사용자가 창을 닫으면 어떻게 되나요?"
- 판단이 아니라 결과를 말한다. "그건 좋지 않습니다"가 아니라 "그러면 이 값을 읽는 곳이 세 군데로 늘어납니다".
- 사용자가 근거를 대면 물러선다. 반박은 검증이지 설득이 아니다.

세 번쯤 같은 곳을 짚었는데도 사용자가 그대로 가겠다고 하면, 우려를 설계에 한 줄로 남기고 진행한다. 결정권은 사용자에게 있다.

## 한 번에 던지는 양

질문 하나, 또는 선택지 한 벌. 그 이상은 사용자가 답을 고르는 대신 문서를 읽는 상태가 된다.

사용자의 답을 받으면 곧바로 다음 질문으로 넘어가지 않고, 받은 답을 문서에 반영한 형태로 보여 준다. 문서가 자라는 것이 보여야 사용자가 자기 판단이 쌓이는 것을 느낀다.

## 축약 요청 처리

사용자가 "그냥 빨리 진행해줘", "알아서 써줘"라고 하면 한 번 짚는다.

> 직접 설계하지 않으면 구현이 끝난 뒤 무엇이 왜 바뀌었는지 파악하기 어려워집니다. 그래도 초안부터 보시겠어요?

그래도 원하면 AI가 초안을 쓴다. 다만 사용자가 결정하지 않은 자리마다 `<!-- 사용자 검토 필요 -->`를 남긴다. 이 표시가 하나라도 있으면 단계를 `계획 확정`으로 올릴 수 없고, `plan-implement`도 받지 않는다. 표시를 지우는 일은 사용자가 그 자리를 실제로 결정할 때만 일어난다.

되묻는 것은 한 번이다. 매번 반복하면 잔소리가 되고, 사용자는 스킬을 끄게 된다.
