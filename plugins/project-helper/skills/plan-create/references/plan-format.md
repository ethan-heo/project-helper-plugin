# 계획서 규격

이 스킬이 만드는 계획서의 표기 규격이다. 여기가 정본이다.

계획서는 사람이 읽는 문서인 동시에 `plan-implement`와 `plan-verify`가 상태를 판별하는 근거다. 두 스킬은 이 파일을 읽지 않고 각자 자기가 만지는 부분만 전제로 들고 있다. 그래서 아래 표기를 흔들면 그쪽에서 문서를 해석하지 못한다. 형식을 바꿔야 한다면 두 스킬의 본문도 함께 본다.

## 파일 위치

기본 경로는 `docs/plans/YYYY-MM-DD-<주제>.md`다. 대상 프로젝트의 지시사항(`CLAUDE.md`, `AGENTS.md` 등)에 다른 규칙이 있으면 그쪽이 우선한다.

## 섹션 구성

다섯 섹션을 이 문자열, 이 순서로 둔다. 섹션을 추가하거나 이름을 바꾸지 않는다.

```
## 요약
## 상태
## 설계
## 구현 순서
## 테스트
```

문서 맨 위에 `# <제목>` 한 줄을 둘 수 있다. 각 섹션 안의 소제목(`###`)은 자유롭게 쓴다.

## 상태 표

`## 상태` 아래에 이 표를 둔다. 행 순서와 항목 이름은 고정이다.

```
| 항목 | 값 |
| --- | --- |
| 단계 | 계획 확정 |
| 마지막 갱신 | 2026-08-25 |
| 구현 진행률 | 3 / 13 |
```

| 항목 | 허용 값 |
| --- | --- |
| 단계 | `계획 확정`, `구현 중`, `구현 완료`, `완료` 중 하나 |
| 마지막 갱신 | `YYYY-MM-DD` 형식의 실제 날짜 |
| 구현 진행률 | `n / m` — n은 체크된 항목 수, m은 전체 항목 수 |

## 구현 순서 항목

`## 구현 순서` 아래에 체크박스 목록을 둔다. 번호는 1부터 빠짐없이 이어진다.

```
- [ ] **AUTH-SESSION-001** 만료 검사 추가 — `auth/session.py`에 `is_expired()`를 만들고 `retry()` 진입부에서 먼저 본다. 완료 판정: 만료된 세션으로 들어오면 재로그인 안내가 나간다.
```

**ID는 도메인-기능-번호로 쓴다.** 도메인은 대상 파일이 속한 디렉터리나 영역에서 딴다(`AUTH`, `BILL`). 기능은 그 안에서 무엇을 건드리는지다(`SESSION`, `RETRY`). 번호는 세 자리다.

**번호는 도메인-기능 조합 안에서 센다.** 문서 전체를 관통하는 일련번호도, 도메인 단위 번호도 아니다. 앞의 두 조각이 같은 항목끼리만 이어 센다.

```
- [ ] **AUTH-SESSION-001** 만료 검사 추가 — ...
- [ ] **AUTH-SESSION-002** 만료 시 재로그인 안내 — ...   ← 같은 조합의 두 번째
- [ ] **AUTH-TOKEN-001** 토큰 갱신 주기 변경 — ...        ← 조합이 다르므로 001
- [ ] **BILL-RETRY-001** 결제 재시도 큐 추가 — ...        ← 역시 001
```

한 조합에 항목이 하나뿐이면 그 ID는 001에서 끝난다. 목록 대부분이 001이어도 이상한 것이 아니다. **번호는 순서가 아니라 그 조합 안에서 몇 번째 항목인가**를 뜻하고, 순서는 목록에 적힌 차례가 나타낸다.

일련번호로 매기면 항목을 중간에 하나 넣을 때 뒤가 전부 밀리고, 이미 커밋 메시지에 적힌 ID가 다른 항목을 가리키게 된다. 조합 안에서 세면 새 항목은 그 조합의 마지막 번호 다음을 받고 나머지는 그대로다.

번호가 002를 넘어가는 조합이 여럿이면 기능을 너무 넓게 잡은 것이다. 반대로 전부 001이면 기능이 곧 항목이라는 뜻이고, 계획서에서는 그쪽이 흔하다.

**도메인-기능 조합은 한 계획 묶음 안에서 겹치지 않게 한다.** 상위 문서와 슬라이스 문서가 같은 조합을 쓰면 어느 쪽 항목인지 구분되지 않는다. 상위는 넓게(`SKILL-CREATE`), 슬라이스는 좁게(`SKILL-PREM`) 잡으면 대개 겹치지 않는다.

일련번호만 쓰면 슬라이스를 넘나들 때 무엇을 가리키는지 알 수 없다. 커밋 메시지나 검증 기록에서 항목 하나를 짚으려면 문서 밖에서도 뜻이 통하는 이름이 필요하다.

도메인이 애매하면 대상 파일의 디렉터리를 쓰고, 그것도 애매하면 계획서 주제를 쓴다.

**상위 문서도 같은 형식을 쓴다.** 상위의 ID는 그 슬라이스가 다루는 영역에서 딴다.

```
- [ ] **SKILL-CREATE-002** `plan-create` 스킬 — 계획서를 함께 쓰는 스킬 본체. 선행: REPO-SETUP-001 → `02-plan-create.md`
```

선행도 ID로 적는다. 한 계획 안에서 상위와 하위가 다른 형식을 쓰면 읽는 쪽이 문서마다 어느 형식인지 먼저 판별해야 한다.

**번호 형식(`- [ ] **3. 제목** — 설명`)은 옛 형식이다.** 새로 만드는 계획서에는 쓰지 않는다. 이미 그 형식으로 쓰인 문서를 만나면 고치지 말고 그대로 진행한다.

항목을 끝내면 체크를 채우고, 바로 아래에 두 칸 들여쓴 기록 한 줄을 붙인다. 기록은 무엇이 왜 바뀌었는지를 남기는 자리이며, 나중에 `plan-verify`가 사용자에게 보여 준다.

```
- [x] **3. `plan-create` 골격 생성** — frontmatter와 섹션 목차를 넣는다. 완료 판정: 스킬 목록에 이름이 보인다.
  - 기록: description을 코드 변경 범위로 좁혔다. "계획"이라는 말이 일정 계획까지 끌어오기 때문이다.
```

기록 줄은 항목 수에 포함되지 않는다.

## 여러 문서로 나눌 때

나눌지 판단하는 기준은 `sections.md`의 "나눌지 판단하기"에 있다. 여기서는 나누기로 했을 때의 형식만 다룬다.

**새 형식을 만들지 않는다.** 같은 다섯 섹션을 상위와 슬라이스 두 층위에 그대로 쓴다. 형식이 둘이 되면 `plan-implement`와 `plan-verify`가 둘 다 알아야 하는데, 하나로 두면 상위 문서도 그대로 읽힌다.

```
docs/plans/<날짜>-<주제>/
├── README.md          상위
├── 01-<이름>.md       슬라이스
└── 02-<이름>.md
```

파일명의 번호가 순서다. 앞 슬라이스에 의존하면 상위의 항목 설명에 적는다.

### 두 층위의 차이

| 섹션 | 상위 문서 | 슬라이스 문서 |
| --- | --- | --- |
| 요약 | 전체 목표·배경·변경점 | 이 슬라이스의 것 |
| 상태 | 진행률 = 검증까지 끝난 슬라이스 수 | 진행률 = 완료된 구현 항목 수 |
| 설계 | 여러 슬라이스에 걸친 판단만 | 이 슬라이스의 설계 |
| 구현 순서 | 항목 하나 = 슬라이스 문서 하나 | 실제 구현 항목 |
| 테스트 | 슬라이스를 넘나드는 것만 | 이 슬라이스 안에서 끝나는 것 |

상위의 구현 항목은 슬라이스 파일을 가리킨다.

```
- [ ] **2. `plan-create` 스킬** — 계획서를 함께 쓰는 스킬 본체. 선행: 01 → `02-plan-create.md`
```

### 무엇을 어디에 둘 것인가

나누기만 하면 같은 내용이 양쪽에 적히기 쉽다. 상위를 쓸 때 슬라이스에서 요약을 끌어올리는 대신 같은 문단을 다시 쓰게 되기 때문이다.

기준은 하나다. **여러 슬라이스에 걸친 판단만 상위에 둔다.** 한 슬라이스의 산출물 사양은 그 슬라이스가 정본을 갖는다. 같은 판단이 양쪽에 필요하면 상위에는 결론 한 줄, 하위에 근거 전문을 둔다.

| 판단 | 정본 | 반대쪽에 남는 것 |
| --- | --- | --- |
| 전체 구조를 왜 이렇게 잡았는가 | 상위 | 슬라이스는 필요하면 가리킨다 |
| 이 슬라이스의 산출물을 왜 이렇게 만드는가 | 슬라이스 | 상위는 결론 한 줄 |
| 슬라이스를 넘나드는 시나리오 | 상위 | 실행하는 슬라이스가 가리킨다 |
| 한 슬라이스 안에서 끝나는 시나리오 | 슬라이스 | 상위에는 두지 않는다 |

참조는 하위에서 상위 방향으로만 한다. 상위가 하위를 가리키기 시작하면 읽는 사람이 문서 사이를 계속 오가야 한다.

형태가 닮은 것은 중복이 아니다. 같은 종류의 산출물을 만드는 슬라이스들은 구현 항목과 단위 검증 문구가 비슷해진다. 여기서 한쪽을 참조로 바꾸면 슬라이스가 단독으로 읽히지 않는다.

### 선행 표기

상위 문서의 구현 항목에 선행 슬라이스를 적는다. 없으면 생략한다.

```
- [ ] **3. 계획 분할 기능** — `plan-create`를 확장한다. 선행: 02 → `03-plan-splitting.md`
```

`선행:` 뒤에는 슬라이스 번호를 쉼표로 나열한다. "슬라이스 2에 의존"처럼 문장으로 적으면 형태가 매번 달라져 읽는 쪽이 확인할 수 없다.

### 브랜치

작업은 브랜치로 격리한다.

| 브랜치 | 단위 | 기점 |
| --- | --- | --- |
| `feature/<주제>` | 계획 묶음 하나 | 기본 브랜치 |
| `slice/<주제>/NN-<이름>` | 슬라이스 하나 | `feature/<주제>` |

접두사를 `feature/`와 `slice/`로 나눈 것은 취향이 아니라 제약이다. git은 브랜치를 파일로 저장하므로 `feature/plan-skills`가 있으면 `feature/plan-skills/01-foundation`을 만들 수 없다. 상위 이름이 파일인데 그 아래에 디렉터리를 두려는 꼴이라 거부된다.

계획서를 나누지 않았으면 `feature/<주제>` 하나만 쓰고 slice 브랜치를 만들지 않는다.

**계획서가 커밋되는 위치**

- 계획 묶음 전체 — `feature/<주제>`
- 슬라이스 문서의 상태 변경 — 그 slice 브랜치
- 상위 `README.md` 갱신 — 머지가 끝난 뒤 `feature/<주제>`

상위를 slice 브랜치에서 고치면 슬라이스마다 같은 파일의 같은 자리를 고치게 되어 머지할 때마다 충돌한다.

**커밋 단위** — 코드 변경과 계획서 갱신을 한 커밋에 담는다. 그러면 커밋 하나가 곧 구현 항목 하나이고, 계획서의 체크 상태가 그 브랜치의 커밋 이력과 항상 일치한다. 커밋과 문서 갱신을 나누면 그 사이에 중단됐을 때 "코드는 들어갔는데 체크는 안 된" 상태가 남는다.

여기서 따라오는 성질이 있다. **계획서의 진행 상태는 브랜치에 종속된다.** 같은 계획서를 다른 브랜치에서 열면 다른 상태로 보이는 것이 정상이고, 어긋난 것이 아니다.

### ID 용어 표

상위 문서에 도메인 코드 사전을 둔다. 설계 섹션 안이나 요약 바로 뒤가 자연스럽다.

```
| 도메인 | 뜻 | 쓰는 곳 |
| --- | --- | --- |
| AUTH | 로그인과 세션 | 슬라이스 2, 4 |
| BILL | 결제와 정산 | 슬라이스 3 |
```

도메인 코드는 계획마다 다르게 정해진다. 한 곳에 모아 두지 않으면 `FMT`가 형식인지 포맷터인지, `REL`이 배포인지 관계인지 알 수 없다. 새 코드를 만들 때마다 이 표에 한 줄을 더한다.

나누지 않은 단일 계획서에서는 코드가 한둘뿐이라 표를 만들지 않아도 된다.

### 상위 문서의 갱신

`plan-verify`가 슬라이스를 `완료`로 닫는 시점에만 상위의 체크와 진행률을 고친다. `plan-implement`는 상위를 건드리지 않는다. 검증되지 않은 것이 상위에서 완료로 보이면 전체 진행 상황이 실제보다 앞서 보이기 때문이다.

## 설계 섹션의 표

### 결정 요약

설계 맨 앞에 둔다. 훑을 사람은 이 표만 보고, 파고들 사람은 아래 산문을 읽는다.

```
| 결정 | 택한 것 | 근거 | 기각한 대안 |
| --- | --- | --- | --- |
| 재시도 상태를 어디에 둘까 | 요청 시점 계산 | 갱신할 자리가 한 곳이다 | 저장 시점 미리 계산 — 원본이 바뀔 때 갱신 자리가 세 곳으로 는다 |
```

한 행이 한 결정이다. 근거는 한 줄로 줄이고, 한 줄로 안 되는 것은 아래 소제목을 만들어 산문으로 쓴다. 표는 무엇이 정해졌는지 보여 주는 자리이지 설명하는 자리가 아니다.

**결정이 한둘뿐이면 표를 만들지 않는다.** 두 줄짜리 표는 산문보다 읽기 나쁘다.

### 예외 상황

설계 안에 둔다. 정상 경로만 적힌 설계는 구현할 때 반드시 막힌다.

```
| 상황 | 처리 |
| --- | --- |
| 재시도 중에 세션이 만료됨 | 재시도를 멈추고 재로그인 안내 |
| 같은 요청이 동시에 두 번 들어옴 | 뒤엣것을 버리고 앞의 결과를 돌려준다 |
| 외부 결제 API가 응답하지 않음 | 30초 후 실패 처리, 재시도 큐에 넣지 않는다 |
```

**최소 세 개를 목표로 한다.** 잘못된 입력, 전제가 깨진 상태, 바깥이 실패하는 경우를 각각 하나씩 생각해 보면 대개 세 개가 나온다.

예외가 없는 계획도 있다. 문서 정리나 이름 변경 같은 것이다. 그때는 "해당 없음"과 그 이유를 적는다. 빈칸으로 두면 생각하지 않은 것인지 없는 것인지 구분되지 않는다.

## 테스트 섹션의 표

통합 시나리오를 표로 쓴다.

```
| ID | 입력 상황 | 기대 동작 | 실행 시점 |
| --- | --- | --- | --- |
| S1 | 비밀번호를 다섯 번 틀린다 | 계정이 30분 잠기고 안내 메일이 나간다 | 003 이후 |
```

한 줄에 입력·기대·시점을 다 넣으면 눈으로 훑기 어렵다. 열을 나누면 어느 시나리오가 아직 못 도는지 한눈에 보인다.

**실행 시점**은 그 시나리오를 돌릴 수 있게 되는 구현 항목의 ID다. 기능이 실제로 동작하기 전에는 돌릴 수 없는 시나리오가 대부분이다.

시나리오가 한둘뿐이면 표 대신 목록을 쓴다. 단위 검증과 e2e는 지금처럼 표와 산문을 그대로 쓴다.

## 형식이 섞이지 않게 한다

기존 계획서를 이어서 작업할 때는 그 문서의 형식을 따른다. 한 문서 안에서 어떤 항목은 ID가 있고 어떤 항목은 번호만 있으면 읽는 쪽이 판별할 수 없다.

## 미해결 검토 표시

사용자가 결정하지 않은 채 AI가 초안을 채운 자리에는 `<!-- 사용자 검토 필요 -->`를 남긴다. 이 표시가 하나라도 남아 있으면 단계를 `계획 확정`으로 올릴 수 없다.

## 확인

확정 전에 이 규격과 대조해 표기를 확인한다. `plan-implement`와 `plan-verify`도 받은 문서가 자기 전제를 만족하는지 시작할 때 본다.

검사 스크립트는 두지 않는다. 세 스킬 모두 같은 모델이 읽으므로 표기가 조금 어긋나도 뜻은 통하고, 스크립트를 두면 규격을 바꿀 때마다 따라 고쳐야 하는 데다 오탐이 진짜 문제를 가린다. 정작 위험한 쪽은 형식이 멀쩡한데 내용이 비어 있는 경우다. 그건 어차피 스크립트로 잡히지 않는다.

기계적으로 어긋나기 쉬운 지점은 하나다. **진행률과 체크된 항목 수의 일치.** 그래서 항목을 체크하는 동작과 진행률을 고치는 동작을 한 동작으로 묶어 두고, `plan-verify`가 시작할 때 다시 대조한다.

빈 양식 `assets/plan-template.md`는 값 자리에 자리표시자가 들어 있다. 양식이지 문서가 아니므로 그대로 둔다.
