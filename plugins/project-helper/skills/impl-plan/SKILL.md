# impl-plan

## 문서 권한과 읽기 순서

이 문서가 `impl-plan`의 실행 지시사항 정본이다. 작업을 시작할 때 이 문서를 먼저 읽고, 아래 표의 절차에 진입할 때 지정된 참조 문서만 읽는다.

| 문서 유형 | 역할 | 적용 범위 |
| --- | --- | --- |
| `AGENTS.md` | 저장소 전체 규칙 | 이 문서보다 우선 |
| `SKILL.md` | 실행 절차와 분기 | `impl-plan` 전체 |
| `references/` | 근거·예외·세부 판정 | 본문이 지정한 절차 |
| `scripts/` | 계획서 형식 검증 | 구현 시작 전 |
| 계획서 | 구현 범위와 확정된 결정 | 이 스킬의 입력 |

참조 문서는 본문에 없는 실행 범위를 추가하지 않는다. `impl-plan`은 `create-plan`의 `SKILL.md`나 참조 문서를 실행 중 읽지 않으며, 계획서가 확정 상태·구조·항목 형식을 갖췄다는 전제만 사용한다. 계획서 자체의 설계가 틀렸으면 이 문서에서 고치지 않고 `create-plan`으로 돌려보낸다.

## 무엇을 하는 스킬인가

확정된 계획서를 받아 구현 순서를 하나씩 실행한다. 계획을 세울 때는 사용자가 주도한다. 구현 단계에서는 AI가 실행을 주도한다.

구현 범위는 계획서 안에 둔다. 이 원칙을 지켜야 계획서가 결정의 기록으로 남는다.

계획서를 구현에 맞춰 고치면 문서가 결정의 기록이 아니라 결과의 요약이 된다. 사용자는 무엇이 왜 바뀌었는지 되짚기 어려워진다.

계획의 전제가 틀렸다면 구현을 멈춘다. 계획서를 고치지 않고 `create-plan`으로 돌려보낸다.

판단이 필요한 자리마다 `references/execution.md`의 해당 절을 읽는다. 어느 절을 언제 읽는지는 맨 아래 표에 있다. 이 참조 문서는 실행 근거와 예외 처리를 제공하며, 구현 범위를 넓히는 별도 지시서가 아니다.

## 절차

### 0. 이어서 하는 경우라면

**중단했던 작업으로 돌아왔다면, 작업 트리가 깨끗한지 확인하고 현재 브랜치로 이어서 할 자리를 잡는다.**

| 현재 브랜치 | 이어서 할 것 |
| --- | --- |
| `<도메인>/<기능>` | 계획서 저장 경로에서 해당 기능 계획서를 찾아 이어서 한다. 여럿이면 사용자에게 묻는다 |
| `feature/<주제>` | 그 계획에서 기능 계획서를 찾아 상태가 `구현 중`인 것부터 이어서 한다 |
| 그 외 | 프로젝트 지시사항에 정한 계획서 저장 경로에서 후보를 찾아 사용자에게 고르게 한다 |

작업 트리에 변경이 있으면 멈추고 남은 변경을 보여 준다. 이어서 실행할 계획서를 한 줄로 알린 뒤 1번으로 간다. 계획서 상태가 이미 `구현 중`이면 5번은 건너뛴다.

최상위 문서나 도메인 문서를 받았을 때도 같은 절차를 따른다. 해당 문서의 기능 목록에서 상태가 `구현 중`인 계획서를 찾는다. 진입할 계획서를 알린 뒤 시작한다.

### 1. 전제를 확인한다

**계획서를 열어 아래 넷을 보고, 하나라도 어긋나면 진행하지 않고 그 지점을 사용자에게 짚는다.**

| 볼 것 | 통과 조건 |
| --- | --- |
| 단계 | 상태 표가 `계획 확정`이다 |
| 검토 표시 | `<!-- 사용자 검토 필요 -->`가 없다 |
| 항목 표기 | `- [ ] **DOMAIN-FEATURE-001** 제목 — 설명`이다 |
| 항목 내용 | 항목만 읽고 무엇을 어디에 할지 정해진다 |
| 문서 구조 | `docs/plans/YYYY-MM-DD-주제/<도메인>/<기능>.md`인 기능 계획서이며 최상위·도메인 README가 함께 있다 |

단일 초안이나 날짜 디렉터리 바로 아래의 계획서를 발견하면 구현을 시작하지 않고 `create-plan`의 구조 이전 절차로 돌려보낸다.

구현을 시작하기 전에 `scripts/validate-plan.sh <기능 계획서>`를 실행해 정식 구조와 확정 상태와 항목 형식을 다시 검사한다.

계획서를 지정받지 못했으면 프로젝트 지시사항에 정한 계획서 저장 경로에서 찾고, 후보가 여럿이면 사용자에게 묻는다. 무엇을 할지 정해지지 않는 항목은 시작 전에 모아서 한 번에 짚는다.

### 2. 선행을 확인한다

**최상위 문서의 선행 관계 표에서 이 계획서의 대상 ID를 찾고, 연결된 선행 ID가 닫혔는지 읽어서 확인한다. 쓰지는 않는다.**

| 선행 상태 | 할 일 |
| --- | --- |
| 선행 기능 계획서의 해당 항목이 체크됨 | 진행한다 |
| 항목은 미체크지만 선행 기능 계획서가 `완료` | 검증 전이라는 점을 알리고 사용자가 정한다 |
| 선행 계획서가 없거나 상태가 `계획 확정`이 아님 | 멈추고 어느 것이 먼저인지 알린다 |

**선행 ID는 다른 도메인을 가리킬 수 있다.** 세 조각 ID의 앞 두 조각으로 기능 계획서를 찾아 해당 구현 항목을 확인한다.

선행 관계를 커밋 규칙과 브랜치보다 먼저 확인한다. 선행 관계가 닫히지 않으면 뒤 단계의 구현을 시작할 수 없기 때문이다.

### 3. 커밋 규칙을 확인한다

**프로젝트 지시사항에서 찾고, 없으면 최근 커밋 열 개로 형식을 추정해 사용자에게 확인받는다.**

임의로 정하지 않는다. 커밋 메시지는 나중에 통째로 고치기 어렵다.

### 4. 브랜치를 준비한다

**`feature/<주제>`가 없으면 기본 브랜치에서 만들고, 계획서를 시작할 때 거기서 `<도메인>/<기능>`을 딴다.**

브랜치 이름은 계획 디렉터리 아래 경로에서 `.md`를 뺀 값이다. 예를 들어 `fmt/split.md`의 브랜치 이름은 `fmt/split`이다.

계획 구조가 단일 문서라면 `feature/<주제>` 브랜치를 사용한다. 머지는 검증 단계에서 수행한다.

### 5. 단계를 `구현 중`으로 바꾼다

**단계와 마지막 갱신을 같은 동작으로 고친다.**

### 6. 항목을 하나씩 끝낸다

**체크되지 않은 첫 항목부터, 아래 넷을 한 묶음으로 반복한다.**

| 순서 | 할 일 |
| --- | --- |
| 1 | 항목에 적힌 범위만 구현한다 |
| 2 | `## 테스트`에서 이 항목에 대응하는 검증을 찾아 통과시킨다 |
| 3 | 체크박스·진행률·마지막 갱신을 고치고 `- 기록:` 줄을 붙인다 |
| 4 | 코드 변경만 커밋한다. 계획서 갱신은 로컬에 남긴다 |

커밋 메시지에는 항목 ID를 넣는다. 항목이 끝날 때마다 변경 내용을 사용자에게 한두 줄로 알린다. 그래야 사용자가 진행 상황을 따라갈 수 있다.

### 7. 계획이 틀렸으면 멈춘다

**설계의 전제가 바뀌는 사실을 발견하면 진행을 멈추고 단계를 `계획 확정`으로 되돌린 뒤 넘긴다.**

| 발견한 것 | 할 일 |
| --- | --- |
| 설계의 전제가 바뀐다 | 멈추고 `계획 확정`으로 되돌린다. 구현 순서는 고치지 않는다 |
| 전제는 그대로인 오차 — 함수 이름이 계획서와 다른 정도 | 그대로 진행하고 기록 줄에 적는다 |

사소해 보여도 전제가 바뀌면 멈춘다.

### 8. 끝냈으면 넘긴다

**모든 항목이 체크되면 단계를 `완료`로 바꾸고 마지막 갱신을 고친다.**

이 스킬은 여기서 종료한다. 별도의 검증 스킬이나 후속 명령을 전제로 하지 않으며, 구현 결과의 추가 검토가 필요하면 사용자의 별도 요청으로 진행한다.

## 하지 않는 것

| 하지 않는 것 | 누가 하나 |
| --- | --- |
| 계획서 수정 | 고치는 것은 상태 표와 체크박스와 기록 줄뿐이다 |
| 범위 확장 | 눈에 띈 다른 문제는 알리되 고치지 않는다 |

## 경계

- 계획서가 없으면 이 스킬이 아니다. 계획서를 먼저 만들어야 한다.

## 참조 파일

참조 문서는 실행 단계별로 필요한 파일만 읽는다.

| 실행 단계 | 참조 파일 | 읽는 목적 |
| --- | --- |
| 재개·준비 | `preparation/resume.md`, `preparation/prerequisites.md`, `preparation/branch.md` | 작업 상태와 전제 확인 |
| 항목 실행 | `execution/item.md`, `execution/commit.md`, `execution/progress.md` | 구현·검증·기록 |
| 선행·형식 검증 | `validation/plan-format.md`, `validation/dependency.md`, `validation/test.md` | 진행 가능 여부 확인 |
| 실패·중단 | `failure/ambiguity.md`, `failure/plan-defect.md`, `failure/interruption.md` | 예외 처리 |
