# impl-plan

## 무엇을 하는 스킬인가

확정된 계획서를 받아 구현 순서를 하나씩 실행한다. 계획을 세울 때는 사용자가 주도했고, 여기서는 당신이 주도한다. 대신 **계획서를 벗어나지 않아야** 이 스킬이 성립한다.

계획서를 구현에 맞춰 고치기 시작하면 문서가 결정의 기록이 아니라 결과의 요약이 된다. 그러면 사용자가 나중에 무엇이 왜 그렇게 됐는지 되짚을 근거가 사라지고, 계획서를 쓴 이유가 없어진다. 그래서 계획이 틀렸다는 것이 드러나면 고치는 것이 아니라 멈추고 돌려보낸다.

판단이 필요한 자리마다 `references/execution.md`의 해당 절을 읽는다. 어느 절을 언제 읽는지는 맨 아래 표에 있다.

## 절차

### 0. 이어서 하는 경우라면

**중단했던 작업으로 돌아왔다면, 작업 트리가 깨끗한지 확인하고 현재 브랜치로 이어서 할 자리를 잡는다.**

| 현재 브랜치 | 이어서 할 것 |
| --- | --- |
| `<도메인>/<기능>-<번호>` | `docs/plans/*/<도메인>/<기능>/<기능>-<번호>.md`를 찾아 그 계획서를 이어서 한다. 여럿이면 사용자에게 묻는다 |
| `feature/<주제>` | 그 계획에서 위층부터 내려가 체크되지 않은 첫 계획서를 고른다 |
| 그 외 | `docs/plans/`에서 후보를 찾아 사용자에게 고르게 한다 |

작업 트리가 더러우면 멈추고 무엇이 남았는지 보여 준다. 무엇을 이어서 하는지 한 줄로 알린 뒤 1번으로 간다. 이미 `구현 중`이면 5번은 건너뛴다.

최상위나 도메인 문서를 받았을 때도 같다. 그 문서의 항목은 아래층 문서를 가리키므로, 체크되지 않은 첫 항목을 따라 계획서에 닿을 때까지 내려간다. 어느 계획서로 들어갔는지 알린 뒤 시작한다.

### 1. 전제를 확인한다

**계획서를 열어 아래 넷을 보고, 하나라도 어긋나면 진행하지 않고 그 지점을 사용자에게 짚는다.**

| 볼 것 | 통과 조건 |
| --- | --- |
| 단계 | 상태 표가 `계획 확정`이다 |
| 검토 표시 | `<!-- 사용자 검토 필요 -->`가 없다 |
| 항목 표기 | `- [ ] **DOMAIN-FEATURE-001** 제목 — 설명`이다. 옛 문서의 `- [ ] **n. 제목** — 설명`도 그대로 받는다 |
| 항목 내용 | 항목만 읽고 무엇을 어디에 할지 정해진다 |

계획서를 지정받지 못했으면 `docs/plans/`에서 찾고, 후보가 여럿이면 사용자에게 묻는다. 무엇을 할지 정해지지 않는 항목은 만날 때마다 묻지 말고 시작 전에 모아서 한 번에 짚는다.

### 2. 선행을 확인한다

**도메인 문서에서 이 계획서를 가리키는 항목을 찾고, 그 `선행:` ID가 닫혔는지 읽어서 확인한다. 쓰지는 않는다.**

| 선행 상태 | 할 일 |
| --- | --- |
| 그 항목이 체크됨 | 진행한다 |
| 미체크지만 그 계획서가 `구현 완료` | 검증 전이라는 점을 알리고 사용자가 정한다 |
| 그 외 | 멈추고 어느 것이 먼저인지 알린다 |
| 위층 문서 없음 | 건너뛴다 |

**선행 ID는 도메인을 넘어갈 수 있다.** ID가 곧 경로이므로 앞 조각으로 찾아간다. `SKILL-CREATE`는 `skill/README.md`의 항목이고, 도메인 코드 하나뿐인 `SKILL`은 최상위 `README.md`의 항목이다.

커밋 규칙이나 브랜치보다 먼저 보는 이유는 여기서 막히면 뒤 단계가 전부 헛일이 되기 때문이다.

### 3. 커밋 규칙을 확인한다

**프로젝트 지시사항에서 찾고, 없으면 최근 커밋 열 개로 형식을 추정해 사용자에게 확인받는다.**

임의로 정하지 않는다. 커밋 메시지는 나중에 통째로 고치기 어렵다.

### 4. 브랜치를 준비한다

**`feature/<주제>`가 없으면 기본 브랜치에서 만들고, 계획서를 시작할 때 거기서 `<도메인>/<기능>-<번호>`를 딴다.**

뒤 두 조각은 계획서 경로에서 `.md`를 뺀 것이다. `fmt/split/split-001.md`면 `fmt/split-001`이다. 층 구조가 없는 옛 계획서면 `feature/<주제>` 하나만 쓴다. 머지는 하지 않는다.

### 5. 단계를 `구현 중`으로 바꾼다

**단계와 마지막 갱신을 같은 동작으로 고친다.**

### 6. 항목을 하나씩 끝낸다

**체크되지 않은 첫 항목부터, 아래 넷을 한 묶음으로 반복한다.**

| 순서 | 할 일 |
| --- | --- |
| 1 | 항목에 적힌 범위만 구현한다 |
| 2 | `## 테스트`에서 이 항목에 대응하는 검증을 찾아 통과시킨다 |
| 3 | 체크박스·진행률·마지막 갱신을 고치고 `- 기록:` 줄을 붙인다 |
| 4 | 코드 변경과 계획서 갱신을 **한 커밋**에 담는다 |

커밋 메시지에는 항목 ID를 넣는다. 한 항목이 끝날 때마다 무엇이 바뀌었는지 사용자에게 한두 줄로 알린다. 알리지 않으면 사용자가 변경을 따라올 수 없다.

### 7. 계획이 틀렸으면 멈춘다

**설계의 전제가 바뀌는 사실을 발견하면 진행을 멈추고 단계를 `계획 확정`으로 되돌린 뒤 넘긴다.**

| 발견한 것 | 할 일 |
| --- | --- |
| 설계의 전제가 바뀐다 | 멈추고 `계획 확정`으로 되돌린다. 구현 순서는 고치지 않는다 |
| 전제는 그대로인 오차 — 함수 이름이 계획서와 다른 정도 | 그대로 진행하고 기록 줄에 적는다 |

사소해 보여도 전제가 바뀌면 멈춘다.

### 8. 끝냈으면 넘긴다

**모든 항목이 체크되면 단계를 `구현 완료`로 바꾸고 멈춘 뒤 `/verify-plan`을 안내한다.**

## 하지 않는 것

| 하지 않는 것 | 누가 하나 |
| --- | --- |
| `완료` 표시 | `verify-plan`. 구현한 쪽이 합격 판정까지 내리면 검증이 형식만 남는다 |
| 위층 문서 갱신 | `verify-plan`. 도메인 문서도 최상위도 읽기만 한다 |
| 머지 | feature로 올리는 것은 `verify-plan`, 기본 브랜치로 보내는 것은 사용자 |
| 계획서 수정 | 고치는 것은 상태 표와 체크박스와 기록 줄뿐이다 |
| 범위 확장 | 눈에 띈 다른 문제는 알리되 고치지 않는다 |

## 경계

- 계획서가 없으면 이 스킬이 아니다. 계획서를 먼저 만들어야 한다.
- 단계가 `구현 완료`나 `완료`면 `/verify-plan`다.

## 참조 파일

`references/execution.md`의 절을 필요한 시점에 읽는다.

| 읽을 부분 | 읽는 시점 |
| --- | --- |
| 중단했다가 돌아왔을 때 | 0번. 체크 상태와 커밋 이력이 어긋나 보일 때 |
| 받는 문서의 전제 / 항목 표기 두 가지 / 모호한 항목 | 1번. 어긋난 것을 찾았거나 항목이 모호할 때 |
| 선행 확인 | 2번. 선행이 닫히지 않았을 때 |
| 커밋 메시지 규칙 찾기 | 3번. 프로젝트 지시사항에 규칙이 없을 때 |
| 브랜치 | 4번. 브랜치를 처음 만들 때 |
| 한 커밋에 담는 이유 / 기록 줄 | 6번. 첫 항목을 시작하기 전에 한 번 |
| 계획의 결함 | 7번. 전제가 흔들릴 때 |
