# create-architecture

## 역할과 목적

여러 계획이 함께 따를 결정을 사용자와 정하고 프로젝트마다 하나의 아키텍처 문서를 갱신합니다.

## 실행 원칙

**해법을 먼저 확정하지 말고 목표·요구사항·가설을 구분한 뒤 결정 하나씩 사용자와 확정합니다.**

구조 결정은 둘 이상의 구현 계획에 영향을 주거나, 구성 요소 사이의 책임이나 계약을 바꾸는 결정입니다. 산출물은 `<루트>/architecture/`이며 질문마다 새 디렉터리를 만들지 않습니다. 작성할 때는 [공유 표기 기준](../_shared/writing-style.md)을 따릅니다.

## 실행 절차

| 순서 | 단계 | 할 일 |
| --- | --- | --- |
| 0 | 준비 | 문서 루트 판정과 기존 문서 확인 |
| 1 | 현재 구조 기록 | 시스템 전체 조사와 1.0 확정 |
| 2 | 문제 재정의 | 목표·요구사항·가설 분리와 확인 |
| 3 | 결정 목록 합의 | 필요한 결정과 우선순위 합의 |
| 4 | 결정 확정 | 질문·사례·대안·선택·영역 갱신 |
| 5 | 시나리오 대조 | 실제 요청 두세 개로 실행 흐름 대조 |
| 6 | 확정 | 검증·버전 반영·사용자 확인 후 커밋 |

### 0. 준비

**문서 루트를 판정하고 아키텍처 문서 유무를 확인합니다.**

| 선행 상태 | 할 일 |
| --- | --- |
| 문서가 없고 코드가 있다 | 1단계 진입 |
| 문서와 코드가 모두 없다 | 2단계 진입 |
| 문서가 있다 | 색인·결정 기록·관련 영역 확인 후 2단계 진입 |
| 같은 경로에 다른 양식이 있다 | 처리 방식 확인 후 진행 |

### 1. 현재 구조 기록

**[조사 규칙](references/survey.md)에 따라 전체 구조를 기록하고 6단계의 확정 절차로 1.0을 만듭니다.**

영역 목록과 결정 기록은 각각 사용자 확인을 받습니다. 1.0 확정 후 2단계로 돌아갑니다. 현재 구조 기록만 요청받았다면 확정 후 종료합니다.

### 2. 문제 재정의

**[판정 기준](references/framing.md)으로 목표·요구사항·가설을 나눠 확인합니다.**

가설을 결정 후보로 남깁니다. 목표가 없으면 목표부터 질문하고, 분류와 결정 목록 합의 전에 스키마나 컴포넌트 구성을 제안하지 않습니다.

### 3. 결정 목록 합의

**[질문 규칙](references/questioning.md)에 따라 결정 목록과 우선순위를 사용자와 합의합니다.**

다른 결정의 전제, 되돌리기 어려운 결정, 불확실성이 큰 결정 순서로 검토합니다.

### 4. 결정 확정

**[확정 순서](references/questioning.md)에 따라 한 번에 결정 하나를 다룹니다.**

사용자의 생각을 먼저 듣고 [선행 사례](references/verification.md)를 조사한 뒤 대안을 제시합니다. 선택을 결정 기록과 관련 영역 파일에 반영하고 남은 목록을 재검토합니다.

### 5. 시나리오 대조

**[검증 절차](references/verification.md)에 따라 실제 요청 두세 개의 실행 흐름을 끝까지 확인합니다.**

흐름이 끊기거나 담당 구성 요소가 없으면 확정을 보류하고 해당 결정을 목록에 다시 넣습니다.

### 6. 확정

**[문서 규칙](references/document.md)으로 버전·변경 이력을 반영하고 검증을 통과한 문서만 사용자 확인 후 커밋합니다.**

`scripts/validate-architecture.sh <루트>/architecture`를 실행합니다. 코드가 없는 프로젝트의 첫 확정은 1.0입니다. 사용자가 검토할 수 있도록 바뀐 결정·영역·버전을 제시하며, 커밋에는 아키텍처 디렉터리에서 이번에 바꾼 파일만 포함합니다. 기존에 스테이징된 다른 파일을 포함하지 않습니다.

메시지는 프로젝트 커밋 규칙을 따르고, 규칙이 없으면 `docs: 아키텍처 문서 <버전> 갱신`을 씁니다. `create-plan`에서 이어서 실행했다면 확정 후 그 스킬의 준비 단계로 돌아간다고 알리고 원래 계획 요청을 재개합니다.

## 예외 처리

| 예외 조건 | 할 일 |
| --- | --- |
| 문서의 결정과 코드가 어긋난다 | 코드를 현재 사실로 보고 차이 보고 |
| 검증 스크립트가 실패한다 | 확정 보류 후 실패한 파일 정리 |
| 사용자가 커밋을 거절한다 | 문서 확정 유지와 미커밋 사실 안내 |
| git 저장소가 아니다 | 문서 확정 후 커밋만 생략 |

## 경계

- 코드 변경 한 번의 구현 방식은 `/create-plan`으로 안내합니다.
- 무엇을 왜 만들지 정하는 일은 `/create-prd`로 안내합니다.
- 필드 스키마와 실제 코드 구현은 이 스킬에서 다루지 않습니다.
