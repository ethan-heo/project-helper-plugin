# write-devlog

## 역할과 목적

`write-devlog`는 그날 갱신된 계획서와 PRD를 글감으로 삼아, 사용자가 글을 쓸 때 따라갈 목차를 만든다. 문서를 요약하지 않고, 읽는 사람이 배경과 문제에서 출발해 의사결정과 결과까지 따라올 수 있는 순서로 재구성한다. 글은 사용자가 직접 쓴다. 이 스킬은 무엇을 어떤 순서로 쓸지와 그 재료를 모아 주는 데까지만 관여한다.

## 실행 원칙

**완성된 글을 대신 쓰지 않고, 재료가 없는 자리는 채우지 않고 묻는다.**

제목 후보와 핵심 메시지는 예외로 제안한다. 두 자리가 비면 글의 방향을 따로 정해야 해서 목차를 받은 뜻이 줄기 때문이다. 제안은 사용자가 고르거나 물릴 수 있으며, 절의 본문 문장은 여전히 쓰지 않는다.

사용자가 이 스킬을 명시하면 뒤따르는 답변은 기본적으로 목차 작성의 입력으로 해석한다. 질문이 스킬의 개념이나 사용법만 묻는 설명 요청이면 작성을 진행하지 않고 일반 답변을 제공한다. 작성 입력으로 이어진 실행 맥락은 목차가 저장되거나 사용자가 다른 스킬 또는 일반 질문을 명시할 때까지 유지한다.

근거는 계획서와 PRD 두 가지뿐이다. 코드나 커밋 이력에서 내용을 끌어오지 않는다. 문서에 없는 대목은 추측으로 메우지 않고 사용자에게 물어 채운다.

다른 스킬의 산출물은 읽기만 하고 고치지 않는다. 계획서의 상태 표나 체크박스를 건드리지 않으며 코드도 손대지 않는다. 계획서의 단계가 `계획 완료`든 `완료`든 실행할 수 있다. 그날 무엇을 했는지 기록하는 것이 목적이지 구현이 끝났는지 판정하는 것이 목적이 아니기 때문이다.

## 참조 문서 규칙

이 문서가 `write-devlog`의 실행 지시사항을 정하는 기준 문서다. 작업을 시작할 때 이 문서를 먼저 읽고, 아래 표의 절차에 진입할 때 지정된 참조 문서만 읽는다.

| 문서 유형 | 역할 | 적용 범위 |
| --- | --- | --- |
| `SKILL.md` | 실행 절차와 분기 | `write-devlog` 전체 |
| `../_shared/docs-root.md` | 문서 루트 판정 규칙 | 수집 단계의 경로 결정 |
| `references/collection.md` | 기준일 판정과 글감 수집 | 수집 단계 |
| `references/outline.md` | 흐름 단계와 절 구성, 제목·핵심 메시지 제안 | 목차 작성 단계 |
| `references/questioning.md` | 빈자리를 채우는 질문 | 보충 단계 |
| `assets/outline-template.md` | 목차 양식 | 파일을 만들 때 |

참조 문서는 본문에 없는 실행 범위를 추가하지 않는다.

## 작성 절차

### 1. 글감을 모은다

**기준일을 정하고, 그날 갱신된 계획서와 PRD를 모아 목록을 사용자에게 보인다.**

[`collection.md`](references/collection.md)를 읽고 아래 순서로 진행한다.

| 순서 | 할 일 |
| --- | --- |
| 1 | 기준일을 정한다. 사용자가 날짜를 지정하지 않으면 오늘로 본다 |
| 2 | [`docs-root.md`](../_shared/docs-root.md)로 문서 루트를 판정한다 |
| 3 | `<루트>/plans/`와 `<루트>/prds/`에서 `마지막 갱신` 값이 기준일과 같은 문서를 모은다 |
| 4 | 수집 목록과 제외한 문서를 함께 보이고, 뺄 것과 더할 것을 확인받는다 |

| 수집 결과 | 할 일 |
| --- | --- |
| 한 편 이상 | 다음 단계로 넘어간다 |
| 한 편도 없다 | 목차를 만들지 않고 사실을 알린 뒤 다른 날짜를 지정할지 묻는다 |

### 2. 목차를 짠다

**배경에서 결과까지 이어지는 흐름으로 절을 세운다. 필수 네 단계는 항상 두고, 선택 네 단계는 재료가 있을 때만 세운다.**

[`outline.md`](references/outline.md)를 읽고 아래를 채운다.

| 구분 | 단계 |
| --- | --- |
| 필수 | 배경, 문제 정의, 의사결정, 결과 |
| 선택 | 기획 과정, 시행착오, 회고, 향후 개선 방향 |

절마다 제목과 흐름 단계, 작성 포인트, 재료를 붙인다. 작성 포인트는 짧은 목록으로 적고 글의 주장을 확정하는 문장은 쓰지 않는다. 재료는 판단 하나가 항목 하나이며, 택한 것과 기각한 대안을 한 항목에 함께 두고 앞 절에서 이어받는 것을 재료 앞에 한 줄로 적는다. 기능을 소개하는 절은 세우지 않고, 왜 그렇게 정했는지를 절의 자리에 둔다.

| 상황 | 할 일 |
| --- | --- |
| 글감이 한 갈래다 | 한 편의 목차로 짠다 |
| 글감이 여러 주제로 갈린다 | 몇 갈래로 나눌지 제안하고 사용자가 고르게 한다 |

### 3. 빈자리를 채운다

**계획서에 근거가 없어 비는 자리를 질문해 채우고, 제목 후보와 핵심 메시지를 제안해 확정받는다.**

[`questioning.md`](references/questioning.md)를 읽고 질문을 만든다. 질문은 필수 단계용과 선택 단계용 두 묶음으로 나눠 각각 세 개까지 묻는다. 사용자가 답하지 않기로 한 자리는 추가 확인 항목으로 남긴다.

제목 후보는 방향이 겹치지 않게 두셋을 내고, 핵심 메시지와 무게중심을 함께 제안한다. 사용자가 후보를 모두 물리면 가제 한 줄만 남긴다.

### 4. 저장한다

**목차를 `<루트>/posts/YYYY-MM-DD-<주제>.md`로 남긴다.**

| 상황 | 할 일 |
| --- | --- |
| `posts/`가 없다 | 만들고 `.gitignore`에 등록한다 |
| 같은 날짜의 목차 파일이 이미 있다 | 덮어쓰지 않고 이어 쓸지 새로 만들지 묻는다 |

`assets/outline-template.md`를 복사해 네 부를 모두 채운다.

| 부 | 채울 것 |
| --- | --- |
| 1 | 추천 제목 방향 |
| 2 | 핵심 메시지와 무게중심 |
| 3 | 절마다 제목과 흐름 단계, 작성 포인트, 재료 |
| 4 | 추가로 확인할 항목 |

3부의 절 하나가 블록 하나다. 소제목에 절 번호와 제목과 흐름 단계를 함께 적고, 절 제목만 따로 나열한 목록은 두지 않는다. 첫 절을 뺀 나머지 절에는 재료 앞에 이어받는 것을 한 줄로 둔다.

저장한 뒤 절 목록과 남은 추가 확인 항목을 사용자에게 알린다.

## 경계

- 완성된 글은 쓰지 않는다. 사용자가 요청해도 목차와 재료까지만 제공하고, 본문 집필은 사용자의 몫임을 알린다. 제목 후보와 핵심 메시지만 예외로 제안하며, 이것도 확정은 사용자가 한다.
- 근거를 찾지 못한 내용을 지어내지 않는다. 그 자리는 4부의 추가 확인 항목으로 내린다.
- 구현 결과를 프로젝트 안의 문서로 정리하는 일은 이 스킬이 아니라 `/create-docs`다.
- 요구사항을 정하는 일은 `/create-prd`, 구현 방식을 정하는 일은 `/create-plan`이다.
- 계획서와 PRD, 코드를 고치지 않는다. 이 스킬이 만드는 파일은 `<루트>/posts/` 아래의 목차뿐이다.
