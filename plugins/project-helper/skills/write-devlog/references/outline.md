# 목차 구성

## 목적

계획서에 흩어진 결정을 글의 순서로 배열해, 사용자가 첫 문장부터 바로 쓸 수 있게 한다.

## 핵심 지시

문제 → 결정 → 결과 흐름으로 절을 세우고, 절마다 제목과 할 말, 재료, 열린 질문 네 가지를 채운다.

## 절차 흐름

### 계획서의 자리를 목차의 자리로 옮긴다

| 계획서의 자리 | 목차의 자리 | 옮길 때 살릴 것 |
| --- | --- | --- |
| 요약의 배경 | 문제 | 무엇이 불편했는지, 그대로 두면 무엇이 나빠지는지 |
| 설계의 기각한 대안과 그 사유 | 문제 | 쉬워 보이는 길이 왜 막혔는지 |
| 설계의 결정 요약과 근거 | 결정 | 무엇을 택했고 왜 그것이었는지 |
| 설계의 예외 상황 | 결정 | 어디까지 감당하기로 했는지 |
| 구현 순서의 완료 판정 | 결과 | 무엇을 보고 끝났다고 판단했는지 |
| 테스트의 합격 기준 | 결과 | 어떻게 확인했는지 |
| PRD의 목적과 목표 | 문제 | 애초에 무엇을 이루려 했는지 |

기각한 대안은 글에서 가장 쓸모 있는 재료다. 결정만 남기면 결론의 나열이 되지만, 무엇을 왜 버렸는지가 함께 있으면 읽는 사람이 판단을 따라올 수 있다.

### 절 하나를 채운다

| 요소 | 담을 내용 | 비었을 때 |
| --- | --- | --- |
| 제목 | 그 절이 다루는 것 | 재료를 먼저 모으고 나중에 붙인다 |
| 할 말 | 이 절에서 풀어야 할 내용 한두 줄 | 절을 세울 근거가 없다는 뜻이므로 절을 지운다 |
| 재료 | 근거가 된 계획서의 결정, 구현 항목의 완료 판정, PRD의 목표 | 열린 질문으로 돌린다 |
| 열린 질문 | 계획서에 없어 사용자만 답할 수 있는 대목 | 비워 둔다 |

재료에는 계획서의 파일 경로나 절 이름을 적지 않고 내용을 옮긴다. 계획서는 로컬에만 있고 정리되면 사라지므로, 경로를 남기면 목차가 깨진 참조를 안는다.

구현 항목의 ID도 그대로 옮기지 않는다. `DEVLOG-SKILL-002` 같은 식별자는 저장소 안에서만 뜻이 통하며, 글에서는 무엇을 만들었는지로 바꿔 써야 한다.

### 분량을 정한다

| 글감의 크기 | 절의 수 |
| --- | --- |
| 기능 계획서 한 편 | 세다섯 절 |
| 여러 계획서를 묶는다 | 계획마다 결정을 하나씩 골라 묶고, 절이 여덟을 넘으면 주제를 나눌지 묻는다 |

## 예외 처리

| 예외 조건 | 할 일 |
| --- | --- |
| 결정이 하나뿐이라 흐름이 서지 않는다 | 문제와 결과를 한 절씩만 두고 짧은 글로 잡는다. 억지로 절을 늘리지 않는다 |
| 계획서에 기각한 대안이 없다 | 문제 절을 배경만으로 세우고, 무엇과 견주었는지를 열린 질문으로 남긴다 |
| 구현이 끝나지 않아 결과가 비어 있다 | 결과 절을 "지금까지 확인한 것"으로 잡고 남은 일을 열린 질문으로 돌린다 |
| 글감이 서로 무관한 두 주제다 | 한 편에 섞지 않고 나눌지 사용자에게 묻는다 |

## 근거·예시

계획서는 구현자가 읽는 순서로 쓰여 있어 결정이 설계 절에 몰려 있고 배경은 요약에 한 줄로 남는다. 글은 반대다. 읽는 사람은 문제에 공감한 다음에야 결정을 궁금해한다.

예를 들어 "수집 기준을 파일 수정 시각이 아니라 문서 안의 날짜로 정했다"는 결정은, 계획서에서는 표의 한 행이지만 글에서는 "열어 보기만 해도 그날 작업한 문서로 잡히더라"는 문제 절이 앞에 서야 뜻이 통한다.
