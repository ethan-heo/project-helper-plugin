# 목차 구성

## 목적

계획서와 PRD에 흩어진 결정을 읽는 사람이 따라올 수 있는 순서로 배열해, 사용자가 첫 문장부터 바로 쓸 수 있게 한다.

## 핵심 지시

배경에서 결과까지 이어지는 흐름으로 절을 세우되, 필수 네 단계는 항상 두고 선택 네 단계는 재료가 있을 때만 세운다.

## 절차 흐름

### 흐름 단계를 고른다

| 구분 | 단계 | 세우는 조건 |
| --- | --- | --- |
| 필수 | 배경 | 항상 세운다. 재료가 없으면 절을 두고 그 자리를 추가 확인 항목으로 표시한다 |
| 필수 | 문제 정의 | 항상 세운다 |
| 선택 | 기획 과정 | 우선순위나 범위를 가른 판단이 문서에 있거나 사용자가 답했을 때만 |
| 필수 | 의사결정 | 항상 세운다 |
| 선택 | 시행착오 | 계획과 어긋난 대목을 사용자가 답했을 때만 |
| 필수 | 결과 | 항상 세운다 |
| 선택 | 회고 | 지금 다시 한다면 무엇을 달리할지 사용자가 답했을 때만 |
| 선택 | 향후 개선 방향 | 추후 작업이 문서에 있거나 사용자가 답했을 때만 |

선택 단계는 재료가 없으면 절로 세우지 않고 마지막 부의 추가 확인 항목으로 내린다. 빈 절을 남겨 두면 목차를 받은 사람이 쓸 수 없는 자리를 안고 시작하게 된다.

기능 소개를 절로 세우지 않는다. 무엇을 만들었는지는 결과 절에서 완료 판정으로 다루고, 절의 자리는 왜 그렇게 정했는지에 내준다.

### 계획서와 PRD의 자리를 목차의 자리로 옮긴다

| 문서의 자리 | 목차의 자리 | 옮길 때 살릴 것 |
| --- | --- | --- |
| PRD의 목적과 목표 | 배경 | 애초에 무엇을 이루려 했는지 |
| 요약의 배경 | 문제 정의 | 무엇이 불편했는지, 그대로 두면 무엇이 나빠지는지 |
| PRD의 요구사항 우선순위와 범위 | 기획 과정 | 무엇을 먼저 하기로 했고 무엇을 뒤로 미뤘는지 |
| 설계의 기각한 대안과 그 사유 | 기획 과정 또는 문제 정의 | 쉬워 보이는 길이 왜 막혔는지 |
| 설계의 결정 요약과 근거 | 의사결정 | 무엇을 택했고 왜 그것이었는지 |
| 설계의 예외 상황 | 의사결정 | 어디까지 감당하기로 했는지 |
| 구현 항목의 기록 줄 | 시행착오 | 계획과 실제가 어긋난 대목 |
| 구현 순서의 완료 판정 | 결과 | 무엇을 보고 끝났다고 판단했는지 |
| 테스트의 합격 기준 | 결과 | 어떻게 확인했는지 |
| 계획서의 추후 작업 | 향후 개선 방향 | 남겨 둔 것과 남긴 이유 |

PRD의 목차를 그대로 옮기지 않는다. PRD는 무엇을 만들지 정하는 순서로 쓰여 있고 글은 왜 그렇게 정했는지를 따라가는 순서로 읽힌다. 이 표는 문서의 절 이름이 아니라 그 안의 내용을 옮기는 데 쓴다.

기각한 대안은 글에서 가장 쓸모 있는 재료다. 결정만 남기면 결론의 나열이 되지만, 무엇을 왜 버렸는지가 함께 있으면 읽는 사람이 판단을 따라올 수 있다.

### 절 하나를 채운다

절 하나가 블록 하나다. 소제목에 절 번호와 제목과 흐름 단계를 함께 적고, 그 아래에 작성 포인트와 재료를 둔다.

```
### 3. 되돌리지 않고, 무시하지도 않기 — 의사결정
```

| 요소 | 담을 내용 | 비었을 때 |
| --- | --- | --- |
| 제목 | 그 절이 다루는 것 | 재료를 먼저 모으고 나중에 붙인다 |
| 흐름 단계 | 여덟 단계 중 하나의 이름 | 단계가 정해지지 않았다는 뜻이므로 절을 세우지 않는다 |
| 작성 포인트 | 무엇을 어떤 순서로 풀지, 짧은 항목 두셋 | 절을 세울 근거가 없다는 뜻이므로 선택 단계면 절을 지운다 |
| 재료 | 근거가 된 결정, 완료 판정, PRD의 목표와 우선순위 | 마지막 부의 추가 확인 항목으로 돌린다 |

단계 이름을 절 제목으로 쓰지 않는다. "의사결정"은 글의 제목이 될 수 없으므로, 제목은 그 절이 다루는 내용으로 뽑고 단계는 옆에 병기한다.

절 제목을 따로 나열한 목록은 두지 않는다. 소제목이 목차의 역할을 한다.

### 재료의 인과를 살린다

재료는 판단 단위로 나눈다. 판단 하나가 항목 하나이며, 택한 것과 그 근거와 기각한 대안이 한 항목 안에 함께 있다. 결정 셋이 걸린 절이면 항목도 셋이 된다.

한 항목에 여러 결정을 뭉쳐 넣으면 무엇과 무엇이 대응하는지 읽어 낼 수 없다. 반대로 결정과 대안을 따로 떼면 대립 관계가 사라져, 어느 결정에 걸린 대안인지 되짚어야 한다.

| 이렇게 | 이렇게 말고 |
| --- | --- |
| 연관성은 같은 기능이나 같은 사용자 흐름에 영향을 주는지로 판단한다. 구현 항목이 달라도 동작의 범위로 판단할 수 있기 때문이며, 기존 항목을 직접 변경하는 작업만 연관으로 보면 주변 작업을 놓친다 | 연관성은 같은 기능이나 같은 사용자 흐름으로 판단한다 / 기존 항목을 직접 변경하는 작업만 연관으로 보는 안은 기각했다 |

항목 문장은 무엇 때문에 무엇이 되었는지를 잇는다. 사실만 적으면 목록이 결정의 나열로 남고, 읽는 사람이 인과를 다시 세워야 한다.

| 이렇게 | 이렇게 말고 |
| --- | --- |
| 확정 계획을 고칠 수 없으니 추가 작업이 새 계획서로 나갔고, 그 결과 하나의 기능에 계획서가 여럿 생겼다 | 하나의 기능에 관련 계획서가 여러 개 생길 수 있었다 |
| 완료된 계획에 걸린 추가 작업이 규칙의 가장 약한 자리라 그 상황을 따로 재현해 확인했다 | 완료된 계획과 같은 기능에 영향을 주는 추가 작업도 기존 계획서를 수정한다 |

절 사이의 인과는 재료 앞의 연결 줄이 맡는다. 앞 절의 무엇을 이어받는지 한 줄로 적어, 원인과 결과가 절 경계로 갈려도 재료만 훑을 때 연결이 보이게 한다. 첫 절에는 이어받을 것이 없으므로 연결 줄을 두지 않는다.

재료에는 계획서의 파일 경로나 절 이름을 적지 않고 내용을 옮긴다. 계획서는 로컬에만 있고 정리되면 사라지므로, 경로를 남기면 목차가 깨진 참조를 안는다.

구현 항목의 ID도 그대로 옮기지 않는다. `DEVLOG-OUTLINE-002` 같은 식별자는 저장소 안에서만 뜻이 통하며, 글에서는 무엇을 만들었는지로 바꿔 써야 한다.

### 작성 포인트의 형식

작성 포인트는 문단이 아니라 짧은 목록으로 적는다. 항목마다 무엇을 다룰지와 어떤 순서로 열지까지만 쓰고, 그래서 무엇을 주장하라는 문장은 쓰지 않는다.

| 쓸 수 있는 문장 | 쓸 수 없는 문장 |
| --- | --- |
| 기각한 두 갈래를 먼저 보이고 그 사이에서 정한 기준으로 넘어간다 | 여기서 진짜 문제는 문서 개수가 아니라 결정의 소재가 분산되는 것임을 분명히 한다 |
| 확정 계획의 변경을 제한한 이유를 한 문장으로 짚는다 | 이 제약이 합리적이었다는 데서 출발해야 다음 절의 부작용이 트레이드오프로 읽힌다 |

왼쪽은 무엇을 다룰지를 지시하고, 오른쪽은 글의 주장과 구성을 이미 확정한다. 오른쪽 같은 문장이 들어가면 사용자가 쓸 여지가 그만큼 줄어든다.

### 제목 방향과 핵심 메시지를 낸다

| 요소 | 만드는 방식 |
| --- | --- |
| 제목 후보 | 방향이 겹치지 않게 두셋을 낸다. 하나는 문제를, 하나는 결정을 앞세운다 |
| 핵심 메시지 | 이 글을 다 읽은 사람이 하나만 가져간다면 무엇인지 한두 문장으로 제안한다 |
| 무게중심 | 그 메시지를 떠받치는 절을 하나 지목한다 |

후보와 메시지는 제안이며 확정은 사용자가 한다. 사용자가 고른 것을 그대로 적고, 고르지 않으면 가제 한 줄만 남긴다.

### 분량을 정한다

| 글감의 크기 | 절의 수 |
| --- | --- |
| 기능 계획서 한 편 | 필수 네 절에 선택 한둘 |
| 여러 계획서를 묶는다 | 계획마다 결정을 하나씩 골라 묶고, 절이 여덟을 넘으면 주제를 나눌지 묻는다 |

## 예외 처리

| 예외 조건 | 할 일 |
| --- | --- |
| 선택 단계의 재료가 없고 사용자도 답하지 않는다 | 그 절을 세우지 않고 마지막 부의 추가 확인 항목으로 내린다 |
| 필수 단계의 재료마저 비어 있다 | 절은 그대로 두고 그 자리를 추가 확인 항목으로 표시한다. 임의로 채우지 않는다 |
| 결정이 하나뿐이라 흐름이 서지 않는다 | 필수 네 절만 두고 짧은 글로 잡는다. 억지로 절을 늘리지 않는다 |
| 계획서에 기각한 대안이 없다 | 문제 정의 절을 배경만으로 세우고, 무엇과 견주었는지를 추가 확인 항목으로 남긴다 |
| 구현이 끝나지 않아 결과가 비어 있다 | 결과 절을 "지금까지 확인한 것"으로 잡고 남은 일을 향후 개선 방향으로 돌린다 |
| 사용자가 제목 후보를 모두 물린다 | 가제 한 줄만 남기고 확정은 글을 쓸 때로 미룬다 |
| 글감이 서로 무관한 두 주제다 | 한 편에 섞지 않고 나눌지 사용자에게 묻는다 |

## 근거·예시

계획서는 구현자가 읽는 순서로 쓰여 있어 결정이 설계 절에 몰려 있고 배경은 요약에 한 줄로 남는다. 글은 반대다. 읽는 사람은 배경과 문제에 공감한 다음에야 결정을 궁금해하고, 결정을 이해한 뒤에야 결과를 판단할 수 있다.

예를 들어 "수집 기준을 파일 수정 시각이 아니라 문서 안의 날짜로 정했다"는 결정은, 계획서에서는 표의 한 행이지만 글에서는 "열어 보기만 해도 그날 작업한 문서로 잡히더라"는 문제 절이 앞에 서야 뜻이 통한다.

선택 단계를 조건부로 둔 이유는 재료의 출처가 다르기 때문이다. 배경과 결정은 문서에 남지만 시행착오와 회고는 사용자의 기억에만 있다. 답을 받지 못한 자리를 절로 세워 두면 목차가 아니라 숙제가 된다.
