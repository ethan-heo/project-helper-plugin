# 글감 수집

## 목적

기준일에 손댄 계획서와 PRD만 골라내, 그날의 작업을 벗어난 내용이 글에 섞이지 않게 한다.

## 핵심 지시

문서 안의 `마지막 갱신` 값을 기준으로 수집하고, 값을 읽을 수 없는 문서는 제외한 뒤 그 사실을 목록에 함께 보인다.

## 절차 흐름

### 기준일을 정한다

| 사용자의 요청 | 기준일 |
| --- | --- |
| 날짜를 말하지 않았다 | 오늘 |
| "어제", "지난 금요일"처럼 상대적으로 말했다 | 오늘을 기준으로 환산한 날짜. 환산한 결과를 사용자에게 확인받는다 |
| `YYYY-MM-DD`로 지정했다 | 그 날짜 |
| 기간을 말했다 | 기간의 모든 날짜. 목차는 한 편으로 묶는다 |

### 문서를 훑는다

수집 범위는 `<루트>/plans/`와 `<루트>/prds/` 두 곳이다. 다른 경로는 보지 않는다.

| 대상 | 날짜를 읽는 자리 |
| --- | --- |
| 기능 계획서 | 상태 표의 `\| 마지막 갱신 \| YYYY-MM-DD \|` 행 |
| PRD | 문서 상단의 `**마지막 갱신** — YYYY-MM-DD` 줄 |

계획 최상위 문서와 도메인 문서에는 상태 표가 없다. 이 둘은 수집 대상이 아니며, 기능 계획서가 걸렸을 때 그 계획이 무엇을 이루려 했는지 확인하는 용도로만 읽는다.

### 목록을 확인받는다

목차를 짜기 전에 아래 세 가지를 함께 보인다.

- 수집한 문서와 각 문서의 `마지막 갱신` 값
- 날짜가 어긋나 제외한 문서
- 날짜 값을 읽지 못해 제외한 문서

사용자가 뺄 문서나 더할 문서를 말하면 그대로 반영한다. 사용자가 직접 지정한 문서는 날짜가 기준일과 달라도 포함한다.

### 주제 분류를 뽑는다

목록을 확인받은 뒤, 목차를 짜기 전에 이 글감이 무엇에 관한 이야기인지 분류로 뽑아 보인다.

| 분류의 요소 | 정하는 방식 |
| --- | --- |
| 근거 | 계획서의 목표와 배경, PRD의 목적. 구현 항목의 목록과 파일 경로는 쓰지 않는다 |
| 이름 | 글의 독자가 알아들을 주제어. 구현 항목 ID나 디렉터리 이름은 쓰지 않는다 |
| 개수 | 글감이 갈리는 만큼. 한 갈래면 하나다 |
| 제시 | 분류마다 근거가 된 문서를 함께 붙인다 |

미리 정해 둔 분류 목록은 두지 않는다. 프로젝트마다 다루는 주제가 다르므로, 목록을 두면 맞지 않는 분류에 글감을 끼워 넣게 된다.

분류를 보인 뒤 이 주제로 목차를 만들지 확인받는다. 동의를 받기 전에는 목차 작성으로 넘어가지 않는다.

| 사용자의 답 | 할 일 |
| --- | --- |
| 진행에 동의한다 | 목차 작성으로 넘어간다 |
| 분류를 물린다 | 목차를 만들지 않고 어떤 주제로 볼지 되묻는다. 물린 분류를 그대로 다시 제시하지 않는다 |
| 갈래를 조정한다 | 조정한 갈래를 기준으로 다시 보이고 확인받는다 |

분류가 여러 갈래로 나오면 그 지점이 곧 목차를 나눌 후보다. 갈래마다 근거 문서를 붙여 보이고 몇 편으로 나눌지 한자리에서 함께 묻는다. 같은 판단을 두 번 묻지 않기 위해서다.

## 예외 처리

| 예외 조건 | 할 일 |
| --- | --- |
| 기준일에 갱신된 문서가 하나도 없다 | 목차를 만들지 않고 사실을 알린 뒤 다른 날짜를 지정할지 묻는다 |
| 문서에 `마지막 갱신` 값이 없다 | 수집 대상에서 빼고 제외 목록에 넣는다. 값을 임의로 추정하지 않는다 |
| 날짜 값이 `YYYY-MM-DD` 형식이 아니다 | 같은 방식으로 제외하고 목록에 넣는다 |
| `plans/`나 `prds/` 디렉터리가 없다 | 있는 쪽만 훑고, 없는 경로를 알린다 |
| 수집된 문서가 많아 한 편으로 묶이지 않는다 | 주제를 몇 갈래로 나눌지 제안하고 사용자가 고르게 한다 |
| 같은 날짜의 목차 파일이 이미 있다 | 덮어쓰지 않고 이어 쓸지 새로 만들지 묻는다 |
| 계획서의 목표와 배경이 비어 있다 | 분류를 지어내지 않는다. 그 문서를 근거로 쓸 수 없다고 알린 뒤 사용자에게 주제를 묻는다 |
| 글감이 한 편뿐이라 갈래가 하나다 | 나누는 질문은 하지 않고 분류만 보인 뒤 진행 여부를 확인한다 |
| 사용자가 분류를 물린다 | 목차를 만들지 않고 어떤 주제로 볼지 되묻는다 |
| 수집된 글감이 한 편도 없다 | 분류 판정에 들어가지 않는다. 날짜 재지정 안내가 먼저다 |

## 근거·예시

파일 수정 시각으로 판정하면 열어 보기만 한 문서도 그날 작업한 것으로 잡힌다. 계획서를 참고하려고 여러 편을 열어 본 날이면 수집 목록이 실제 작업과 어긋난다.

분류를 미리 보이는 이유는 판단의 순서 때문이다. 지금까지는 수집 목록만 보고 목차 작성으로 넘어갔으므로, 사용자는 목차를 다 받은 뒤에야 그 글감이 무엇에 관한 이야기인지 알았다. 쓸 만한 주제가 아니라는 판단이 언제나 뒤늦게 왔고, 그때는 이미 목차를 만든 뒤였다.

근거를 함께 붙이는 이유도 같다. 분류만 내놓으면 사용자는 그 판정이 어느 계획서에서 나왔는지 알 수 없어 물릴지 말지를 정할 수 없다.

문서 안의 날짜는 사람이 작업을 마치며 남긴 값이므로 의도가 담겨 있다. 대신 값을 남기지 않은 문서가 생길 수 있는데, 이때 추정으로 메우면 근거 없는 수집이 된다. 제외하고 목록에 드러내면 사용자가 직접 지정해 넣을 수 있다.
