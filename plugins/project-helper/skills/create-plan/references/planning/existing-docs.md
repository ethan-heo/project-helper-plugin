# 기존 문서 조사

## 목적

계획을 세우기 전에 프로젝트에 이미 있는 문서를 읽어 현재 구조와 제약을 파악합니다.

## 핵심 지시

코드를 뒤지기 전에 문서를 먼저 찾아 읽고, 거기서 확인한 사실을 질문과 설계의 재료로 삼습니다.

## 문서를 찾는 순서

문서 루트는 [`docs-root.md`](../../../_shared/docs-root.md)의 탐색 순서로 판정합니다. 이 문서는 확정된 루트 안에서 무엇을 읽을지만 정합니다.

| 순서 | 찾을 곳 | 판정 |
| --- | --- | --- |
| 1 | 프로젝트 지시사항(`CLAUDE.md`, `AGENTS.md`, `README.md`) | 참조하라고 지정된 문서가 있으면 먼저 읽습니다 |
| 2 | `<루트>/architecture/` | 색인·결정 기록·관련 영역 확인 |
| 3 | 확정한 루트의 나머지 마크다운 문서 | 요구사항과 겹치는 문서 확인 |
| 4 | 확정한 루트의 `prds/` | 요구사항의 의도를 담은 PRD 확인 |
| 5 | 아키텍처 외에 읽을 문서가 없음 | 추가 문서 없이 코드 조사 |

아키텍처 문서가 없으면 `create-plan` 본문의 준비 단계에 따라 `create-architecture`를 이어서 실행합니다. 문서가 없는 채로 계획 초안을 작성하지 않습니다.

## 읽는 범위

요구사항이 건드리는 범위에 걸리는 문서만 읽습니다. 넓게 훑기보다 다음 두 가지를 확인하는 데 집중합니다.

| 확인할 것 | 얻는 것 |
| --- | --- |
| 대상 영역의 책임 범위와 용어 | 요구사항이 어디에 속하는지, 무엇을 건드리면 안 되는지 |
| 이미 정해진 구조와 규칙 | 설계가 따라야 할 제약과 기존 컨벤션 |

읽지 않은 영역을 근거로 설계하지 않습니다.

### 아키텍처 문서

**색인에서 영역 목록을 확인한 뒤 결정 기록과 요청에 관련된 영역 파일만 읽습니다.**

관련 영역을 고를 수 없으면 영역 목록을 보여 사용자에게 확인합니다. 문서 전체의 형식은 `create-architecture/scripts/validate-architecture.sh <루트>/architecture`로 검사합니다. 실패하면 문서를 근거로 삼지 않고 `create-architecture`로 정리합니다. 형식 검사는 관련 없는 영역의 내용을 설계 근거로 읽는 절차가 아닙니다.

구조 결정의 범위는 [공통 판단 기준](../../../_shared/architecture.md#구조-결정의-범위)을 따릅니다. 문서에 없는 구조 결정이 필요하면 문서를 먼저 갱신합니다. 계획의 설계와 문서의 결정이 어긋나면 설계 수정과 문서 갱신 중 사용자가 선택하도록 본문의 분기를 따릅니다.

### 선행 실행과 계획 재개

**[create-architecture](../../../create-architecture/SKILL.md)에 원래 계획 요청을 넘기고, 같은 대화에서 문서를 확정한 뒤 계획을 재개합니다.**

| 선행 실행 결과 | 할 일 |
| --- | --- |
| 문서 확정 | 계획 준비 단계에서 문서를 다시 읽고 초안 작성 재개 |
| 사용자가 중단 | 계획 작성도 멈추고 중단 지점 안내 |
| 문서 검증 실패 | `create-architecture`에서 정리한 뒤 계획 재개 |

## 계획서에 반영하는 방식

문서에서 알아낸 내용은 설계 섹션에 확인한 사실로 적습니다. 문서 경로나 절 이름은 남기지 않습니다. 가리키는 문서가 정리되면 계획서가 깨진 참조를 안게 되기 때문입니다.

아키텍처 문서는 인용 규칙의 예외입니다. 고정된 경로와 버전으로 추적하므로, 최상위 문서에 아키텍처 경로와 기준 버전을 남기고 설계에서 결정 ID를 인용합니다. 아키텍처의 결정을 다시 정하지 않으며, 계획 안에서 끝나는 결정만 결정 요약 표에 적습니다.

### 아키텍처 기준 버전 확정

**계획 확정 직전에 아키텍처 색인의 버전을 다시 확인하고, 최상위 문서의 공통 설계에 경로와 기준 버전을 기록합니다.**

계획 작성 도중 문서가 갱신되었으면 변경된 결정과 설계를 대조합니다. 충돌을 해결한 뒤 최신 버전을 기록하며, 기능·도메인 문서에 중복 기록하지 않습니다.

## 예외 처리

| 예외 조건 | 할 일 |
| --- | --- |
| 문서와 코드의 기술이 어긋남 | 코드의 현재 동작과 차이 보고 |
| 문서에 미확인 표시가 남아 있음 | 표시된 내용을 근거로 삼지 않고, 필요하면 사용자에게 질문합니다 |
| 아키텍처 문서가 없음 | 새 스킬로 문서 확정 후 계획 재개 |
| 요구사항이 걸리는 영역을 판단할 수 없음 | 추측하지 않고 사용자에게 대상을 확인합니다 |

코드가 현재 사실이라는 판정으로 아키텍처 결정을 자동 대체하지 않습니다. 차이가 계획의 설계에 영향을 주면 본문의 설계 수정·문서 갱신 분기로 처리합니다.

## 근거·예시

문서는 코드에 드러나지 않는 결정의 이유와 책임 경계를 담고 있습니다. 그것을 먼저 읽어야 요구사항이 어디에 속하는지 판단할 수 있습니다.

다만 문서는 코드보다 늦게 갱신되므로 사실 판정의 기준은 항상 코드입니다.
