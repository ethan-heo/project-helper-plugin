# 기존 문서 조사

## 목적

계획을 세우기 전에 프로젝트의 개발 문서를 읽어 현재 구조와 제약을 파악한다.

## 핵심 지시

코드를 뒤지기 전에 개발 문서를 먼저 찾아 읽고, 거기서 확인한 사실을 질문과 설계의 재료로 삼는다.

## 문서를 찾는 순서

| 순서 | 찾을 곳 | 판정 |
| --- | --- | --- |
| 1 | 프로젝트 지시사항이 지정한 개발 문서 경로 | 지정이 있으면 그 경로를 쓴다 |
| 2 | `docs/글로벌_아키텍처_가이드.md`와 `docs/도메인_문서/` | 둘 다 있으면 `create-docs` 산출물로 판정한다 |
| 3 | 문서 경로의 다른 마크다운 문서 | 위 둘이 없을 때만 요구사항과 겹치는 문서를 찾아 읽는다 |
| 4 | 아무것도 없음 | 코드만 조사했다고 알리고 진행한다 |

## 읽는 범위

`create-docs` 산출물이 있으면 아래 순서로 읽는다.

| 순서 | 대상 | 얻는 것 |
| --- | --- | --- |
| 1 | 글로벌 아키텍처 가이드 | 시스템 구조, 도메인 목록, 기술 스택, 공통 컨벤션 |
| 2 | 요구사항에 걸리는 도메인의 `01_도메인_개요.md` | 그 도메인의 책임 범위, 용어, 비즈니스 규칙 |
| 3 | (필요할 때만) `02_도메인_모델.md`, `03_API_명세.md` | 데이터 구조나 인터페이스를 바꿔야 할 때의 현재 명세 |

어느 도메인이 걸리는지는 글로벌 아키텍처 가이드의 도메인 구성 표에서 판단한다. 판단이 서지 않으면 사용자에게 확인한다.

3번은 요구사항이 그 층을 건드릴 때만 읽는다. 읽지 않은 층을 근거로 설계하지 않는다.

## 계획서에 반영하는 방식

문서에서 알아낸 내용은 설계 섹션에 확인한 사실로 적는다. 문서 경로나 절 이름은 남기지 않는다. 가리키는 문서가 정리되면 계획서가 깨진 참조를 안게 되기 때문이다.

## 예외 처리

| 예외 조건 | 할 일 |
| --- | --- |
| 문서와 코드의 기술이 어긋난다 | 코드를 사실로 삼아 계획하고, 어긋난 지점을 사용자에게 보고한다 |
| 문서에 미확인 표시가 남아 있다 | 그 자리를 근거로 삼지 않고, 필요하면 사용자에게 질문한다 |
| 개발 문서가 없다 | 코드만 조사했다고 알리고 진행한다 |
| 요구사항에 걸리는 도메인을 판단할 수 없다 | 추측하지 않고 사용자에게 대상 도메인을 확인한다 |

## 근거·예시

문서는 코드에 드러나지 않는 결정의 이유와 도메인의 책임 경계를 담고 있다. 그것을 먼저 읽어야 요구사항이 어느 도메인에 속하는지, 무엇을 건드리면 안 되는지 판단할 수 있다.

다만 문서는 코드보다 늦게 갱신되므로 사실 판정의 기준은 항상 코드다.
