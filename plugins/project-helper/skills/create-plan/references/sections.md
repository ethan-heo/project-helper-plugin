# 섹션별 작성 기준

다섯 섹션을 위에서부터 순서대로 채운다. 각 섹션은 아래 통과 조건을 만족해야 다음으로 넘어간다. 조건을 만족했는지는 사용자에게 확인받는다.

읽는 사람은 이 작업에 참여하지 않은 동료라고 가정한다. 내부 약어와 코드명은 첫 등장에서 한 번 풀어쓴다.

## 요약

목표, 배경, 변경점 세 덩어리로 쓴다. 각 한두 문장, 길어도 세 문장이다.

| 부분 | 담는 것 | 담지 않는 것 |
| --- | --- | --- |
| 목표 | 무엇을 이루려 하는가 | 어떻게 만들 것인가 |
| 배경 | 지금 무엇이 문제인가, 왜 지금인가 | 해법 |
| 변경점 | 무엇이 어떻게 달라지는가 | 구현 세부 |

**변경점은 비워 두고 시작한다.** 설계와 구현 순서가 나오기 전에는 정확히 쓸 수 없다. 마지막에 돌아와 채우고, 그때 설계·구현 순서와 어긋나는 곳이 없는지 대조한다.

**통과 조건** — 목표와 배경에 사용자가 동의했다. 배경이 "필요해서"가 아니라 구체적인 문제를 가리킨다.

## 상태

`plan-format.md`의 규격대로 채운다. 처음에는 단계 `계획 확정`, 진행률 `0 / 0`으로 두고, 구현 순서가 확정되면 전체 수를 채운다.

## 설계

가장 중요한 섹션이다. 해법과 그 근거를 담는다.

**맨 앞에 결정 요약 표를 둔다.** 결정 / 택한 것 / 근거 / 기각한 대안 네 열이다. 훑을 사람은 표만 보고 파고들 사람은 아래 산문을 읽는다. 결정이 한둘뿐이면 표를 만들지 않는다. 형식은 `plan-format.md`의 "설계 섹션의 표"에 있다.

**예외 상황을 표로 적는다.** 최소 세 개를 목표로 한다. 잘못된 입력, 전제가 깨진 상태, 바깥의 실패를 각각 하나씩 생각해 보면 대개 세 개가 나온다. 예외가 없는 계획이면 "해당 없음"과 이유를 적는다. 빈칸으로 두지 않는다.

표 아래 산문에 담을 것은 이렇다.

- 코드베이스에서 실제로 확인한 사실. 파일과 함수 이름을 짚는다. "아마 이럴 것이다"는 확인하고 쓰거나 불확실하다고 밝힌다.
- 왜 그 구조인가. 표의 근거 한 줄로 안 되는 것만 여기 쓴다.
- 영향 범위와 제약. 무엇을 건드리지 않기로 했는지도 포함한다.
- **기각한 대안** 중 사유가 길어 표에 안 들어가는 것. 아래 형식을 쓴다.

```
검토했으나 기각: <대안> — <기각 사유>. <되살릴 조건이 있다면>
```

기각 사유가 "복잡해서"나 "안 맞아서"에 그치면 근거로 쓸 수 없다. 무엇이 얼마나 복잡해지는지, 무엇과 어떻게 안 맞는지 적는다.

소제목(`###`)으로 나누되 한 소제목은 한 가지를 설명한다. 소제목 하나가 열 줄을 넘어가면 대체로 두 가지를 섞고 있다.

**통과 조건** — 해법이 하나로 좁혀졌고, 기각한 대안과 그 사유가 적혀 있으며, 근거가 확인된 사실에 닿아 있다. 예외 상황이 적혀 있거나 "해당 없음"과 그 이유가 밝혀져 있다.

## 구현 순서

체크박스 목록이다. 표기는 `plan-format.md`를 따른다.

항목 하나의 기준은 이렇다.

- **한 커밋 단위다.** 되돌리려면 이 항목만 되돌리면 되는 크기.
- **무엇을 어디에까지 적는다.** "인증 처리 개선"은 항목이 아니다. "`auth/session.py`에 만료 검사 추가"가 항목이다.
- **완료 판정 기준이 붙는다.** 무엇을 보면 끝난 줄 아는가. 판정 기준이 안 떠오르면 항목이 아직 모호한 것이다.
- **ID가 붙는다.** 커밋 메시지나 검증 기록에서 항목을 가리키려면 문서 밖에서도 뜻이 통하는 이름이 필요하다. 형식은 `plan-format.md`의 "ID"에 있다.
- **앞 항목에만 의존한다.** 뒤 항목이 되어야 동작하는 항목은 순서가 잘못됐다.

**통과 조건** — 모든 항목이 위 다섯 기준을 만족하고, 사용자가 순서에 동의했다.

## 테스트

구현 항목마다 검증을 짝지운다. 빠진 항목이 있으면 그 항목은 완료를 판정할 방법이 없다는 뜻이다.

- **단위 검증** — 항목별로 무엇을 확인하는가. 코드가 아닌 변경이면 확인 절차로 대체한다.
- **통합 시나리오** — 기능이 실제로 동작하는 시점부터 돌릴 수 있는 것.
- **e2e** — 전체가 이어지는 시나리오와 합격 기준. 합격 기준은 "동작한다"보다 관찰 가능한 것으로 쓴다.

표기는 `plan-format.md`의 "테스트 섹션의 표"를 따른다.

**통과 조건** — 모든 구현 항목이 최소 하나의 검증에 대응된다.

## 도메인과 기능 가르기

구현 순서까지 나온 다음에 한 번 멈추고 경계를 긋는다. 나눌지를 묻는 자리가 아니다. 계획서는 언제나 도메인과 기능으로 갈라 놓으므로, 여기서 정할 것은 **어디서 자르는가** 하나다.

**판단 시점은 설계 다음이다.** 요구사항을 받은 직후에는 자를 근거가 없다. 무엇을 만들지가 보여야 경계가 드러난다.

**기준은 검증 가능성이다.** 후보마다 묻는다. 이것 하나만 만들었을 때 돌려 볼 수 있는 시나리오가 있는가. 없으면 독립된 기능이 아니라 앞뒤에 붙어야 할 부분이다. "파일을 만드는 단계"와 "그 파일을 쓰는 단계"를 가르는 것이 전형적인 잘못된 경계다. 앞의 것만으로는 아무것도 확인할 수 없다.

갈라 낸 조각이 곧 **기능**이고, 기능을 묶는 것이 **도메인**이다. 둘 다 그대로 디렉터리가 되고 ID의 앞 두 조각이 된다. 기능 하나가 계획서 하나다.

**경계를 몇 개 그을지는 구현 항목이 정한다.**

| 상황 | 할 일 |
| --- | --- |
| 독립적으로 검증할 지점이 둘 이상 보인다 | 그 지점마다 기능을 하나씩 둔다 |
| 검증 지점이 하나뿐이다 | 기능 하나로 둔다. 구조는 그대로 세 층이다 |
| 기능이 여럿이고 성격이 갈린다 | 성격이 같은 것끼리 묶어 도메인을 만든다 |
| 기능이 여럿이지만 한 갈래다 | 도메인 하나에 전부 담는다 |

기능 하나짜리 계획이라고 해서 구조를 접지 않는다. 억지로 쪼개지도 않는다. 구현 항목 세 개를 검증 지점도 없이 세 기능으로 흩으면 문서 사이를 오가는 비용만 남는다.

한 기능의 구현 항목이 열 개를 넘으면 경계를 다시 본다. 대개 그 안에 검증 지점이 더 있다.

경계 안을 잡았으면 도메인 이름과 기능 이름을 사용자에게 보이고 동의를 받는다. 어디서 자를지는 무엇을 먼저 검증하고 싶은지에 달렸고, 그건 사용자가 판단할 몫이다. 형식은 `plan-format.md`의 "문서 구조"를 따른다.

## 초안을 구조로 옮기기

경계에 동의를 받았으면 한 편으로 쓰던 초안을 디렉터리로 흩는다. **위층부터 쓰고 아래로 내려간다.**

| 순서 | 할 일 |
| --- | --- |
| 1 | `README.md`에 계획 전체의 요약을 옮기고, 설계에 ID 용어 표와 도메인을 가로지르는 판단만 남긴다. 구현 순서 자리에는 체크박스 없는 도메인 목록을 둔다 |
| 2 | 도메인마다 `<도메인>/README.md`를 만들고 그 도메인 몫의 요약·판단을 옮긴다. 구현 순서 자리에는 체크박스 없는 기능 목록을 둔다 |
| 3 | 기능마다 `<도메인>/<기능>.md`를 만들고 초안의 구현 항목과 그 근거를 옮긴다 |
| 4 | 초안의 구현 항목 ID를 각 계획서의 도메인·기능에 맞춰 다시 매긴다. 번호는 문서마다 001부터 센다 |
| 5 | 초안의 테스트 시나리오를 걸치는 범위에 따라 층별로 나눠 담는다 |

위에서 아래로 쓰는 이유는 아래층 문서가 자기 자리를 알고 있어야 하기 때문이다. 계획서를 먼저 쓰면 그 계획서가 어느 도메인에 속하는지 나중에 정해지고, 그러면 ID를 다시 매기게 된다.

옮기고 나면 초안 파일은 남기지 않는다. 같은 내용이 두 곳에 있으면 어느 쪽이 정본인지 알 수 없다.

## 인계 점검

확정 직전에 문서를 구현자의 눈으로 한 번 읽는다. 구현할 때는 이 문서만 보고 진행한다. 계획을 세우며 오갔지만 문서에 옮겨 적히지 않은 판단은 그 시점에 사라진다. "그건 A로 가되 B는 건드리지 말자" 같은 합의가 설계에 문장으로 남지 않으면, 구현하는 쪽은 그런 결정이 있었다는 사실조차 모른다.

이런 누락은 표기를 대조해서는 잡히지 않는다. 형식은 멀쩡한데 내용만 비어 있기 때문이다. 읽고 판단해야 한다.

구현 항목마다 순서대로 묻는다.

1. 이 항목만 읽고 무엇을 어디에 할지 정해지는가.
2. 정해지지 않는다면, 그 근거가 설계에 적혀 있는가.
3. 설계에도 없다면 그 결정은 대화에만 남아 있다. 문서로 옮긴다.

문서 전체에 대해서도 확인한다.

- 건드리지 않기로 한 것이 적혀 있는가. 하지 않기로 한 결정은 잊히기 쉬운데, 구현할 때 되살아나면 범위가 조용히 넓어진다.
- 사용자가 여러 안 중에 골랐다면 고른 이유가 적혀 있는가. 이유 없이 결론만 있으면 나중에 그 선택을 검토할 수 없다.
- 테스트의 합격 기준이 관찰 가능한 표현인가. "정상 동작한다"는 판정할 수 없다.

빠진 것을 발견하면 사용자에게 확인하고 문서에 옮긴다. 대화에 없던 내용을 기억으로 지어내지 않는다. 확인이 안 되면 사용자에게 묻는다.

## 요약 확정

변경점을 채우고 설계·구현 순서와 대조한다. 세 곳이 서로 다른 이야기를 하고 있으면 문서가 아직 완성되지 않은 것이다.

**통과 조건** — 변경점이 실제 계획과 일치하고, 사용자가 전체를 승인했다. 승인과 함께 단계가 `계획 확정`이 된다. 이 표시는 사용자가 한다.
