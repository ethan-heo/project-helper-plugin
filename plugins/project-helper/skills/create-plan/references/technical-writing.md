# 계획서 문장과 형식

계획서는 구현에 참여하지 않은 사람이 한 번 읽고 다음 행동을 정할 수 있게 쓴다. 문장을 짧게 쓰되, 결정·근거·예외를 생략하지 않는다.

## 문단

**한 문단에는 한 가지 생각만 담는다.**

| 문단의 역할 | 담을 내용 |
| --- | --- |
| 주장 | 문단의 핵심 판단을 첫 문장에 쓴다 |
| 근거 | 다음 문장에 확인한 사실이나 이유를 쓴다 |
| 예외 | 별도의 판단이 필요하면 문단을 나누거나 표로 옮긴다 |

주장과 근거를 멀리 떨어뜨리지 않는다. 서론에서는 목적, 역할, 진행 원칙을 각각 문단으로 나눈다.

## 문장

**주어와 술어를 가깝게 두고, 한 문장에는 하나의 핵심 행동만 쓴다.**

| 어긋난 표현 | 고치는 방향 |
| --- | --- |
| 계획서와 역할과 예외를 한 문장에 나열 | 주제별로 문장을 나눈다 |
| `그것`, `이것`, `그 자리`, `해당 부분` | 가리키는 문서·항목·상태를 직접 쓴다 |
| `무조건`, `항상`, `절대` | 예외가 없는 경우에만 남긴다 |
| `매우`, `극히`, `효과적으로` | 수치나 관찰 가능한 결과로 바꾼다 |
| `~하는 것이 필요하다` | `~한다`처럼 직접 쓴다 |

수식어는 수식 대상 가까이에 둔다. 한 문장이 길어지면 원인과 결과, 정상 경로와 예외를 각각 분리한다.

## 절의 형식

**각 절은 명령, 분기, 근거 순서로 작성한다.**

```markdown
**계획서를 열어 상태를 확인한다.**

| 확인한 상태 | 할 일 |
| --- | --- |
| `계획 확정` | 구현을 시작한다 |
| 그 밖의 상태 | 진행하지 않고 상태를 알린다 |

상태를 먼저 확인해야 잘못된 계획서에 구현을 쌓지 않는다.
```

명령은 한 문장으로 굵게 쓴다. 조건이 둘 이상이면 표로 나눈다. 조건이 하나뿐이면 명령문에 바로 적는다. 근거가 필요하지 않은 절은 근거를 억지로 덧붙이지 않는다.

## 표

**열 이름만 읽어도 표의 판단 기준과 행동을 알 수 있게 쓴다.**

| 열의 역할 | 권장 이름 |
| --- | --- |
| 조건 | `확인한 상태`, `예외 조건`, `검증 지점`, `발견한 전제` |
| 행동 | `할 일` |
| 설명 | `근거`, `기대 결과`, `실행 시점` |

`상황`, `내용`, `기준`, `처리`처럼 역할이 모호한 열 이름은 쓰지 않는다. 행동을 담는 열 이름은 `할 일`로 통일한다.

표는 여러 항목을 비교하거나 분기할 때만 쓴다. 결정이 한두 개뿐이거나 설명이 더 짧으면 산문이나 목록을 사용한다.

## 계획서 섹션

**각 섹션의 목적에 맞는 정보만 담는다.**

| 섹션 | 작성 원칙 |
| --- | --- |
| 요약 | 목표와 배경을 먼저 쓰고, 변경점은 설계와 구현 순서 뒤에 쓴다 |
| 상태 | 허용된 상태와 실제 날짜와 진행률만 쓴다 |
| 설계 | 결정, 근거, 기각한 대안, 예외를 쓴다 |
| 구현 순서 | 무엇을 어디에 바꾸는지와 완료 판정을 쓴다 |
| 테스트 | 입력 상황, 기대 동작, 실행 시점과 관찰 가능한 합격 기준을 쓴다 |

요약·설계·구현 순서가 서로 다른 내용을 말하지 않는지 확정 전에 대조한다. 계획서에 규격 자체를 반복해서 쓰지 않는다.

## 참조와 예시

**참조 시점과 참조 대상을 구체적으로 적는다.**

- `시작할 때 한 번`보다 `0번 절을 실행하기 직전`처럼 쓴다.
- `해당 문서`보다 `최상위 계획서`처럼 문서 이름을 쓴다.
- ID 예시는 실제 규격과 같은 조각 수를 사용한다.
- 템플릿 안내문은 작성자가 바로 행동할 수 있는 짧은 명령형으로 쓴다.

예시는 설명을 대신하지 않는다. 예시가 실제 규칙과 다르면 예시를 먼저 고친다.
