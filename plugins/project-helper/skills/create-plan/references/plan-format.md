# 계획서 규격

이 스킬이 만드는 계획서의 표기 규격이다. 여기가 정본이다.

`impl-plan`과 `verify-plan`은 이 파일을 읽지 않고 각자 자기가 만지는 부분만 전제로 삼는다. 표기를 바꾸면 두 스킬의 본문도 함께 본다.

## 파일 위치

기본 경로는 `docs/plans/`다. 프로젝트 지시사항(`CLAUDE.md`, `AGENTS.md` 등)에 다른 규칙이 있으면 그쪽이 우선한다.

나누지 않으면 `YYYY-MM-DD-<주제>.md` 파일 하나를 둔다. 나누면 "여러 문서로 나눌 때"를 따른다.

## 섹션 구성

다섯 섹션을 이 문자열, 이 순서로 둔다. 섹션을 추가하거나 이름을 바꾸지 않는다.

```
## 요약
## 상태
## 설계
## 구현 순서
## 테스트
```

문서 맨 위에 `# <제목>` 한 줄을 둘 수 있다. 제목에는 사람이 읽을 이름만 쓰고 번호를 넣지 않는다. 각 섹션 안의 소제목은 자유롭게 쓴다.

## 상태 표

`## 상태` 아래에 이 표를 둔다. 행 순서와 항목 이름은 고정이다.

```
| 항목 | 값 |
| --- | --- |
| 단계 | 계획 확정 |
| 마지막 갱신 | 2026-08-25 |
| 구현 진행률 | 3 / 13 |
```

| 항목 | 허용 값 |
| --- | --- |
| 단계 | `계획 확정`, `구현 중`, `구현 완료`, `완료` 중 하나 |
| 마지막 갱신 | `YYYY-MM-DD` 형식의 실제 날짜 |
| 구현 진행률 | `n / m` — n은 체크된 항목 수, m은 전체 항목 수 |

## 구현 항목

`## 구현 순서` 아래에 체크박스 목록을 둔다.

```
- [ ] **AUTH-SESSION-001** 만료 검사 추가 — `auth/session.py`에 `is_expired()`를 만들고 `retry()` 진입부에서 먼저 본다. 완료 판정: 만료된 세션으로 들어오면 재로그인 안내가 나간다.
```

완료된 항목은 체크를 채우고 바로 아래에 두 칸 들여쓴 기록 한 줄을 붙인다. 기록 줄은 항목 수에 포함되지 않는다.

```
- [x] **AUTH-SESSION-001** 만료 검사 추가 — ...
  - 기록: 만료를 재시도 앞에서 보게 했다. 뒤에서 보면 이미 보낸 요청을 되돌려야 한다.
```

### ID

**도메인-기능-번호**로 쓴다. 도메인은 대상이 속한 영역(`AUTH`, `BILL`), 기능은 그 안에서 무엇을 건드리는지(`SESSION`, `RETRY`), 번호는 세 자리다. 도메인이 애매하면 대상 파일의 디렉터리를, 그것도 애매하면 계획서 주제를 쓴다.

**번호는 도메인-기능 조합 안에서 센다.** 앞의 두 조각이 같은 항목끼리만 이어 센다.

```
- [ ] **AUTH-SESSION-001** ...
- [ ] **AUTH-SESSION-002** ...   ← 같은 조합의 두 번째
- [ ] **AUTH-TOKEN-001** ...     ← 조합이 다르므로 001
```

목록 대부분이 001이어도 이상한 것이 아니다. 번호는 순서가 아니라 그 조합 안에서 몇 번째인가를 뜻하고, 순서는 목록에 적힌 차례가 나타낸다. 문서 전체를 관통하는 일련번호로 매기면 항목을 중간에 하나 넣을 때 뒤가 전부 밀리고, 커밋 메시지에 이미 적힌 ID가 다른 항목을 가리키게 된다.

번호가 002를 넘어가는 조합이 여럿이면 기능을 너무 넓게 잡은 것이다.

계획을 나눴으면 도메인과 기능을 따로 정하지 않는다. 폴더와 파일이 정해 준다.

## 여러 문서로 나눌 때

나눌지 판단하는 기준은 `sections.md`의 "나눌지 판단하기"에 있다. 여기서는 나누기로 했을 때의 형식만 다룬다.

**새 형식을 만들지 않는다.** 같은 다섯 섹션을 모든 층에 그대로 쓴다.

```
docs/plans/<날짜>-<주제>/
├── README.md              최상위 (도메인이 둘 이상일 때만)
├── auth/
│   ├── README.md          도메인
│   ├── login/
│   │   └── login-001.md   계획서
│   └── session/
│       └── session-001.md
└── bill/
    ├── README.md
    └── retry/
        └── retry-001.md
```

**ID 조각이 그대로 경로가 된다.** 도메인도 디렉터리, 기능도 디렉터리, 계획서가 파일이다. 경로는 전부 소문자로 쓰고 ID는 본문에서 대문자 그대로 쓴다.

| ID | 경로 |
| --- | --- |
| `AUTH` | `auth/` |
| `AUTH-LOGIN` | `auth/login/` |
| `AUTH-LOGIN-001` | `auth/login/login-001.md` 안의 구현 항목 |

**기능 하나에 계획서 하나다.** 파일 이름은 `<기능>-<번호>.md`이고 번호는 `001`로 시작한다. 기능 디렉터리에 `README.md`를 두지 않는다. 계획서 자체가 그 기능의 문서다.

번호가 `002`로 넘어가는 상황은 두지 않는다. 한 편으로 읽기 어려울 만큼 커졌다면 계획서를 쪼갤 때가 아니라 기능을 둘로 나눌 때다. 번호 자리를 이름에 두는 것은 도메인·기능·번호 세 조각이 경로에서도 그대로 보이게 하기 위해서다.

**도메인이 하나뿐이어도 디렉터리를 만든다.** 대신 최상위 `README.md`는 만들지 않고 도메인 문서가 그 자리를 대신한다. 나중에 도메인이 늘면 최상위만 얹으면 된다.

### 각 층은 한 가지만 한다

| 층 | 문서 | 하는 일 |
| --- | --- | --- |
| 최상위 | `README.md` | 도메인을 나열한다 |
| 도메인 | `auth/README.md` | 그 도메인의 기능을 나열한다 |
| 계획서 | `auth/login/login-001.md` | 그 기능을 어떻게 만들지 적는다 |

위 두 층은 목록과, 아래 여럿을 가로지르는 판단만 담는다. 실제 설계와 구현 항목은 계획서에만 있다. 위층의 설계가 길어지기 시작하면 그 판단이 정말 여러 문서에 걸치는지 다시 본다. 한 문서 안에서 끝나는 것이면 그 문서로 내린다.

층마다 ID 조각이 하나씩 는다.

```
최상위:  - [ ] **AUTH** 로그인과 세션 — 인증 흐름 전반.
도메인:  - [ ] **AUTH-LOGIN** 이메일 로그인 — 로그인 화면과 인증 처리. 선행: BILL-RETRY
계획서:  - [ ] **AUTH-LOGIN-001** 실패 횟수 잠금 — `auth/login.py`에 ... 완료 판정: ...
```

위층 항목에 파일 포인터를 적지 않는다. ID가 곧 경로다.

계획서 하나가 곧 한 도메인-기능 조합이므로, 그 안의 번호는 문서 안에서 1부터 센다.

### 층별로 무엇을 담는가

| 섹션 | 최상위 | 도메인 | 계획서 |
| --- | --- | --- | --- |
| 요약 | 계획 전체 | 이 도메인 | 이 기능 |
| 상태 | 진행률 = 닫힌 도메인 수 | 진행률 = 닫힌 기능 수 | 진행률 = 완료된 구현 항목 수 |
| 설계 | 도메인을 가로지르는 판단, ID 용어 표 | 이 도메인 안을 가로지르는 판단 | 이 기능의 설계 |
| 구현 순서 | 도메인 목록 | 기능 목록 | 실제 구현 항목 |
| 테스트 | 도메인을 넘나드는 것 | 이 도메인 안에서 끝나는 것 | 이 기능 안에서 끝나는 것 |

**여러 문서에 걸친 판단만 위층에 둔다.** 한 문서의 산출물 사양은 그 문서가 정본을 갖는다. 같은 판단이 양쪽에 필요하면 위층에 결론 한 줄, 아래층에 근거 전문을 둔다.

참조는 아래에서 위 방향으로만 한다. 위층이 아래를 가리키면 읽는 사람이 문서 사이를 계속 오가야 한다.

형태가 닮은 것은 중복이 아니다. 같은 종류의 산출물을 만드는 문서들은 구현 항목과 검증 문구가 비슷해진다. 여기서 한쪽을 참조로 바꾸면 그 문서가 단독으로 읽히지 않는다.

### 선행과 참조

구현 항목에 선행을 적는다. 없으면 생략한다. `선행:` 뒤에는 ID를 쉼표로 나열한다. 층을 넘어 다른 도메인의 기능을 가리켜도 된다.

```
- [ ] **AUTH-LOGIN** 이메일 로그인 — 로그인 화면과 인증 처리. 선행: AUTH-SESSION
```

본문에서 다른 문서를 가리킬 때도 ID를 쓴다. 번호나 파일 경로로 가리키지 않는다. 순서는 계획 도중에 바뀌고, 그러면 흩어져 있던 참조가 전부 다른 것을 가리키게 된다.

### ID 용어 표

가장 위층 문서의 설계 안에 도메인 코드 사전을 둔다.

```
| 도메인 | 뜻 |
| --- | --- |
| AUTH | 로그인과 세션 |
| BILL | 결제와 정산 |
```

도메인 코드는 계획마다 다르게 정해진다. 한 곳에 모아 두지 않으면 같은 코드가 문서마다 다르게 설명되고 어느 쪽이 정본인지 알 수 없게 된다.

도메인이 둘 이상이면 최상위 `README.md`, 하나면 그 도메인 문서에 둔다. 아래층에는 만들지 않는다. 새 도메인을 만들면 그 표에 한 줄을 더한다. 어디에 쓰이는지는 적지 않는다. 항목이 늘 때마다 표를 고치게 된다.

나누지 않은 단일 계획서는 그 문서의 설계 안에 둔다. 코드가 한둘뿐이면 만들지 않아도 된다.

## 설계 섹션의 표

### 결정 요약

설계 맨 앞에 둔다. 훑을 사람은 이 표만 보고, 파고들 사람은 아래 산문을 읽는다.

```
| 결정 | 택한 것 | 근거 | 기각한 대안 |
| --- | --- | --- | --- |
| 재시도 상태를 어디에 둘까 | 요청 시점 계산 | 갱신할 자리가 한 곳이다 | 저장 시점 미리 계산 — 원본이 바뀔 때 갱신 자리가 세 곳으로 는다 |
```

한 행이 한 결정이다. 근거는 한 줄로 줄이고, 한 줄로 안 되는 것은 아래 소제목을 만들어 산문으로 쓴다. 표는 무엇이 정해졌는지 보여 주는 자리이지 설명하는 자리가 아니다.

**결정이 한둘뿐이면 표를 만들지 않는다.** 두 줄짜리 표는 산문보다 읽기 나쁘다.

### 예외 상황

설계 안에 둔다. 정상 경로만 적힌 설계는 구현할 때 반드시 막힌다.

```
| 상황 | 처리 |
| --- | --- |
| 재시도 중에 세션이 만료됨 | 재시도를 멈추고 재로그인 안내 |
| 같은 요청이 동시에 두 번 들어옴 | 나중 것을 버리고 앞의 결과를 돌려준다 |
| 외부 결제 API가 응답하지 않음 | 30초 후 실패 처리, 재시도 큐에 넣지 않는다 |
```

**최소 세 개를 목표로 한다.** 잘못된 입력, 전제가 깨진 상태, 바깥이 실패하는 경우를 각각 하나씩 생각해 보면 대개 세 개가 나온다.

예외가 없는 계획도 있다. 그때는 "해당 없음"과 그 이유를 적는다. 빈칸으로 두면 생각하지 않은 것인지 없는 것인지 구분되지 않는다.

## 테스트 섹션의 표

통합 시나리오를 표로 쓴다.

```
| ID | 입력 상황 | 기대 동작 | 실행 시점 |
| --- | --- | --- | --- |
| S1 | 비밀번호를 다섯 번 틀린다 | 계정이 30분 잠기고 안내 메일이 나간다 | AUTH-LOGIN-001 이후 |
```

한 줄에 입력·기대·시점을 다 넣으면 눈으로 훑기 어렵다. **실행 시점**은 그 시나리오를 돌릴 수 있게 되는 구현 항목의 ID다.

시나리오가 한둘뿐이면 표 대신 목록을 쓴다. 단위 검증은 대상과 확인 내용 두 열의 표, e2e는 산문으로 쓴다.

## 미해결 검토 표시

사용자가 결정하지 않은 채 AI가 초안을 채운 자리에는 `<!-- 사용자 검토 필요 -->`를 남긴다. 이 표시가 하나라도 남아 있으면 단계를 `계획 확정`으로 올릴 수 없다.

## 형식이 섞이지 않게 한다

기존 계획서를 이어서 작업할 때는 그 문서의 형식을 따른다. 옛 계획서는 번호 붙은 항목이나 도메인 폴더 없는 구조일 수 있다. 그대로 두고 이어 간다. 한 문서 안에 두 형식이 섞이면 읽는 쪽이 판별할 수 없다.

## 규격을 계획서에 옮겨 적지 않는다

계획서는 이 계획에서 무엇을 왜 그렇게 정했는지를 담는다. 여기 적힌 규칙을 계획서 본문에 다시 쓰지 않는다. 옮겨 적기 쉬운 것들이다.

- ID를 어떻게 짓고 번호를 어디서 세는가
- 층이 몇 개이고 무엇이 폴더이고 무엇이 파일인가
- 각 섹션에 무엇을 담고 무엇을 담지 않는가
- 용어 표를 어느 문서에 두는가

읽는 사람은 계획서에서 이 계획의 내용을 찾는다. 규칙 설명이 섞이면 어디까지가 계획이고 어디부터가 도구 사용법인지 갈리지 않는다. 규칙이 계획서로 복사되면 규격을 고칠 때 따라 고쳐야 할 자리가 계획서 수만큼 늘어난다.

예외는 계획서 규격 자체를 만드는 계획이다. 그때는 규격이 그 계획의 산출물이므로 설계에 적는 것이 맞다. 그 경우에도 "이렇게 정했다"로 적고 "이렇게 써라"로 적지 않는다.

## 확인

확정 전에 이 규격과 대조해 표기를 확인한다.

검사 스크립트는 두지 않는다. 세 스킬 모두 같은 모델이 읽으므로 표기가 조금 어긋나도 뜻은 통하고, 스크립트는 규격을 바꿀 때마다 따라 고쳐야 하는 데다 오탐이 진짜 문제를 가린다. 정작 위험한 "형식은 멀쩡한데 내용이 비어 있는" 경우는 어차피 잡히지 않는다.

기계적으로 어긋나기 쉬운 지점은 하나다. **진행률과 체크된 항목 수의 일치.**
