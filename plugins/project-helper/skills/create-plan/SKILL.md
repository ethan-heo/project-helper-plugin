# create-plan

## 문서 권한과 읽기 순서

이 문서가 `create-plan`의 실행 지시사항 정본이다. 작업을 시작할 때 이 문서를 먼저 읽고, 아래 표의 절차에 진입할 때 지정된 참조 문서만 읽는다.

| 문서 유형 | 역할 | 적용 범위 |
| --- | --- | --- |
| `AGENTS.md` | 저장소 전체 규칙 | 이 문서보다 우선 |
| `SKILL.md` | 실행 절차와 분기 | `create-plan` 전체 |
| `references/` | 근거·예외·세부 판정 | 본문이 지정한 절차 |
| `assets/` | 계획서·색인 템플릿 | 파일을 만들 때 |
| `scripts/` | 계획서 형식 검증 | 확정 직전 |

참조 문서는 본문에 없는 실행 범위를 추가하지 않는다. 공통 계획서 형식은 이 스킬의 참조 문서에 정의되어 있지만, `impl-plan`은 필요한 형식 전제만 자체적으로 선언해 이 문서를 실행 중 참조하지 않는다.

## 왜 이 스킬이 있는가

이 스킬의 목적은 사용자가 구현 계획의 결정을 직접 내리도록 돕는 것이다.

AI가 계획서를 혼자 완성하면 사용자는 코드가 왜 그렇게 바뀌었는지 알기 어렵다. 나중에 결과를 수정하거나 판단하거나 설명하기도 어렵다.

따라서 성과의 기준은 **사용자가 직접 내린 결론이 계획서에 남아 있는가**이다. 질문과 답변은 계획서를 만드는 핵심 과정이다.

사용자는 계획의 저자이자 결정권자다. AI는 검토자이자 기록자다.

AI는 관련 파일과 기존 처리 방식과 제약을 조사한다. 조사 결과를 제시하되, 해법과 선택은 사용자에게 맡긴다.

시작하기 전에 `references/facilitation.md`의 "역할"과 "3단계 개입"을 읽는다. 질문과 대안 제시가 필요한 시점에는 같은 문서의 해당 절을 다시 읽는다. 나머지 참조 파일은 아래 참조 표에 적힌 절을 실행하기 직전에 읽는다.

## 진행 절차

### 0. 준비

**요구사항과 저장소를 확인한 다음, 상태를 `초안 작성 중`으로 둔 빈 양식을 복사한다.**

| 순서 | 할 일 |
| --- | --- |
| 1 | 요구사항을 확인한다. 무엇을 원하는지 불분명하면 여기서 한 번 좁힌다 |
| 2 | 관련 파일, 기존 처리 방식, 제약을 찾아 둔다. 여기서 해법을 만들지는 않는다 |
| 3 | 프로젝트 지시사항에서 계획서를 둘 경로를 찾고, 그 경로가 `.gitignore`에 등록되어 있는지 확인한다. 없으면 `docs/plans/`를 추가한다 |
| 4 | `assets/plan-template.md`를 복사해 초안 `YYYY-MM-DD-<주제>.md` 하나를 만든다 |

계획서는 규모와 무관하게 최상위·도메인·기능 세 층 구조로 완성한다. 상태는 기능 계획서에서만 관리한다. 최상위와 도메인 문서에는 목록과 판단만 둔다.

구현 순서가 나와야 경계를 정할 수 있다. 그러므로 대화 중에는 초안 한 편에 내용을 쌓고, 4-1번에서 디렉터리 구조로 옮긴다.

### 1~6. 섹션 채우기

**위에서부터 순서대로 채우고, 섹션마다 통과 조건을 만족했는지 사용자에게 확인받은 뒤 다음으로 넘어간다.**

| 순서 | 섹션 | 지킬 것 |
| --- | --- | --- |
| 1 | 요약(가제) | 목표와 배경만 쓴다. 변경점은 비워 둔다 |
| 2 | 상태 | 기능 계획서에만 규격대로 자동 생성. 단계 `계획 확정`, 진행률 `0 / 0` |
| 3 | 설계 | 필요한 설계 유형을 제안하고, 사용자가 승인한 유형의 형식으로 해법과 근거를 작성한다 |
| 4 | 구현 순서 | 한 항목 = 한 커밋 = 되돌릴 수 있는 최소 단위 |
| 4-1 | (경계 긋기) | 도메인과 기능을 가르고 위층부터 구조로 옮긴다 |
| 5 | 테스트 | 모든 구현 항목이 최소 하나의 검증에 대응 |
| 6 | 요약 확정 | 변경점을 채우고 설계·구현 순서와 대조 |

사용자의 답을 문서에 반영한 뒤, 반영 결과를 보여 준다. 그다음에 다음 섹션으로 넘어간다.

설계 섹션을 작성하기 전에 `references/design-cases.md`를 읽고 요구사항과 코드베이스에 해당하는 유형만 제안한다. 사용자가 범위를 승인하면 선택한 유형의 형식을 적용하고, 해당하지 않는 유형은 계획서에 넣지 않는다.

변경점은 설계와 구현 순서가 정해진 뒤 작성한다. 그 시점에 실제 변경 범위를 정확히 적을 수 있다.

### 4-1. 도메인과 기능 가르기

**구현 순서를 채운 다음 한 번 멈추고, 도메인과 기능의 경계를 사용자에게 보여 동의를 받은 뒤 디렉터리 구조로 옮긴다.**

| 정할 것 | 기준 |
| --- | --- |
| 기능을 몇 개로 가를까 | 독립적으로 돌려 볼 수 있는 검증 지점마다 하나. 지점이 하나뿐이면 기능도 하나다 |
| 도메인을 몇 개로 묶을까 | 성격이 갈리는 만큼. 한 갈래면 도메인도 하나다 |

이 단계에서는 나눌지 여부를 묻지 않는다. 기능이 하나여도 최상위·도메인·기능 계획서 세 층을 만든다.

경계는 먼저 검증할 대상을 기준으로 정한다. 어느 대상을 먼저 검증할지는 사용자가 결정한다.

구조로 옮길 때는 위층부터 작성한다. 최상위 문서에는 도메인 목록과 선행 관계를 남긴다. 도메인 문서에는 기능 목록을 남긴다. 기능 계획서에는 상태를 남긴다. 이동이 끝나면 초안 파일을 삭제한다.

### 7. 확정

**구조 이전과 인계 점검을 마치고 사용자의 승인을 받은 뒤에만 단계를 `계획 확정`으로 바꾼다.**

| 순서 | 할 일 |
| --- | --- |
| 1 | 규격과 대조해 표기를 확인한다 |
| 2 | 미해결 검토 표시가 남아 있으면 그 자리를 사용자와 정리한다. 하나라도 남으면 확정할 수 없다 |
| 3 | 인계 점검을 한다. 항목마다 "이것만 읽고 무엇을 어디에 할지 정해지는가"를 묻는다 |
| 4 | 구현 진행률의 전체 수를 구현 항목 수로 맞춘다 |

초안을 쓰는 동안에는 `초안 작성 중`, 구조로 옮기는 동안에는 `구조 이전 필요`, 사용자 확인을 기다리는 동안에는 `사용자 승인 대기`를 사용한다. 세 층 구조·인계 점검·사용자 승인이 끝나기 전에는 `계획 확정`으로 바꾸지 않는다.

확정하기 전에 `scripts/validate-plan.sh`로 문서 구조와 상태와 항목 형식을 검사한다.

스스로 확정하지 않는다. 이 지점이 사용자의 책임이 실제로 걸리는 자리이기 때문이다. 승인을 받으면 계획서는 로컬에 둔 채 `/impl-plan`으로 진행한다고 안내한다.

## 경계

- 이미 계획서가 있고 상태가 `계획 확정`이면 이 스킬이 아니라 `/impl-plan`다.
- 상태가 `완료`면 구현 결과를 확인한다.
- `impl-plan`이 계획의 결함을 발견해 상태를 `계획 확정`으로 되돌린 경우, 이 스킬로 돌아와 해당 부분을 사용자와 다시 설계한다. 이때 요약부터 다시 쓰지 않고 어긋난 곳만 고친다.
