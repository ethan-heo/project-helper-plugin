# create-plan

## 역할과 목적

`create-plan`은 코드 변경을 바로 구현하지 않고, 사용자와 함께 구현 결정을 좁혀 실행 가능한 계획서로 기록한다. 사용자는 계획의 결정권자이고, AI는 조사·질문·검토·기록을 맡는다.

## 실행 원칙

**사용자의 결정은 기록하고, AI의 추정은 표시하며, 문서에 없는 범위는 추가하지 않는다.**

사용자가 이 스킬을 명시하면 뒤따르는 질문은 기본적으로 계획 작성의 입력으로 해석한다. 질문이 스킬의 개념이나 사용법만 묻는 설명 요청이면 실행을 진행하지 않고 일반 답변을 제공한다. 계획 작성 입력으로 이어진 실행 맥락은 계획이 완료되거나 사용자가 다른 스킬 또는 일반 질문을 명시할 때까지 유지한다.

추가 작업이 들어오면 먼저 연관성을 판단한다. 판단 대상은 현재 계획의 기능과 사용자 흐름이다. 연관되면 계획 상태가 `진행 중`이거나 `완료`여도 기존 계획서의 설계·구현 순서·테스트를 수정한다. 수정한 뒤 상태는 `계획 완료`로 유지한다. 연관되지 않으면 현재 계획에 넣지 않고 기존 계획서의 `추후 작업` 절에 기록한다.

이 스킬은 요구사항을 곧바로 구현하는 스킬이 아니다. 사용자와 함께 설계를 좁히고, 확정된 결정을 구현 가능한 계획서로 남긴다.

## 참조 문서 규칙

이 문서가 `create-plan`의 실행 지시사항을 정하는 기준 문서다. 작업을 시작할 때 이 문서를 먼저 읽고, 아래 표의 절차에 진입할 때 지정된 참조 문서만 읽는다.

| 문서 유형 | 역할 | 적용 범위 |
| --- | --- | --- |
| `SKILL.md` | 실행 절차와 분기 | `create-plan` 전체 |
| `references/` | 근거·예외·세부 판정 | 본문이 지정한 절차 |
| `assets/` | 계획서·색인 템플릿 | 파일을 만들 때 |
| `scripts/` | 계획서 형식 검증 | 확정 직전 |

참조 문서는 본문에 없는 실행 범위를 추가하지 않는다. 문서 관리 형식은 `docs/공통_인프라_및_컨벤션/문서_작성_기준.md`를 따른다.

시작하기 전에 [`roles.md`](references/collaboration/roles.md)와 [`questioning.md`](references/collaboration/questioning.md)를 읽는다. AI는 관련 파일과 제약을 조사해 제시하고, 해법과 선택은 사용자에게 맡긴다.

## 계획 작성 절차

### 0. 준비

**요구사항과 저장소를 확인한 다음, 상태를 `초안 작성`으로 둔 빈 양식을 복사한다.**

| 순서 | 할 일 |
| --- | --- |
| 1 | 요구사항을 확인한다. 무엇을 원하는지 불분명하면 여기서 한 번 좁힌다 |
| 2 | [`existing-docs.md`](references/planning/existing-docs.md)를 읽고 프로젝트의 개발 문서를 찾아 읽는다. 문서가 없으면 그 사실을 사용자에게 알린다 |
| 3 | 관련 파일, 기존 처리 방식, 제약을 찾아 둔다. 여기서 해법을 만들지는 않는다 |
| 4 | 프로젝트 지시사항에서 계획서를 둘 경로를 찾고, 그 경로가 `.gitignore`에 등록되어 있는지 확인한다. 없으면 `docs/plans/`를 추가한다 |
| 5 | `assets/plan-template.md`를 복사해 초안 `YYYY-MM-DD-<주제>.md` 하나를 만든다 |

문서를 코드보다 먼저 읽는다. 도메인의 책임 경계와 기존 결정을 알아야 요구사항이 어디에 속하는지 판단할 수 있다. 다만 사실 판정의 기준은 코드이므로, 문서와 코드가 어긋나면 코드를 따르고 그 차이를 사용자에게 보고한다.

계획서는 규모와 무관하게 최상위·도메인·기능 세 층 구조로 완성한다. 상태는 기능 계획서에서만 관리한다. 최상위와 도메인 문서에는 목록과 판단만 둔다.

구현 순서가 나와야 경계를 정할 수 있다. 그러므로 대화 중에는 초안 한 편에 내용을 쌓고, 4-1번에서 디렉터리 구조로 옮긴다.

### 1~6. 섹션을 순서대로 채운다

**위에서부터 순서대로 채우고, 섹션마다 통과 조건을 만족했는지 사용자에게 확인받은 뒤 다음으로 넘어간다.**

| 순서 | 섹션 | 지킬 것 |
| --- | --- | --- |
| 1 | 요약(가제) | 목표와 배경만 쓴다. 변경점은 비워 둔다 |
| 2 | 상태 | 기능 계획서에만 규격대로 자동 생성. 단계 `초안 작성`, 진행률 `0 / 0` |
| 3 | 설계 | 필요한 설계 유형을 제안하고, 사용자가 승인한 유형의 형식으로 해법과 근거를 작성한다 |
| 4 | 구현 순서 | 한 항목 = 한 커밋 = 되돌릴 수 있는 최소 단위 |
| 4-1 | (경계 긋기) | 도메인과 기능을 가르고 위층부터 구조로 옮긴다 |
| 5 | 테스트 | 모든 구현 항목이 최소 하나의 검증에 대응 |
| 6 | 요약 확정 | 변경점을 채우고 설계·구현 순서와 대조 |

**각 섹션을 하나씩 확정한 뒤 내용을 문서에 반영하고 다음 섹션으로 넘어간다.**

카테고리마다 먼저 열린 질문을 제시한다. 답변만으로 구현자가 바로 작성하기 어렵다면 선택지와 선택에 따른 차이를 제시한다. 선택지 밖의 답변을 받으면 그 답변을 새 기준으로 삼아 필요한 질문을 이어간다. 구현자가 추가 질문 없이 작성할 수 있게 되면 카테고리 내용을 기록하고 다음 카테고리로 이동한다.

사용자가 결정해야 하는 대안이 2~3개라면 `1.`, `2.`, `3.` 형식으로 번호를 붙인다. 단순 안내 목록에는 번호를 붙이지 않는다.

확인받지 못한 결정은 확정된 사실처럼 쓰지 않는다.

**설계 섹션을 작성하기 전에 [`design.md`](references/design.md)를 읽고 해당하는 설계 유형만 제안한다.**

| 설계 승인 상태 | 할 일 |
| --- | --- |
| 사용자가 유형을 승인함 | 선택한 유형의 형식으로 작성한다 |
| 사용자가 유형을 승인하지 않음 | 범위를 다시 좁힌다 |

해당하지 않는 설계 유형은 계획서에 넣지 않는다.

**설계와 구현 순서가 정해진 뒤 요약의 변경점을 작성한다.**

실제 변경 범위가 확정된 뒤 작성해야 요약과 구현 순서가 어긋나지 않는다.

### 4-1. 문서 경계를 정한다

**구현 순서를 채운 뒤 도메인과 기능의 경계를 정한다. 경계를 사용자에게 보여 동의를 받은 다음 디렉터리 구조로 옮긴다.**

| 정할 것 | 기준 |
| --- | --- |
| 기능을 몇 개로 가를까 | 독립적으로 돌려 볼 수 있는 검증 지점마다 하나. 지점이 하나뿐이면 기능도 하나다 |
| 도메인을 몇 개로 묶을까 | 성격이 갈리는 만큼. 한 갈래면 도메인도 하나다 |

**기능과 도메인의 경계를 먼저 검증할 대상을 기준으로 정한다.**

기능이 하나여도 최상위·도메인·기능 계획서 세 층을 만든다.

| 판단 대상 | 결정 주체 |
| --- | --- |
| 먼저 검증할 대상 | 사용자 |
| 대상에 따른 기능·도메인 경계 | AI가 제안하고 사용자에게 확인 |

**구조로 옮길 때는 최상위 문서부터 작성하고, 이동이 끝나면 초안 파일을 삭제한다.**

| 문서 층위 | 남길 내용 |
| --- | --- |
| 최상위 | 도메인 목록과 선행 관계 |
| 도메인 | 기능 목록 |
| 기능 계획서 | 상태 |

### 7. 확정

**구조 이전과 인계 점검을 마치면 단계를 `계획 완료`로 바꾼다.**

| 순서 | 할 일 |
| --- | --- |
| 1 | 규격과 대조해 표기를 확인한다 |
| 2 | 미해결 검토 표시가 남아 있으면 그 자리를 사용자와 정리한다. 하나라도 남으면 확정할 수 없다 |
| 3 | 인계 점검을 한다. 항목마다 "이것만 읽고 무엇을 어디에 할지 정해지는가"를 묻는다 |
| 4 | 구현 진행률의 전체 수를 구현 항목 수로 맞춘다 |

초안을 쓰는 동안 단계는 `초안 작성`이다. 초안 작성이 끝나면 세 층 구조로 나눈다. 구조 이전과 인계 점검을 마친 뒤 단계를 `계획 완료`로 바꾼다.

확정하기 전에 `scripts/validate-plan.sh <계획 디렉터리>`로 문서 구조와 상태와 항목 형식을 검사한다.

구조 이전과 인계 점검이 끝나면 계획서는 로컬에 둔 채 `/impl-plan`으로 진행한다고 안내한다.

## 경계

- 이미 계획서가 있고 상태가 `계획 완료`이면 이 스킬이 아니라 `/impl-plan`이다.
- 상태가 `완료`면 구현 결과를 확인한다.
- 사용자가 구현을 직접 요청했지만 계획서가 없으면, 먼저 이 스킬로 계획을 만든다.
- `impl-plan`이 계획의 결함을 발견하면 이 스킬로 돌아와 해당 부분을 다시 설계한다. 이때 요약부터 다시 쓰지 않고 어긋난 곳만 고친다.
