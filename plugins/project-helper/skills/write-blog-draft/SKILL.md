# write-blog-draft

## 역할과 목적

`write-blog-draft`는 그날 갱신된 계획서와 PRD를 글감으로 삼아, 블로그에 올릴 글의 초안을 쓴다. 문서를 요약하지 않고, 읽는 사람이 배경과 문제에서 출발해 의사결정과 결과까지 따라올 수 있는 순서로 재구성한다. 초안은 절마다 두세 문장으로 논지를 세우는 데까지이며, 살은 사용자가 자기 말로 붙인다.

## 실행 원칙

**절마다 두세 문장으로 논지만 세우고, 재료가 없는 자리는 지어내지 않고 묻는다.**

초안을 게시할 수준까지 채우지 않는 이유는 글의 주인이 사용자이기 때문이다. 문단을 온전히 써 주면 고쳐 쓰는 일이 남의 글을 다듬는 일이 되고, 자기 말로 쓸 여지가 오히려 줄어든다. 반대로 목차와 재료만 주면 첫 문장을 백지에서 시작해야 한다.

사용자가 이 스킬을 명시하면 뒤따르는 답변은 기본적으로 초안 작성의 입력으로 해석한다. 질문이 스킬의 개념이나 사용법만 묻는 설명 요청이면 작성을 진행하지 않고 일반 답변을 제공한다. 작성 입력으로 이어진 실행 맥락은 초안이 저장되거나 사용자가 다른 스킬 또는 일반 질문을 명시할 때까지 유지한다.

근거는 계획서와 PRD 두 가지뿐이다. 코드나 커밋 이력에서 내용을 끌어오지 않는다. 문서에 없는 대목은 추측으로 메우지 않고 사용자에게 물어 채운다.

다른 스킬의 산출물은 읽기만 하고 고치지 않는다. 계획서의 상태 표나 체크박스를 건드리지 않으며 코드도 손대지 않는다. 계획서의 단계가 `계획 완료`든 `완료`든 실행할 수 있다. 그날 무엇을 했는지 기록하는 것이 목적이지 구현이 끝났는지 판정하는 것이 목적이 아니기 때문이다.

## 참조 문서 규칙

이 문서가 `write-blog-draft`의 실행 지시사항을 정하는 기준 문서다. 작업을 시작할 때 이 문서를 먼저 읽고, 아래 표의 절차에 진입할 때 지정된 참조 문서만 읽는다.

| 문서 유형 | 역할 | 적용 범위 |
| --- | --- | --- |
| `SKILL.md` | 실행 절차와 분기 | `write-blog-draft` 전체 |
| `../_shared/docs-root.md` | 문서 루트 판정 규칙 | 수집 단계의 경로 결정 |
| `references/collection.md` | 기준일 판정과 글감 수집, 주제 분류와 블로그 적합성 판정 | 수집 단계 |
| `references/outline.md` | 흐름 단계와 절 구성, 제목·핵심 메시지 제안 | 목차 단계 |
| `references/questioning.md` | 빈자리를 채우는 질문 | 보충 단계 |
| `references/drafting.md` | 문체와 분량, 재료를 문장으로 옮기는 규칙 | 초안 단계 |
| `assets/draft-template.md` | 초안 양식 | 파일을 만들 때 |

참조 문서는 본문에 없는 실행 범위를 추가하지 않는다.

## 작성 절차

절차는 수집 → 목차 → 질문 → 초안 → 저장 다섯 단계다. 목차는 파일로 남기지 않고 대화에서 확인받는 중간 산출물이며, 파일로 저장하는 것은 초안 본문 한 편뿐이다.

### 1. 글감을 모은다

**기준일을 정하고, 그날 갱신된 계획서와 PRD를 모아 목록과 주제 분류와 블로그 적합성 판정을 사용자에게 보인다.**

[`collection.md`](references/collection.md)를 읽고 아래 순서로 진행한다.

| 순서 | 할 일 |
| --- | --- |
| 1 | 기준일을 정한다. 사용자가 날짜를 지정하지 않으면 오늘로 본다 |
| 2 | [`docs-root.md`](../_shared/docs-root.md)로 문서 루트를 판정한다 |
| 3 | `<루트>/plans/`와 `<루트>/prds/`에서 `마지막 갱신` 값이 기준일과 같은 문서를 모은다 |
| 4 | 수집 목록과 제외한 문서를 함께 보이되, 문서마다 필수 관문의 통과 여부를 붙인다. 뺄 것과 더할 것을 확인받는다 |
| 5 | 글감의 주제 분류를 뽑아 근거가 된 문서와 함께 보인다 |
| 6 | 분류마다 필수 관문과 보조 축을 판정한다. 걸린 분류에는 관문의 이름을, 통과한 분류에는 충족한 보조 축을 붙인다 |
| 7 | 이 주제로 글을 쓸지 확인받는다. 동의를 받기 전에는 다음 단계로 넘어가지 않는다 |

| 수집 결과 | 할 일 |
| --- | --- |
| 한 편 이상 | 분류 판정으로 넘어간다 |
| 한 편도 없다 | 분류 판정에 들어가지 않는다. 초안을 만들지 않고 사실을 알린 뒤 다른 날짜를 지정할지 묻는다 |

| 분류 확인 결과 | 할 일 |
| --- | --- |
| 사용자가 진행에 동의한다 | 목차 작성으로 넘어간다 |
| 사용자가 분류를 물린다 | 진행하지 않고 어떤 주제로 볼지 되묻는다 |

| 판정 결과 | 할 일 |
| --- | --- |
| 통과한 분류가 있다 | 그 분류로 목차 작성에 넘어간다. 걸린 분류가 함께 있으면 어느 관문에 걸렸는지 알린다 |
| 통과한 분류가 하나도 없다 | 초안을 만들지 않고 분류마다 걸린 관문을 알린 뒤 끝낸다 |
| 사용자가 판정을 물린다 | 지정한 분류로 진행하고 같은 근거로 다시 판정하지 않는다 |
| 계획서에 설계 절이 없다 | 첫 관문을 통과하지 못한 것으로 보고, 근거가 없어 판정할 수 없었음을 함께 알린다 |

분류는 고정 목록 없이 뽑는다. 근거로 읽는 자리는 요약의 목표와 배경, PRD의 목적에 더해 설계의 결정 요약과 예외 상황, 구현 항목의 완료 판정과 기록 줄까지다. 다만 구현 항목 ID와 파일 경로, 스킬 디렉터리 이름은 근거로만 읽고 분류 이름에는 쓰지 않는다. 여러 갈래로 나오면 몇 편으로 나눌지 한자리에서 함께 묻는다. 분류는 대화에서만 쓰고 저장하는 초안 파일에는 남기지 않는다.

블로그 적합성 판정은 필수 관문 셋을 모두 통과해야 블로그감으로 본다. 보조 축은 통과한 글감의 강약을 매기는 데만 쓰며 통과와 탈락을 가르지 않는다. 판정은 제안이고 확정은 사용자가 한다.

### 2. 목차를 짠다

**배경에서 결과까지 이어지는 흐름으로 절을 세운다. 필수 네 단계는 항상 두고, 선택 네 단계는 재료가 있을 때만 세운다.**

[`outline.md`](references/outline.md)를 읽고 아래를 채운다.

| 구분 | 단계 |
| --- | --- |
| 필수 | 배경, 문제 정의, 의사결정, 결과 |
| 선택 | 기획 과정, 시행착오, 회고, 향후 개선 방향 |

절마다 제목과 흐름 단계, 작성 포인트, 재료를 붙여 사용자에게 보인다. 재료는 판단 하나가 항목 하나이며, 택한 것과 기각한 대안을 한 항목에 함께 두고 앞 절에서 이어받는 것을 재료 앞에 한 줄로 적는다. 기능을 소개하는 절은 세우지 않고, 왜 그렇게 정했는지를 절의 자리에 둔다.

이 목차는 파일로 저장하지 않는다. 대화에서 확인받은 절 구성과 재료가 4단계 초안의 입력이 된다.

갈래를 몇 편으로 나눌지는 수집 단계의 분류 확인에서 이미 정해져 있다. 여기서 다시 묻지 않고 정해진 갈래대로 목차를 짠다.

### 3. 빈자리를 채운다

**계획서에 근거가 없어 비는 자리를 질문해 채우고, 제목 후보와 핵심 메시지를 제안해 확정받는다.**

[`questioning.md`](references/questioning.md)를 읽고 질문을 만든다. 질문은 필수 단계용과 선택 단계용 두 묶음으로 나눠 각각 세 개까지 묻는다. 사용자가 답하지 않기로 한 자리는 채우지 않고, 무엇이 비었는지를 초안을 보일 때 함께 알린다.

제목 후보는 방향이 겹치지 않게 두셋을 내고, 핵심 메시지와 무게중심을 함께 제안한다. 사용자가 후보를 모두 물리면 가제 한 줄을 제목으로 쓴다.

### 4. 초안을 쓴다

**목차에서 세운 절을 문장으로 푼다. 절마다 두세 문장으로 논지만 세우고, 재료에 없는 내용을 지어내지 않는다.**

[`drafting.md`](references/drafting.md)를 읽고 `assets/draft-template.md`를 채운다.

| 요소 | 규칙 |
| --- | --- |
| 서술 어미 | 평어체로 고정한다 |
| 절의 분량 | 두세 문장 |
| 절 제목 | `## <제목>`. 흐름 단계 이름을 적지 않는다 |
| 글 제목 | `# <제목>`. 사용자가 고른 후보를 쓰고, 모두 물렸으면 가제를 쓴다 |
| 식별자 | 구현 항목 ID와 파일 경로, 계획서의 절 이름을 본문에 쓰지 않는다 |

작성 포인트와 재료, 흐름 단계는 초안 파일에 남기지 않는다. 파일에 들어가는 것은 제목과 절 제목과 본문 문장뿐이다.

### 5. 저장한다

**초안을 `<루트>/posts/YYYY-MM-DD-<주제>.md`에 저장한다.**

| 상황 | 할 일 |
| --- | --- |
| `posts/`가 없다 | 만들고 `.gitignore`에 등록한다 |
| 같은 날짜의 초안 파일이 이미 있다 | 덮어쓰지 않고 이어 쓸지 새로 만들지 묻는다 |
| `posts/blog/`나 `posts/log/`에 기존 파일이 있다 | 옮기지 않고 그대로 둔다 |

저장한 뒤 초안의 경로와 절 목록, 재료가 없어 비운 자리를 사용자에게 알린다.

## 경계

- 게시할 수준의 완성된 글은 쓰지 않는다. 절마다 두세 문장으로 논지를 세우는 데까지가 범위이며, 살을 붙이는 일은 사용자의 몫임을 알린다.
- 근거를 찾지 못한 내용을 지어내지 않는다. 그 절은 제목만 세우고 비었다는 사실을 알린다.
- 구현 결과를 프로젝트 안의 문서로 정리하는 일은 이 스킬이 아니라 `/create-docs`다.
- 요구사항을 정하는 일은 `/create-prd`, 구현 방식을 정하는 일은 `/create-plan`이다.
- 사용자가 주제 분류를 물리면 초안을 만들지 않는다. 물린 주제를 그대로 다시 제시하지 않는다.
- 블로그 적합성 판정은 제안이다. 사용자가 판정을 물리면 지정한 분류를 따르고, 같은 근거로 판정을 되풀이하지 않는다.
- 계획서와 PRD, 코드를 고치지 않는다. 이 스킬이 만드는 파일은 `<루트>/posts/` 아래의 초안뿐이다.
