# create-prd

## 역할과 목적

`create-prd`는 무엇을 왜 만드는지를 사용자와의 질의응답으로 확정하고, 그 결과를 PRD 문서 한 편으로 남긴다. 구현 방식은 다루지 않는다. 사용자는 목적과 요구사항의 결정권자이고, AI는 질문·정리·기록을 맡는다.

## 실행 원칙

**답변이 충분해질 때까지 질문하고, 확정되지 않은 것은 미해결로 표시한다.**

**호출 후 입력은 [스킬 실행 맥락](../_shared/session.md#입력-해석)에 따라 해석한다.**

산출물은 여덟 절로 구성한 단일 문서 한 편이다. 절의 분량과 미확정 내용은 [PRD 서술 규칙](../_shared/prd/writing.md)을 따른다.

## 참조 문서 규칙

이 문서가 `create-prd`의 실행 지시사항을 정하는 기준 문서다. 작업을 시작할 때 이 문서를 먼저 읽고, 아래 표의 절차에 진입할 때 지정된 참조 문서만 읽는다.

| 문서 유형 | 역할 | 적용 범위 |
| --- | --- | --- |
| [`session.md`](../_shared/session.md) | 후속 입력 해석 | 호출 직후 |
| `SKILL.md` | 실행 절차와 분기 | `create-prd` 전체 |
| [`architecture.md`](../_shared/architecture.md) | 후속 스킬 판단 | 확정 후 |
| `../_shared/docs-root.md` | 문서 루트 판정 규칙 | 준비 단계의 보관 경로 결정 |
| `references/questioning.md` | 카테고리별 질문 설계와 충분성 판정 | 카테고리 순회 |
| `../_shared/questioning-examples.md` | 질문과 선택지에 붙이는 예시 | 카테고리 순회 |
| `../_shared/prd/writing.md` | 간결성 서술 규칙과 점검 목록 | 절을 쓸 때와 확정 직전 |
| `../_shared/writing-style.md` | 산출물의 문체와 표기 | 절을 쓸 때 |
| `../_shared/prd/prd-template.md` | PRD 문서 양식 | 초안을 만들 때 |
| `../_shared/prd/validate-prd.sh` | 필수 절과 항목 형식 검증 | 확정 직전 |

참조 문서는 본문에 없는 실행 범위를 추가하지 않는다.

## 작성 절차

### 0. 준비

**요청이 PRD 작성에 해당하는지 판단한 다음, 보관 경로에 초안을 만든다.**

| 순서 | 할 일 |
| --- | --- |
| 1 | 요청의 대상이 제품·프로젝트 단위인지 확인한다. 기능 하나의 구현 방식이면 `/create-plan`을 안내하고 종료한다 |
| 2 | [`docs-root.md`](../_shared/docs-root.md)를 읽고 문서 루트를 판정한 뒤 `<루트>/prds/`를 보관 경로로 삼는다. 디렉터리가 없으면 만든다 |
| 3 | 해당 경로가 `.gitignore`에 등록되어 있는지 확인하고, 없으면 사용자에게 보관 방식을 확인한다 |
| 4 | `../_shared/prd/prd-template.md`를 복사해 `YYYY-MM-DD-<주제>.md` 초안을 만들고, `마지막 갱신`을 오늘 날짜로 적는다 |

PRD는 작업 대상 코드가 정해지기 전에 쓴다. 그래서 문서 루트 후보가 여럿일 때 가장 가까운 조상을 고르는 기준을 쓸 수 없고, 이름이 겹치는 후보를 고르는 기준부터 적용한다.

### 1. 카테고리를 순서대로 순회한다

**[`questioning.md`](references/questioning.md)를 읽고, 여덟 카테고리를 순서대로 돈다.**

질문과 다음 카테고리로 넘어가는 판단은 [질문 방식](references/questioning.md#질문-방식)을 따른다. 카테고리 건너뛰기는 같은 문서의 [예외 처리](references/questioning.md#예외-처리)를 따른다.

절을 쓸 때는 [`writing.md`](../_shared/prd/writing.md)의 서술 규칙과 [`writing-style.md`](../_shared/writing-style.md)의 문체·표기·어휘 규칙을 적용한다.

| 상황 | 할 일 |
| --- | --- |
| 답변이 구현 방식을 다룬다 | PRD의 범위가 아님을 알리고 목적과 요구사항으로 되돌린다 |

한 카테고리를 끝낼 때마다 반영한 내용을 사용자에게 한두 줄로 알린다.

### 2. 확정한다

**형식과 문장을 모두 점검한 뒤에만 확정한다.**

| 순서 | 할 일 |
| --- | --- |
| 1 | `../_shared/prd/validate-prd.sh <PRD 파일>`로 필수 절과 요구사항 표기, 미해결 잔존 여부를 검사한다 |
| 2 | `writing.md`의 확정 전 점검 목록을 항목마다 대조한다 |
| 3 | `마지막 갱신`을 오늘 날짜로 맞춘다 |
| 4 | 불통과 항목이 있으면 해당 절을 사용자와 다시 정리한다 |

| 결과 | 할 일 |
| --- | --- |
| 검증 스크립트가 실패한다 | 확정하지 않고 실패한 절을 사용자와 다시 정리한다 |
| 미해결 질문이 남아 있다 | [PRD 서술 규칙의 예외 처리](../_shared/prd/writing.md#예외-처리) 적용 |
| 모두 통과한다 | 확정 후 아래 기준으로 다음 스킬 안내 |

**[PRD 확정 후 안내](../_shared/architecture.md#prd-확정-후-안내)에 따라 다음 스킬을 안내한다.**

## 경계

- 여러 계획이 따를 구조·패턴·계약을 정하는 일은 `/create-architecture`이다.
- 기능 하나의 구현 방식을 정하는 일은 이 스킬이 아니라 `/create-plan`이다.
- 이미 확정된 요구사항의 구현 순서를 짜는 일도 `/create-plan`이다.
- PRD에는 해법과 기술 선택을 쓰지 않는다.
- 미해결 질문이 남은 PRD는 확정하지 않는다.
- 확정된 PRD의 범위가 커서 요구사항별로 하위 PRD를 만드는 일은 `/create-sub-prd`이다.
- 확정된 PRD의 내용을 고칠 때는 `마지막 갱신`을 그날 날짜로 맞춘다. 이 값이 그날 작업한 문서를 골라내는 기준이 된다.
