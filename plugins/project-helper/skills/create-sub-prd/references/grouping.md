# 묶음 후보와 배정

## 목적

상위 PRD의 요구사항을 하위 PRD 단위로 가르는 기준을 정한다.

## 핵심 지시

`사용자와 사용 상황` 절의 행마다 관련 요구사항을 모아 후보를 제안하고, 사용자가 고른 묶음을 배정으로 삼는다.

## 후보를 만드는 순서

| 순서 | 할 일 |
| --- | --- |
| 1 | 상위 PRD의 `사용자와 사용 상황` 절을 읽어 행 목록을 만든다 |
| 2 | 요구사항마다 어느 행의 상황에서 쓰이는지 판단해 그 행에 붙인다 |
| 3 | 요구사항이 붙지 않은 행은 후보에서 뺀다 |
| 4 | 어느 행에도 붙지 않은 요구사항을 따로 모아 사용자에게 제시한다 |
| 5 | 묶음마다 이름과 담긴 요구사항 ID를 표로 보여주고 사용자의 선택을 받는다 |

제안은 판단 재료이지 결론이 아니다. 사용자가 다른 묶음을 지정하면 후보에 맞추지 않고 그 지정을 배정으로 삼는다.

## 배정 규칙

| 규칙 | 내용 |
| --- | --- |
| 완전성 | 상위의 모든 요구사항 ID가 하위 문서 중 어딘가에 배정된다 |
| 유일성 | 한 요구사항 ID는 하위 문서 한 곳에만 배정된다 |
| 묶음 크기 | 한 묶음이 맡는 요구사항 수를 미리 제한하지 않는다. 하나만 맡는 묶음도 허용한다 |
| 이름 | 묶음 이름은 담당 요구사항이 다루는 대상을 가리키는 짧은 명사구로 쓴다 |

## 예외 처리

| 예외 조건 | 할 일 |
| --- | --- |
| 어느 묶음에도 들어가지 않은 요구사항이 있다 | 배정을 확정하지 않고 남은 ID를 제시해 배정받는다 |
| 같은 요구사항이 두 묶음에 들어갔다 | 어느 하나를 고르게 한다. 실제로 둘로 나뉘어야 하는 요구사항이면 상위 문구 수정 절차로 넘긴다 |
| `사용자와 사용 상황` 절의 행이 하나뿐이다 | 시나리오로 갈리지 않음을 알리고 사용자에게 묶음 단위를 직접 받는다 |
| 요구사항이 하나뿐이거나 이미 충분히 구체적이다 | 분해하지 않고 그 사실을 알린다 |
| 묶음 주제를 파일명으로 쓰기 어렵다 | 사용자에게 짧은 이름을 확인받는다. 공백과 경로 구분자는 쓰지 않는다 |

## 근거·예시

구현 대상을 기준으로 묶으면 PRD 단계에서 아직 정해지지 않은 해법을 앞당겨 가정하게 된다. 사용자 시나리오는 이미 상위 PRD 안에 확정된 정보이므로, 그것을 기준으로 삼으면 제안의 근거를 문서 안에서 보일 수 있다.

예를 들어 `사용자와 사용 상황` 절에 "처음 분해할 때"와 "이미 나눈 문서를 다시 나눌 때" 두 행이 있으면, 반복 진입에 관한 요구사항은 두 번째 행의 묶음으로 모인다.
