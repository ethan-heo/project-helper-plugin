# plan-verify

## 무엇을 하는 스킬인가

구현이 끝난 계획서를 받아, 테스트 시나리오를 돌리고 무엇이 왜 바뀌었는지 사용자에게 보여 준 뒤 승인을 받아 닫는다.

**판정은 당신이 하지 않는다.** 실행 결과와 실제 변경 내역을 증거로 내놓고, 통과 여부는 사용자가 정한다. 구현한 쪽과 검증하는 쪽을 나눈 이유가 여기 있다. 같은 자리에서 "다 됐습니다"라고 말하면 검증이 형식만 남는다.

"테스트가 모두 통과했으니 완료로 바꾸겠습니다"는 이 스킬이 할 말이 아니다. "네 개 중 세 개가 통과했고 하나는 이렇게 실패했습니다. 어떻게 하시겠습니까"가 할 말이다.

판단이 필요한 자리마다 `references/verification.md`의 해당 절을 읽는다. 어느 절을 언제 읽는지는 맨 아래 표에 있다.

## 절차

### 1. 전제를 확인한다

**계획서를 열어 아래 넷을 보고, 하나라도 어긋나면 진행하지 않고 그 지점을 사용자에게 짚는다.**

| 볼 것 | 통과 조건 |
| --- | --- |
| 단계 | 상태 표가 `구현 완료`다 |
| 체크 | 모든 구현 항목이 체크돼 있다 |
| 진행률 | 체크된 수와 맞다 |
| 시나리오 | `## 테스트`에 돌릴 것이 있다 |

계획서를 지정받지 못했으면 `docs/plans/`에서 단계가 `구현 완료`인 것을 찾고, 후보가 여럿이면 사용자에게 묻는다.

### 2. 시나리오를 실행한다

**`## 테스트`의 항목을 위에서부터 하나씩 돌리고, 결과를 시나리오 ID와 함께 정리해 보여 준다.**

| 돌릴 수 있는가 | 할 일 |
| --- | --- |
| 자동으로 돌릴 수 있다 | 돌리고 출력을 그대로 보여 준다. "통과"라고만 쓰지 않는다 |
| 사람이 봐야 한다 | 무엇을 확인하면 되는지 알려 주고 사용자의 판단을 받는다 |
| 실행 시점의 구현 항목이 아직 안 끝났다 | 못 돌린 이유로 적는다 |
| 그 밖에 돌릴 수 없다 | 왜 못 하는지 적는다. 조용히 건너뛰지 않는다 |

### 3. 변경 내역을 대조한다

**계획서의 변경점과 실제로 들어간 변경을 맞춰 보고, 어느 한쪽에만 있는 것을 짚는다.**

차이를 발견하면 고치지 말고 어느 쪽이 맞는지 사용자에게 묻는다.

### 4. 변경 요약을 만든다

**각 구현 항목의 기록 줄과 실제 변경을 이어 붙여, 항목마다 왜 그렇게 했고 무엇이 달라지는지 읽을 수 있게 쓴다.**

diff를 그대로 붙이지 않는다. 사용자가 diff를 읽을 수 있었다면 이 단계가 필요 없었다.

### 5. 승인을 받는다

**시나리오 결과와 변경 요약을 보여 주고 물은 뒤, 승인을 받으면 단계를 `완료`로 바꾸고 마지막 갱신을 고친다.**

승인이 나오지 않으면 6·7번으로 가지 않고 "못 미치면 되돌린다"로 간다.

### 6. 머지한다

**`slice/…` 브랜치에서 작업했다면 그 브랜치에 `완료` 표시를 커밋한 뒤 `feature/<주제>`로 옮겨 `--no-ff`로 머지한다.**

| 이런 경우 | 할 일 |
| --- | --- |
| 계획서를 나누지 않았다 | 머지할 대상이 없다. 문서를 닫기만 한다 |
| 머지가 충돌한다 | 멈추고 무엇이 부딪혔는지 보여 준다 |
| `feature`의 계획서가 다 닫혔다 | 기본 브랜치로 보내지 않고 준비됐다고만 알린다 |

### 7. 위층 문서를 갱신한다

**머지가 끝난 뒤 `feature` 브랜치에서 위층 `README.md`의 해당 항목에 체크와 기록과 진행률을 채운다.**

| 이런 경우 | 할 일 |
| --- | --- |
| 위층의 항목이 모두 닫혔다 | 그 문서도 닫을지 사용자에게 묻는다 |
| 위층 문서가 없다 | 건너뛴다 |

머지 전에 고치지 않는다. 그러면 머지할 때마다 충돌한다.

## 못 미치면 되돌린다

**승인이 나오지 않으면 머지하지 않고 상태와 체크만 되돌린다.**

| 못 미친 것 | 되돌리는 단계 |
| --- | --- |
| 시나리오가 실패했거나 빠진 구현이 있다 | `구현 중`. 해당 항목의 체크를 풀고 남은 작업을 특정한다 |
| 계획 자체가 틀렸다 | `계획 확정`. 무엇이 어긋났는지 보고하고 `/plan-create`로 넘긴다 |

이미 들어간 커밋은 건드리지 않는다.

## 하지 않는 것

| 하지 않는 것 | 왜 안 하나 |
| --- | --- |
| 합격 판정 | 증거를 내놓는 데까지가 이 스킬의 몫이다 |
| 승인 없는 `완료` 표시 | 이 표시는 사용자의 책임이 걸리는 자리다 |
| 커밋 되돌리기 | 되돌리는 것은 상태와 체크뿐이다 |
| 승인 전 머지, 기본 브랜치로의 머지 | 앞은 검증을 건너뛰는 것이고, 뒤는 사용자가 정할 일이다 |
| 빠진 구현 채우기 | 발견하면 알리고 `구현 중`으로 돌린다. 그 자리에서 구현하지 않는다 |

## 경계

- 단계가 `계획 확정`이면 `/impl-plan`다.
- 단계가 `완료`면 이미 닫힌 문서다.
- 계획서 없이 "테스트 돌려봐"는 이 스킬이 아니다.

## 참조 파일

`references/verification.md`의 절을 필요한 시점에 읽는다.

| 읽을 부분 | 읽는 시점 |
| --- | --- |
| 받는 문서의 전제 | 1번. 어긋난 것을 찾았을 때 |
| 시나리오 실행 | 2번. 시작하기 전에 한 번 |
| 변경 내역 대조 | 3번. 차이를 찾았을 때 |
| 변경 요약 | 4번. 쓰기 전에 한 번 |
| 승인 | 5번. 승인인지 애매할 때 |
| 머지 | 6번. 머지하기 전에 |
| 위층 문서 갱신 | 7번. 위층 문서가 있을 때 |
