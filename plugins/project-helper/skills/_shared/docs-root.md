# 문서 루트 판정

## 목적

프로젝트마다 다른 문서 루트를 찾아내, 계획서와 PRD와 개발 문서를 같은 곳에 모은다.

## 핵심 지시

보관 경로를 정할 때 `docs/`를 기본값으로 가정하지 않고, 아래 순서로 문서 루트를 판정한 뒤 그 루트를 기준으로 경로를 만든다.

## 절차 흐름

### 탐색 순서

| 순서 | 판정 |
| --- | --- |
| 1 | 프로젝트 지시사항에 명시된 경로가 있으면 그것을 쓰고 탐색을 끝낸다 |
| 2 | `글로벌_아키텍처_가이드.md`와 `도메인_문서/`가 나란히 있는 디렉터리를 찾는다. 그 디렉터리가 문서 루트다 |
| 3 | `plans/` 아래에 `YYYY-MM-DD-*` 디렉터리를 가진 곳을 찾아 그 부모를 문서 루트로 본다 |
| 4 | 어느 순서에서도 후보가 나오지 않으면 `docs/`를 쓰고 그 사실을 사용자에게 알린다 |

2번과 3번은 저장소 전체를 훑지 않는다. `.git`, `node_modules`, 빌드 산출물처럼 생성물이 쌓이는 디렉터리를 제외하고, 저장소 루트에서 네 단계 깊이까지만 찾는다.

### 루트를 기준으로 만드는 경로

| 산출물 | 경로 |
| --- | --- |
| 계획서 | `<루트>/plans/` |
| PRD | `<루트>/prds/` |
| 개발 문서 | `<루트>` 바로 아래 |

### 후보가 여럿일 때

모노레포처럼 문서 루트를 여러 개 두는 구조에서는 후보가 둘 이상 나오는 것이 정상이다. 곧바로 묻지 않고 아래 순서로 좁힌다.

| 순서 | 기준 |
| --- | --- |
| 1 | 작업 대상 파일 경로의 가장 가까운 조상에 있는 후보를 고른다 |
| 2 | 조상 관계로 갈리지 않으면, 후보 경로의 이름과 요구사항에 등장한 대상 이름이 겹치는 것을 고른다 |
| 3 | 그래도 하나로 좁혀지지 않으면 후보를 번호 매김 목록으로 제시해 사용자가 고르게 한다 |

작업 대상 코드가 아직 없는 스킬은 1번을 건너뛰고 2번부터 적용한다.

### 판정 결과를 남기는 방식

| 상황 | 할 일 |
| --- | --- |
| 계획서를 만들거나 갱신하는 중이다 | 계획 최상위 문서에 확정한 루트를 기록한다 |
| 후보가 여럿이라 3번까지 내려가 사용자에게 물었다 | 고른 경로를 프로젝트 지시사항에 적어 두기를 제안한다. 적어 두면 다음부터 1번에서 끝난다 |
| 계획 최상위 문서에 기록이 있다 | 탐색을 다시 하지 않고 그 기록을 쓴다 |

## 예외 처리

| 예외 조건 | 할 일 |
| --- | --- |
| 지시사항의 경로가 존재하지 않는다 | 탐색으로 넘어가지 않고 사용자에게 경로를 확인받는다. 오타를 조용히 덮어쓰지 않기 위해서다 |
| 2번과 3번의 후보가 서로 다른 디렉터리를 가리킨다 | 2번의 결과를 우선한다. 개발 문서가 계획서보다 확정된 구조다 |
| 정한 루트에 다른 문서 체계가 이미 있다 | 덮어쓰지 않고 사용자에게 경로를 확인받는다 |
| 계획 최상위 문서에 적힌 루트가 현재 저장소에 없다 | 진행을 멈추고 사용자에게 알린다 |
| 후보가 없어 `docs/`로 정했는데 그 디렉터리도 없다 | 만들고 그 사실을 알린다 |

## 근거·예시

기본값 하나로는 문서 루트의 위치를 맞출 수 없다. 산출물을 `docs/` 바로 아래에 두지 않는 프로젝트에서는 계획서가 엉뚱한 곳에 쌓이고, 이미 있는 개발 문서를 "없음"으로 판정한다.

예를 들어 개발 문서가 `docs/project-helper/` 아래에 있고 지시사항에 경로 지정이 없는 저장소라면, 2번 순서에서 `docs/project-helper/글로벌_아키텍처_가이드.md`와 `docs/project-helper/도메인_문서/`를 함께 찾아 그 디렉터리를 루트로 판정한다.

후보를 좁히는 1번 기준이 대부분을 걸러 내는 이유는, 스킬이 불릴 때 이미 작업 대상 코드가 정해져 있기 때문이다. `packages/api/`를 고치는 중이라면 `packages/api/docs/`가 저장소 루트의 `docs/`보다 가깝다.
