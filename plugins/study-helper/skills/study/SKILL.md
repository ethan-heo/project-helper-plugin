# study

## 역할과 목적

`study`는 배우고 싶은 기술 하나를 받아, 사용자가 직접 구현할 예제 과제를 낸다. 과제를 푸는 코드는 주지 않는다. 사용자는 무엇을 배울지 정하는 결정권자이고, AI는 질문·과제 선정·환경 준비를 맡는다.

## 실행 원칙

**과제를 내기 전에 배울 범위를 사용자에게 묻고, 답한 범위 안에서만 과제를 정한다.**

학습 기조는 [`learning-principles.md`](../_shared/learning-principles.md)에 있다. 과제와 설명을 만들 때의 적용 규칙은 이 문서가 정하고, 근거가 된 원칙을 `P<번호>`로 가리킨다.

## 참조 문서 규칙

이 문서가 `study`의 실행 지시사항을 정하는 기준 문서다.

| 문서 | 역할 | 읽는 시점 |
| --- | --- | --- |
| `SKILL.md` | 실행 절차와 판정 기준 | `study` 전체 |
| [`learning-principles.md`](../_shared/learning-principles.md) | 학습 원칙의 목록 | 적용 규칙의 근거를 확인할 때 |
| `assets/readme-template.md` | `README.md` 양식 | 과제를 기록할 때 |
| `assets/task-template.md` | `TASK.md` 양식 | 과제를 기록할 때 |
| `assets/plan-template.md` | `PLAN.md` 양식 | 과제를 기록할 때 |

## 실행 절차

### 1. 배울 범위를 좁힌다

**이 기술로 무엇을 만들 수 있게 되고 싶은지 묻는다.**

기술 이름만으로는 과제의 크기와 방향이 정해지지 않는다. 사용자가 답한 내용이 과제의 만들 대상이 된다.

| 판정 | 기준 |
| --- | --- |
| 범위가 충분함 | 만들 대상 하나를 문장으로 적을 수 있다 |
| 범위가 넓음 | 여러 과제로 갈라지는 답이다 |

범위가 충분하지 않으면 질문을 이어 간다. 질문 횟수를 미리 제한하지 않는다.

질문에는 답의 구체성을 보여 주는 예시를 한두 개 붙인다.

### 2. 앞선 과제와 겹치는지 확인한다

**현재 디렉터리의 과제 폴더에서 `.study/task.json`을 읽어 같은 기술의 만들 대상을 모은다.**

| 판정 | 기준 |
| --- | --- |
| 같은 기술 | `technology` 값이 이번 호출의 기술과 같다 |
| 겹침 | 앞선 `goal`과 이번 만들 대상이 같은 동작을 요구한다 |

기술 이름의 표기가 달라 같은 기술인지 판단하기 어려우면, 추측하지 않고 사용자에게 확인한다.

겹치지 않는 만들 대상을 찾지 못하면 앞선 과제 목록을 보여 주고 범위를 다시 묻는다.

### 3. 언어와 런타임을 묻는다

**만들 대상을 정한 뒤, 무엇으로 만들지 묻는다.**

같은 기술도 여러 환경으로 만들 수 있다. 사용자가 고른 환경으로 과제 폴더를 준비한다.

### 4. 과제 폴더를 만든다

**`study`를 부른 디렉터리 바로 아래에 `<기술>-<만들 대상>` 폴더를 만든다.**

두 값은 영문 kebab-case로 줄여 쓴다. 예를 들어 WebRTC Signaling의 offer와 answer를 주고받는 과제는 `webrtc-signaling-offer-answer`가 된다.

폴더 안에는 과제를 완성하는 코드를 만들지 않는다. 사용자가 비어 있는 자리에서 시작해야 한다.

### 5. 과제를 기록한다

**과제 폴더에 `README.md`와 `TASK.md`와 `PLAN.md`와 `.study/task.json`을 쓴다.**

네 파일에 같은 항목을 넣지 않는다. 폴더를 처음 연 사람이 보는 안내는 `README.md`에, 사용자가 읽는 과제 서술은 `TASK.md`에, 사용자가 쓰는 계획은 `PLAN.md`에, 다음 `study`가 읽는 값은 `.study/task.json`에 둔다.

| 파일 | 담는 것 | 읽는 쪽 |
| --- | --- | --- |
| `README.md` | 과제 소개, 시작 순서, 나머지 세 파일의 역할 | 폴더를 처음 연 사람 |
| `TASK.md` | 만들 대상, 완성 조건, 쓰는 의존성, 실행 방법 | 사용자, 이후의 `review` |
| `PLAN.md` | 설계, 구현 단계, 막힌 점, 설계 변경 | 이후의 `hint`, `review` |
| `.study/task.json` | `technology`, `goal`, `runtime` | 이후의 `study` |

`README.md`는 `assets/readme-template.md`를 채워 만들되, 제목과 `이 과제` 절만 이번 과제에 맞게 쓰고 `시작 순서`와 `문서 위치` 절은 양식 그대로 둔다. `TASK.md`는 `assets/task-template.md`를 채워 만든다. `PLAN.md`는 `assets/plan-template.md`를 그대로 복사하고 제목 줄만 과제 이름으로 바꾼다. `.study/task.json`의 세 값은 모두 한 줄로 적고, `goal`은 겹침 판정에만 쓴다.

```json
{
  "technology": "WebRTC Signaling",
  "goal": "offer와 answer를 주고받아 두 브라우저를 연결한다",
  "runtime": "Node.js 22, 브라우저"
}
```

`README.md`와 `TASK.md`에는 과제를 완성하는 코드를 넣지 않는다. 의존성은 하는 일과 쓰는 시점까지만 적고, 호출 방법은 적지 않는다.

`README.md`에는 완성 조건과 의존성, 실행 방법을 옮겨 적지 않는다. 그 내용은 `TASK.md`에 두고, `README.md`는 어느 파일을 열어야 하는지만 가리킨다.

`PLAN.md`의 내용은 사용자가 쓴다. 절마다 놓인 예시를 이번 과제에 맞게 바꾸지 않고, 설계나 구현 단계를 미리 채우지 않는다. 만든 뒤에는 읽지도 고치지도 않는다.

### 6. 의존성을 설치한다

**고른 런타임의 설정 파일을 만들고 설치 명령을 실행한 뒤, 실행 방법을 알린다.**

| 순서 | 할 일 |
| --- | --- |
| 1 | 런타임이 설치되어 있는지 확인한다 |
| 2 | 설정 파일을 만든다 |
| 3 | 설치 명령을 실행한다 |
| 4 | 실행 방법을 `TASK.md`에 적고 사용자에게 알린다 |

설치가 끝나면 사용자는 추가 설치 없이 코드를 쓰고 실행할 수 있어야 한다.

### 7. Git 저장소를 준비한다

**과제 폴더를 Git으로 관리할 수 있게 만들고, 사용자가 코드를 쓰기 전 상태를 첫 커밋으로 남긴다.**

| 순서 | 할 일 |
| --- | --- |
| 1 | 과제 폴더의 상위에 이미 Git 저장소가 있는지 확인한다 |
| 2 | 상위 저장소가 없으면 과제 폴더에서 `git init`을 실행한다 |
| 3 | 고른 런타임에 맞는 `.gitignore`를 과제 폴더에 쓴다 |
| 4 | 과제 폴더의 파일을 모두 담아 첫 커밋을 만든다 |

`.gitignore`에는 설치한 의존성 폴더와 빌드 산출물, 환경 변수 파일처럼 다시 만들 수 있는 것만 넣는다. 예를 들어 Node.js 과제라면 `node_modules/`와 `.env`가 여기에 해당한다. `README.md`, `TASK.md`, `PLAN.md`, `.study/task.json`은 과제를 다시 찾을 때 필요하므로 모두 커밋에 넣는다.

첫 커밋의 메시지는 `chore: <기술> <만들 대상> 과제 환경 준비`로 쓴다. 이 커밋이 기준선이 되어, 이후의 변경은 모두 사용자가 직접 쓴 코드가 된다.

상위에 이미 Git 저장소가 있으면 저장소를 새로 만들지 않는다. 과제 폴더의 파일만 담아 상위 저장소에 첫 커밋을 만들고, 그 사실을 사용자에게 알린다.

준비가 끝나면 `git status`와 `git diff`로 자기가 쓴 코드를 확인할 수 있다는 점과, 막혔을 때 첫 커밋으로 되돌아가 다시 시도할 수 있다는 점을 한 줄로 알린다.

## 적용 규칙

**과제와 설명을 만들 때 아래 규칙을 지키고, 근거가 된 원칙을 `P<번호>`로 확인한다.**

| 적용 자리 | 규칙 | 근거 |
| --- | --- | --- |
| 범위 질문 | 아는 것과 모르는 것을 진단하지 않고, 만들고 싶은 것을 묻는다 | P15 |
| 범위 질문 | 사용자가 답한 말로 만들 대상을 적고, 다른 말로 바꾸지 않는다 | P7 |
| 과제 선정 | 앞선 과제와 만들 대상이 겹치지 않게 한다 | P12 |
| 과제 선정 | 과제 하나에 사용자가 막힐 지점을 하나 이상 남긴다 | P1, P9, P17 |
| 과제 제시 | 이 과제가 그 기술의 어느 자리에 있는지 `README.md`에 한두 문장으로 적는다 | P8 |
| 과제 제시 | `README.md`는 안내만 담고 과제 서술은 `TASK.md`에 둔다 | P14 |
| 완성 조건 | 사용자가 스스로 확인할 수 있는 조건으로 적는다 | P3, P13 |
| 의존성 설명 | 하는 일과 쓰는 시점까지만 적고 호출 방법은 남겨 둔다 | P1, P9, P10, P11 |
| 의존성 설명 | 설명을 `TASK.md` 한곳에 모으고 과제 서술에 섞지 않는다 | P14 |
| 작업 계획 | `PLAN.md`는 빈 양식으로 두고 사용자가 설계를 적게 한다 | P1, P9, P15 |
| 환경 준비 | 설치까지 끝내 사용자의 노력이 과제에만 들게 한다 | P1 |
| 환경 준비 | 첫 커밋으로 기준선을 남겨 사용자가 자기가 쓴 코드만 확인하게 한다 | P3 |
| 환경 준비 | 되돌릴 수 있는 상태를 만들어 해법을 보기 전에 여러 번 시도하게 한다 | P9, P17 |

### 이 스킬에서 쓰지 않는 원칙

P2, P4, P5, P6, P16, P18, P19는 과제를 내는 자리에 해당하지 않는다. 꺼내 보기와 간격 반복, 실패 뒤의 전략 변경은 사용자가 직접 하거나 `hint`·`review`가 맡는다. 원칙을 더하거나 고칠 때는 이 목록도 함께 고친다.

## 예외 처리

| 예외 조건 | 할 일 |
| --- | --- |
| 기술 이름 없이 불렀다 | 무엇을 공부할지 묻고 기다린다 |
| `.study/task.json`을 읽을 수 없다 | 그 폴더를 판정에서 빼고 건너뛴 폴더를 알린다 |
| 사용자가 과제를 바로 달라고 한다 | 범위 질문을 한 번은 하고, 답을 받은 뒤 과제를 낸다 |
| 같은 이름의 과제 폴더가 이미 있다 | 덮어쓰지 않고 기존 폴더를 알린 뒤 다른 만들 대상을 제안한다 |
| 네 파일 중 하나를 쓰지 못했다 | 과제를 낸 상태로 두지 않고 실패한 경로를 알린다 |
| 고른 런타임이 설치되어 있지 않다 | 설치를 시도하지 않고 사실을 알린 뒤 다른 런타임을 묻는다 |
| 의존성 설치가 실패했다 | 과제 폴더와 네 기록 파일은 남기고 실패한 명령과 출력을 알린다 |
| Git이 설치되어 있지 않다 | 저장소 준비를 건너뛰고 과제는 그대로 내주며, 건너뛴 사실을 알린다 |
| 커밋할 사용자 이름이나 메일 주소가 없다 | 값을 임의로 정하지 않고 첫 커밋 없이 두며, 설정할 명령을 알린다 |
| 과제 폴더의 상위가 이미 Git 저장소다 | 저장소를 새로 만들지 않고 상위 저장소에 과제 폴더를 커밋한다 |

## 경계

- 과제를 푸는 코드와 정답은 제시하지 않는다.
- 이미 받은 과제의 힌트는 `hint`, 완성한 예제의 피드백은 `review`가 맡는다.
- 개념을 설명하는 강의는 이 스킬의 범위가 아니다.
